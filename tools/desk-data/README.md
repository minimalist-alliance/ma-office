# desk-data

The read-only root helper behind `deskd`'s `data.*` methods: it lists and reads the member's files on `/data` so a member can download all their data, and the transfer script can move a desk to the member's own hardware. Decision: `docs/decisions/draft-data-export-and-transfer.md` (decisions 2 to 5). Protocol: that ADR's appendix, "`data.sock`, between deskd and `desk-data`".

| File | Installed as |
|---|---|
| `desk-data` | `/usr/local/lib/ma/desk-data`, `0755 root` (Python 3, Debian 13's `python3`, stdlib only) |
| `desk-data.socket` | `/etc/systemd/system/desk-data.socket`: `/run/desk/data.sock`, `0600`, owner `desk`, `Accept=yes`, `MaxConnections=24` |
| `desk-data@.service` | `/etc/systemd/system/desk-data@.service`: one root process per connection, the connection on stdin |
| `desk-data.tmpfiles` | `/etc/tmpfiles.d/desk-data.conf`: `/data/.ma-export-tmp`, `0700 root` |
| `install.sh` | Installs the four above on a desk that isn't built from the image (task 31's self-hosted desk) |
| `tests/` | `unittest`, no root needed |

## Why root
`deskd` runs as `desk` and sees only `/data/desk`. The Browser's profile is `0750 kiosk` with `0600` files, and each app's data is `0700` under its own uid. Widening `deskd`'s container would give it read access to all of that all the time. Instead, `desk-data` runs only for the length of one request, like `desk-units`, and only `deskd` (uid 1100, checked with `SO_PEERCRED`) can ask. The unit keeps one capability, `CAP_DAC_READ_SEARCH` (read what isn't its own), and nothing else.

## What it never does
- Write, rename or delete anything under `/data`, except its own scratch copies in `/data/.ma-export-tmp`. `ProtectSystem=strict` and `ReadOnlyPaths=/data` enforce it; there's no verb that writes.
- Follow a symlink. Every path is opened a component at a time from the part's root with `O_NOFOLLOW` (and `O_DIRECTORY` for directories). A link is listed as `link` with its `target`, and reading it, or through it, is `invalid`.
- Read outside the part asked for, read anything that isn't a regular file, or block on a FIFO.
- Use the network (`PrivateNetwork`, `AF_UNIX` only), start a program, or log a file name (the journal gets the op and why it was refused).
- Read the machine's own data: `rtc`, `selfhost` (a self-hosted desk's key and pairing, task 31), `desk-egress`, `.ma-volume`, `desk/volume.json`, apps' packages and caches, the Browser's caches and lock files (decision 4). They're left out of `parts` and `manifest`, and `read` says `not_found` for them.

## The protocol, and what it settles that the ADR leaves open
One request line, one reply header, and for `read` the chunked body and trailer, exactly as the appendix says. Beyond it:

- **Requests are strict.** Unknown fields, duplicate keys, `NaN`, `"v": true`, `limit` outside 1 to 2,000 and a request over 16,384 bytes (newline included) are `bad_request`. `cursor` and `limit` may be left out (`null`, 2,000), and so may `offset` (0).
- **Paths:** relative, `/`-separated, no empty, `.` or `..` component, no NUL, each component at most 255 bytes, at most 4,000 bytes in all (longer paths are left out of manifests; a UTF-8 path that long still fits a 16 KiB request with every character `\u`-escaped). A name that isn't UTF-8 is listed with each bad byte as `\udcXX` (Python's surrogateescape) and `read` takes it back the same way.
- **Manifest entries:** `mode` is the permission bits as a number (`0o600` is 384), `size` is 0 for a directory or a link, and FIFOs, sockets and devices aren't listed. `cursor` is the last path of the previous page and is only compared, never opened, so a page never repeats or skips even when the cursor's own file is gone.
- **`parts`:** `files` and `bytes` count regular files and their sizes on disk, after the exclusions.
- **Labels:** as decision 4, plus `browser-readable` "Bookmarks and history". A stored directory called `browser-readable` would be shadowed by the generated part, so it's left out.
- **`browser-readable`:** `<profile>/bookmarks.html` for each directory under `browser/profile` with a `Bookmarks`, `<profile>/history.csv` for each with a `History` database. Their manifest `size` is the source's, an estimate; `read`'s `size` is exact. `mtimeMs` is the source's, and the files are made the same way every time, so a resumed read checks. `history.csv` starts with a UTF-8 byte order mark (so a double-click opens it right in a spreadsheet), and a cell a spreadsheet would run as a formula (`=`, `+`, `-`, `@`) gets a leading `'`, because page titles are anyone's.
- **`offset` past the end** sends no bytes, and the trailer gives the hash and length of what's there, which the reader sees doesn't match.
- **A file that changes while it's read gets no trailer.** The trailer hashes what was sent, so on its own it can't see a file rewritten in place during the read: the body would be old bytes and new, and the trailer would match them. So a file read in place (not a SQLite copy) is `fstat`ed before its first byte and after its last, and if its device, inode, size, mtime or ctime moved, the body stops short with no zero and no trailer, the failed-read ending, which deskd turns into an END with an empty payload and both readers ask for again. A file that shrank or grew while it was read ends the same way (it used to end with a trailer for what was read). ctime is what makes it sure: a program can set mtime back, or anywhere, but not ctime. Timestamps come from a coarse clock (about 4 ms), so a write in the same tick as the one before the read could leave them unmoved: a file changed in the last 50 ms waits until it has been still that long, by ctime, and one that never is for 10 s is `failed` before its header. Not caught: a program writing through a shared memory map, which can change a page it had already dirtied without moving any time.
- **Timing:** a `read` header can take up to 10 s for a SQLite database that its program keeps busy (below), or for a file that keeps changing (above), and a resumed read hashes the part before `offset` before its first chunk (about 1 s per GB). A peer that sends no request for 30 s is dropped. A reader that takes nothing for 330 s is dropped: that's past deskd's 5 minutes without credit (`API.md` §12), after which deskd ends the transfer and closes the connection itself, so 5 minutes is the limit a reader meets, as `API.md` promises, and this is only a backstop. It was 30 s, from one idle limit for both, which ended any read whose reader paused for half a minute, a database's included, which then has to start again from 0.

## SQLite: a consistent copy while the member keeps working
A regular file that starts with the 16 bytes `SQLite format 3\0` is never sent from `/data` directly. The helper makes a consistent copy in this connection's own directory in `/data/.ma-export-tmp/`, and that copy is what's measured (`size`) and sent. The database's `-journal`, `-wal` and `-shm` are left out of manifests and are `not_found` on `read`: the copy is whole. The copy is unlinked as soon as it's opened for sending, so it's gone when the process is, however it ends. Every start empties what no live helper holds (each holds an `flock` on its own directory). It works like this, 10 s in all:

1. **SQLite's online backup**, for up to 1 s. The source is opened `file:…?mode=ro` (never `immutable`) and copied in one step (`pages=-1`), so the whole copy is one read transaction and a writer can't make it start over. SQLite opens the source by its path, so afterwards every file it has open must be one of the inodes reached with `O_NOFOLLOW` (the database, its `-wal`, `-shm` or `-journal`); otherwise the read is `failed`. This works with a live writer in WAL mode, even with `/data` read-only: SQLite reads the WAL itself when it can't write the `-shm`.
2. **Chromium's exclusive locks.** Chromium keeps its databases in exclusive locking mode, so no other process can read them while it runs. On Chrome on the dev box, `History`, `Web Data` and `Login Data` all stayed `SQLITE_BUSY` while it ran and opened once it stopped. So the online backup never gets in, and after its 1 s the helper copies the files instead: the **copy-when-quiet**. It's also used straight away when `/data` being read-only stops SQLite (`SQLITE_READONLY*`, `SQLITE_CANTOPEN*`): a WAL database closed cleanly has no `-shm` to read, and a hot journal left by a crash can't be rolled back read-only.
3. **Copy-when-quiet:** the database, and its `-wal` or `-journal` if non-empty, copied byte for byte (never the `-shm`). It's taken only if none of them was written in the last 200 ms, which means a write during the copy moves their mtime, even with coarse (about 4 ms) timestamps. It's kept only if each one's mode, inode, size, mtime and ctime are the same after the copy as before, and the database is still the inode that was opened. Otherwise the helper tries again every 250 ms, and if 10 s go by without a quiet copy the read is `failed`. Never a torn file.
4. **Repair in scratch:** the files copied are the state a crash would leave, so SQLite opens them in scratch and recovers them: it rolls back a hot journal, or replays the WAL up to its last commit. An online backup of that makes the one whole file that's sent. What's sent is the database as of its last commit on disk, without any transaction that was open.
5. **Not a database after all** (`SQLITE_NOTADB` or `SQLITE_CORRUPT` from the online backup: a damaged or partial file) is sent as it is, since there's nothing to keep consistent.
6. **Room:** a copy has to leave 2 GiB free on `/data` after twice the database's size on disk (database, `-wal` and `-journal`), and after what the copies other connections are making may still write. That's the Browser's floor in the desk app contract; under 800 MB Chromium evicts site storage (ADR 0035). Otherwise the read is `failed`. Each connection is its own process, so each says what its copy in progress may still write in a `room` file in its own scratch directory, and the check and the claim are made under an `flock` of `/data/.ma-export-tmp` itself (a lock file in it would be emptied by the next helper to start). A directory no live helper holds doesn't count. What a copy has written so far counts twice, in the free space and in its room, which errs toward the floor. Once a copy is made its room is given back, as its bytes are in the free space by then. `bookmarks.html` and `history.csv` claim room the same way. Before this, each read checked the free space alone, so several big databases read at once could take `/data` past the floor.

## In the image (from `ma-desk-0.2.6`, task 37)
The image carries these four files as copies: `image/recipe/files/usr/local/lib/ma/desk-data`, `image/recipe/files/etc/systemd/system/desk-data.socket` and `desk-data@.service`, and `image/recipe/files/etc/tmpfiles.d/desk-data.conf` (its own file, so `build.sh`'s `systemd-tmpfiles --create .../ma.conf` doesn't make the scratch directory on the root; it's made on the volume at boot). `build.sh` makes the helper `0755` and enables `desk-data.socket` beside `desk-units.socket`. **This directory stays the source:** change a file here, run the tests below, copy it into the recipe, and bake. `image/bake.sh` refuses to bake when a copy differs.

`image/verify.sh` section 3b3 checks a booted image: `desk-data.socket` enabled and listening, `/run/desk/data.sock` `0600 desk`, `/data/.ma-export-tmp` `0700 root` on the data volume, `kiosk` refused by the socket's mode and root by `SO_PEERCRED`, `parts` answering for `desk`, and a `read` of `browser/profile/Default/History` with the Browser running that comes back whole (size, trailer, SHA-256), passes SQLite's `integrity_check` and has the page verify visited, with no scratch file left behind. It prints `systemd-analyze security desk-data@.service`'s score for the record.

`desk-runtime.md` §1 (the process), §2 (`data.sock`, `/data/.ma-export-tmp`) and §8.7 (the socket) describe it for the desk. A desk on an image up to 0.2.5 gets it from `install.sh` over SSM, and a root swap takes it off again; a swap to 0.2.6 or later brings it back.

Smoke request, as `desk`, on a desk:
```sh
sudo -u desk python3 -I -c 'import socket; s = socket.socket(socket.AF_UNIX); s.connect("/run/desk/data.sock"); s.sendall(b"{\"v\":1,\"op\":\"parts\"}\n"); print(s.recv(65536).decode())'
```

## Self-hosted desk (task 31)
`sudo ./install.sh` from this directory, after the desk's own install (it refuses unless it's root, the user `desk` is uid 1100, and `/data` and `/run/desk` exist). It's idempotent, prints each thing it did or left, and restarts the socket only when a unit changed.

## Tests
```sh
python3 -I -m unittest discover -s tools/desk-data/tests -v
```
56 tests, about 15 s, no root, nothing outside a temporary directory. `DESK_DATA_TEST_LOG=1` shows the helper's journal lines. They cover every op; the request rules and limits; the denied uid; idle and stalled peers, and a reader that pauses past the request's 30 s; exclusions (caches, locks, machine parts, `volume.json`, apps' packages, SQLite siblings, the shadowed `browser-readable`); `agent/keys`' `master.key` and sealed files, which do go (ADR 0042); `..`, absolute, NUL and over-long paths; links out of the part, into another part and in the middle of a path; FIFOs; resume from an offset against a full read; files that shrink, grow, and are rewritten in place (mtime put back) mid-read, which end with no trailer, and a resume of one rewritten since; a file that has to settle, one that never does, and one with an mtime in the future; a WAL database with a live writer and uncommitted rows (also on a read-only directory), one closed cleanly on a read-only directory, one held in exclusive locking mode as Chromium does, one that never stops changing, a hot journal after a crash, and a path swapped under SQLite; copies in progress in other helpers counting against the floor, including two reads at once, with a gone helper's room not counted; manifest paging at several page sizes; `bookmarks.html` and `history.csv` from real-format `Bookmarks` and `History`; and the scratch directory's cleanup.

They passed on this repo's dev box (Ubuntu 24.04, Python 3.12, SQLite 3.45) and in a `debian:trixie` container (Python 3.13.5, SQLite 3.46.1, the desk's versions), both as an ordinary user and as root. The 10 added and 3 changed in the data review (`docs/sub-status/data-review-fixes.md`) have run on the dev box only, as an ordinary user: that machine has no container runtime now. Not yet run: under the real unit's sandbox as root on a desk, where `/data` is truly read-only (`EROFS`, which the tests stand in for with `0555` directories).
