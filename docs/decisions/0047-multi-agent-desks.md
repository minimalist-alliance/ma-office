# 0047. Many agents on a desk, each its own app, set up by the lead agent

**Status:** Proposed (2026-11-08), first pass of task 49, for the AI Engineer's and the Product Designer's review and the Security Analyst's read before prod. *(Note 2026-11-09, from the code on main: `sub/multi-agent` is merged, so `desk-agent` and the Desk app have it; it is in no image release yet, `image/RELEASES.md`.)*
**Date:** 2026-11-08
**Amends:** design 9.2 (staff agents, "default cap 5"), 9.6 (tools), 9.10 ("scheduled runs come in Phase 4") and 9.11 (agent-to-agent, which was between desks only). Builds on ADR 0020 (limits), 0042 (keys sealed on the desk) and 0043 (limit layers).

## Context
The owner, on task 49: "I would want to be able to create as many agents on a desk as possible and they need to be able to send messages to each other if the user opts in for that. Some agents might be in solo mode. ... Agents need their own workspace with a storage limit. They need timers to trigger certain actions. The main idea I think though is that the lead agent would help setup all of the other agents guided by the user. Each agent should show up as a separate "app" on the user's desk ..." (the whole quote is in `~/subcontractor-tasks/49-multi-agent-desk.md`).

Until now `desk-agent` ran one agent, the manager, with no tools: `agent.create` answered `agent_cap`.

## Decision

1. **Many agents, one runtime each, one process.** Every agent is a row in `agent.db` and its own `ManagerAgent` instance (`forAgent`), with its own binding, status and one run at a time. The desk's **runs at once** are capped at 4 (`TierCaps.RUNS_AT_ONCE`); that, not the number of agents, bounds memory. Measured on a build box (README, "Footprint, many agents"): an idle agent costs about 0.07 MiB of RSS and no CPU; four runs at once peak under 100 MiB against the container's 320 MiB. So the **agent cap is a tier setting** chosen for disk and spending, not memory: **Alliance 10, Officer 32, Founder 50** (ma-platform `TIER_AGENT_DEFAULTS`; desk-agent's built-in default without a Platform is Alliance's, since the fix pass). The cap counts the lead.
2. **The manager is the lead.** Id `manager` and wire `role: manager` stay, so deskd, older clients and rollbacks keep working; `lead: true` marks it, and its default name is now `Lead` (renamed once on desks that kept `Manager`). It can't be deleted.
3. **The lead proposes; the member decides.** The lead's tools (`desk_agents`, `desk_choices`, six `propose_*`) never change anything. Each proposal is stored with its payload's canonical JSON and SHA-256 and shown as a card on the lead's reply. `agent.proposal.answer` applies it only on the member's yes, echoing the hash (design 9.6's approval integrity), through exactly the code a hand-made change runs, so every check applies again. Proposals expire after 24 hours, answer once, and are in the audit log. Everything a proposal can do the member can do by hand in each agent's settings.
4. **Tools on every provider.** A run is a loop: a model call, the tools it asked for, their results, again, each call reserved against every limit before it goes, so the run's steps (50) and dollars ($2) bound it. Anthropic's Messages API and the Responses API (OpenAI, xAI) each map tools both ways in their adapter. Tool output goes back capped at 20,000 characters, and anything from a tool, a file, another agent or a timer is framed as data, never the member's word (design 9.7).
5. **Agent-to-agent messaging is opt-in, synchronous and bounded.** A new agent is solo. The member gives an agent links to other agents, each with a rules-of-engagement note of at most 500 characters; a message goes only along a link from an agent that isn't solo (see "Fix pass": solo now means sends no messages), and its rules travel with it (in the receiver's prompt and in the log). `message_agent` runs one turn of the receiver with the receiver's own key, tools and limits, and returns its reply. Hard limits, all tier settings, each checked before the receiver runs: messages per hour per pair (30), chain depth (3), no message to an agent already in the chain (no loops, no deadlock), and a share of the receiver's daily dollar limit for message-started runs (25%). Every message, refused or not, is in `agent.a2a.list`, kept 100 days. This is within one desk; design 9.11's desk-to-desk A2A stays Phase 4.
6. **A workspace per agent.** `/data/agent/workspaces/<agentId>/`, with a quota per agent (the tier's default, adjustable per agent up to the tier's largest), private unless the member shares it read-only with chosen agents. Paths are checked as text and then walked one component at a time without following links; writes go through a temporary file and an atomic move. Writes stop with 1.5 GiB of the disk left (the fix pass; first 512 MiB), and the quotas together may not pass half the disk. Agents can list, read and write; deleting is the member's, in settings.
7. **Timers.** One-shot (`inMinutes`, or a time) and repeating (days at a time, or every N minutes, at least the tier's minimum), in the member's zone (the one the limits use), at most the tier's number per agent. Kept in `agent.db`, so they survive restarts; one thread sleeps until the soonest. A fire starts a run like a member's message, so it counts toward every limit; its cost is kept on the timer. Busy retries a minute later, ten times; a one-shot missed by under a day runs at start.
8. **Each agent is its own app.** The web keeps the existing `agent` tile as the lead's and adds an `agent:<id>` item per staff agent, created and removed as `agent.state` says. The look is data in one place, `web/agent/src/look/`: 24 line icons, 12 tones with a value per theme, and one foreground (`#fafafa`) that a test checks at 4.5:1 or more on every tone in every theme. An uploaded PNG is decoded on the desk by our own strict decoder (no AWT in the container), at most 256 KiB and 512 by 512, and kept only as a mask (its alpha, or its darkness if it has no transparency) re-encoded with no other chunks; the client draws it in the foreground. `agent.icon.get` answers only the desk's owner, as every `agent.*` method does.
9. **Schema: additive, no version bump.** Task 49's tables and columns are created at every open if missing (`TeamSchema`), and `user_version` stays 1, so an older desk-agent still opens `agent.db` after a rollback (it would refuse a newer version). It sees staff agents in its list and can't run them, which is safe.
10. **Tier settings come from the Platform.** The Management Console's Prices/limits sets each tier's eight values (`agents` per tier in `pricing#current`); the desk's config carries the owner's tier's as `agentDefaults.tier`, deskd passes it through in `desk.account.set` as `tier`, and desk-agent falls back to its built-in defaults field by field.

## Consequences
- The owner's "as many as possible" is a console setting, not a code change, and memory isn't what limits it.
- A runaway between agents is bounded four ways (rate, depth, loop, spend share) on top of every existing limit; the worst case is one chain of four runs.
- Deleting an agent removes its thread, workspace, timers, icon, links and limits; the audit log and agent-message log keep their rows.
- The lead's proposal flow puts a confirm step on every change, which costs the member one click per change. Batching cards is a later refinement.
- The look's ids live in TypeScript and are mirrored in `TeamTools` for the lead's validation; a test checks they match when the web folder is present.
- `AgentService` grew, and a parallel branch (`sub/deskd-guild-sessions`) changes the same file and `ManagerAgent` (its `forAgent` has the same shape as this one's); merging them needs care.

## Fix pass (Nov 8)
Three reviews (the AI Engineer's, the Product Designer's, the Security Analyst's) found problems in the first pass; every High is fixed. Interface details are in `services/desk-agent/docs/multi-agent.md`. Decisions taken:

- **Solo means the agent sends no messages.** It still receives from any agent whose link names it, under that link's rules. Before, "solo" cut an agent off both ways, so a member could not have an agent that only answers. Every new agent still starts solo. *Consequence:* a link is the sender's consent and the member sets it in the sender's settings; the receiver's settings show incoming links read only.
- **A message-started run sees only the pairing and no shared workspaces.** B, answering A, sees the A-B messages, not B's thread with the member, and cannot read workspaces shared with B (its own stays). *Consequence:* a sender can't pull the member's private thread or files out through a helper agent; an agent that needs a file must have it in its own workspace.
- **Alliance as the fallback.** desk-agent's built-in defaults are Alliance's (10 agents, 50/200 MB, 5 timers, 15 minutes, 20 an hour, depth 3, 25%). The last tier and age band received are kept; a missing tier changes nothing, and the Platform leaves the tier out when it can't read it. *Consequence:* a desk that can't learn its tier is held to the smallest limits, not the largest.
- **The 1.5 GiB floor and the 50% budget.** Writes stop below 1.5 GiB free; the quotas together may not pass half of `/data`; a create with no size takes what's left (at least 10 MB). Quotas are stored at create and held to the tier's maximum at use. *Consequence:* a full set of agents can't fill the disk the desk itself needs; lowering a tier's default never shrinks an agent that exists, and lowering the maximum holds agents to it at their next write.
- **The lead's tile stays the Agent app's tile; Look is hidden in the lead's settings** (the Product Designer's M15 call). The lead is the desk's own agent, not a staff agent with a look. *Consequence:* only staff agents choose an icon and tone; the lead's mark can't be mistaken for another agent's.
- **Over-cap agents are paused, not deleted.** When the cap falls below the count, the oldest agents stay (the lead never counts out) and the rest show `paused` with `agent_cap` and refuse runs. Timers beyond a tier's count show `over_cap`. *Consequence:* a tier change never destroys a member's work; raising the cap brings agents back.
- **One run slot is the member's.** Timer and message-started runs stop at 3 of the desk's 4 slots. Guild members' runs have their own pool. *Consequence:* a busy chain of agents can't lock the member out of their own desk.
- **Also:** names unique per desk; proposals carry `origin` and `before` and are capped (10 pending, 5 per run); desk-wide message limits (`desk_rate`, `desk_spend`); timers wait while the member's age band isn't adult; a step cut off or refused ends the run `failed` before any tool runs.

## Not decided here
- Memory and compaction (design 9.10), browser and notebook tools for agents, and scheduled runs that wake a stopped desk (Platform wake-on-schedule).
- Whether agents should be able to delete workspace files (now the member's alone).
