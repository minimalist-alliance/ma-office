# ADR 0091: Notebook colors: the tabs' six names in the page, labels in the page row

Highlight and text color on text, a color on blocks, and a label on pages, so a member can organize notes and mark what matters.

**Status:** Proposed. Built on `sub/notebook-color` (the data side, Region Engineer stream `nb-data`) with the menus on `sub/notebook-color-menus` (`nb-menus`). It changes the stored format, so the Region Engineer merges it after a Security short read.
**Amends:** [ADR 0015](0015-notebook-editor-tiptap-yjs.md) (the document schema gains a mark and an attribute) and [ADR 0044](0044-notebook-service-hocuspocus-on-node.md) (one column, three methods). **Builds on:** [ADR 0080](0080-guild-shared-desk.md) (a guild's shared Notebook and its edit budget), design 3.12 (colors stored by name and mapped per theme) and 5.1 to 5.6.
**Date:** 2026-11-10.

## Context
The owner, Nov 10 about 12:50 am MT: "I want the Notebook and Files apps to have their own unique color schemes that still go with the whole minimalism thing and fit well with the grey and blues of the MA branding. I want context menu features in Notebook as well. Especially the ability to use color to organize better and highlight key things."

Before this, a page had one highlight color, stored as the name `yellow` (STATUS question 2), and pages had no color of their own; tabs had six named colors. Page text is a Y.Doc bound to TipTap through `@tiptap/y-tiptap` 3.0.10, which projects Yjs through the editor's schema, and the desk's `desk-notebook` stores the Yjs state, ProseMirror JSON read from it, versions and a Markdown copy. The shared interface with the menus' builder is `~/work/region/notebook-color-interface.md` ("Final names", 2026-11-10).

## Decisions

### 1. What's stored is a color's name, the binder tabs' six, never a color value
`blue`, `green`, `amber`, `rose`, `violet` and `slate`: `PALETTE_IDS` in `web/notebook/src/model/colors.ts` is the tabs' `TAB_COLORS`, the names the owner has already seen (the coordinator's call, 2026-11-10, from the Product Designer's spec, `~/ma-coord/design-drafts/app-colors/README.md`, "Notebook's organizing colors"). So one color means the same thing everywhere: a page labeled green, a green highlight and a green callout belong together. There's no red: red is for danger and errors. The values for each name, per theme (Light, Dusk, Dark) and per role (the spec's `label`, `highlight`, `text` and `callout`), are the UI's, in one module, `web/notebook/src/ui/palette.ts`, the menus' builder's. A new palette or theme changes how a name looks and never rewrites anyone's notes. Anything stored that isn't one of the six (a hex someone wrote, a later palette's name) draws as none, and is kept as it is. `model/` imports nothing from `ui/`, since the desk's service bundles `model/` alone. (An earlier draft of this branch stored `c1` to `c8`; nothing with those was merged or shipped.)

### 2. The shape
- **Highlight:** the existing `highlight` mark, attribute `color: <name>`. A page from before holds `color: "yellow"`; it's kept as stored and reads as `amber` (`highlightId`), which is today's yellow. The toolbar's one-click highlight (Mod-Shift-H) now writes `amber`, the default highlight.
- **Text color:** a new mark, `textColor`, attribute `color: <name>`. It can sit with a highlight on the same text.
- **Block color:** attribute `color: <name> | null` on `paragraph`, `heading`, `blockquote`, `codeBlock`, `listItem`, `taskItem`, `bulletList`, `orderedList` and `taskList` (`COLOR_BLOCK_TYPES`). A callout is a colored block. A new block made by Enter starts uncolored (`keepOnSplit: false`).
- **Page label:** `PageRec.label?: <name> | null`, absent or null for none. Page metadata like the tab's color, not page text: in the desk's `pages.label` column, sent in `notebook.tree` only when set, so a page without one reads exactly as before.
- **DOM:** `<mark data-color>`, `<span data-text-color>` and `data-block-color` on the block's element. Never an inline style (the Desk app's CSP has no `style-src 'unsafe-inline'`), and the colors come from CSS per theme.

### 3. The commands
`web/notebook/src/model/commands.ts`, plain ProseMirror commands with wrappers for the live editor: `setHighlight`, `setTextColor`, `clearFormatting` (every mark but links), `setBlockColor(editor, at, name)`, and `colorsAt` and `blockAt` for a menu's check marks. `at` is a document position, such as where a right click landed, since the schema's blocks have no ids; `null` means every block the selection touches. The block colored is the innermost list item around the position, or else the top-level block, so a quote is colored whole and a list item on its own. `NotebookBackend` gains `setPageLabel`, `duplicatePage` and `importPage`. The page list reads `label`, with `labelOf`, `filterByLabels` and `sortByLabel` in `model/tree.ts`, and search takes `labels`.

### 4. Sync, history and undo
- **Colors are page text.** A command is a ProseMirror transaction, which the Yjs binding writes like typing: it syncs live to every editor of the page (a guild's shared Notebook included), Mod-Z undoes it through Yjs's UndoManager, and a version taken after it holds it. Coloring writes Yjs formatting and attributes and deletes no character.
- **On a guild's desk coloring is free.** The edit budget (`owners.ts`) charges only another member's text, blocks and embeds removed, and formatting and attributes were already anyone's to change, so a member colors another's words and blocks at no cost. Tested with real providers.
- **A label is metadata.** `notebook.page.label` changes the page row and bumps the tree's `rev`, so it reaches every session through the `notebook.tree` topic, last writer wins. It isn't page text, so it isn't in a version or in Yjs's undo, as a tab's color isn't. It doesn't change `updatedAt`.

### 5. On the desk
- **`pages.label`** is added without a schema bump, created if missing at every start, as `page_clients` and `page_updates.actors` were: a build without it never names the column, so a rollback still opens the file and leaves labels as it found them, and `PRAGMA user_version` stays 1.
- **Three methods,** relayed by deskd as the rest are: `notebook.page.label {pageId, label}`, `notebook.page.duplicate {pageId}` and `notebook.page.import {tabId, after?, doc, label?}`. Anyone who may make a page may use them on a guild's desk.
- **A duplicate is exact.** Its body is the original's Yjs content cloned into a new Y.Doc under a new client id (`model/ydoc.ts`, `copyState`), so every mark and attribute comes along, known to this build or not, and the copy goes right after the original with its label. Its history starts fresh. On a guild's desk the copy's text is the copier's (its client id goes in `page_clients` in the same transaction), so they may trash it.
- **An import** is checked against the schema first (`cleanDoc`): node and mark types it doesn't have are taken out (their text stays), a link that isn't http, https or mailto loses its link, colors that aren't one of the six names are dropped, and attributes it doesn't know are kept. Its body is written without the schema (`docState`), as the editor's binding would write it, plus those attributes.
- **Search** filters by `labels` and says each hit's label; labels with no words list those pages by title, as `has:checklist` alone does.

### 6. Export and import
- **The notebook's own file** (`model/notebookFile.ts`): `{format: "ma-notebook", version: 1, exportedAt, palette?, pages: [{title, label, createdAt, updatedAt, doc}]}`, saved as `<title>.notebook.json`. Pages leave and come back exactly: names, labels, every mark and attribute. `palette` records what each name looked like at export time (its four roles), for readers elsewhere. A reader keeps fields it doesn't know; only a change an older reader would get wrong bumps `version`, and that reader refuses the file rather than guess. Import maps by name; a color that isn't one of the six is mapped to the nearest in the UI's palette for its role, or dropped (near white behind text, and near black or white as text, count as no color).
- **HTML** carries the names as the editor renders them, so pasting it back keeps them, and a stylesheet made from the palette's light values draws them: a callout with its `callout` background and a 3 px left rule in its `label` value, as the spec has it, and an old page's `yellow` as amber.
- **Markdown** has no colors. A highlight stays `<mark>`; with the palette, `<mark style>` and `<span style>`, which GitHub drops and most other readers draw. Block colors and labels are in HTML and the notebook file only. The desk's `readable/` copy has no palette, so it's as before.
- **Pasting from other apps** maps a pasted color to the nearest name only when the UI hands the schema its palette (`schemaExtensions({ nearestColor })`); without it, as before, they're dropped.

## Compatibility and ship order
- **Older pages** open unchanged: no field means no color, the old `yellow` reads as `amber`, and nothing is rewritten on open.
- **Ship `desk-notebook` and `deskd` before (or with) the Desk app.** An older `deskd` answers `not_found` ("No such method") to the three methods, and an older `desk-notebook` does the same; the menus should say the desk needs an update. An older `desk-notebook` keeps a colored page's Yjs state byte for byte and reads it schema-free for search, versions and `readable/`, so it loses nothing at rest, but its version restore goes through its own schema: a version with a text color fails to restore (an error, no change), and one with only block colors restores without them. An older desk ignores `labels` in search.
- **An editor older than this** (a tab left open across a release) can't keep what its schema lacks: `y-tiptap` projects through it, so the first edit drops every block color on the page, and on a guild's shared page that's everyone's. **The guard** (below) stops it at the desk. The storage side keeps unknown fields too (schema-free reads, exact duplicates, imports that keep attributes).

## The guard: an editor older than the page can't strip it
- **The app says its page schema when it opens a page.** The provider's token, which the contract leaves free ("any non-empty string"; deskd has already checked the session and relays `collab` unread), is `schema=2` (`collabToken()`, `NOTEBOOK_SCHEMA` in `model/compat.ts`: 1 before colors, 2 with them). A token that says none, as every app before this one sends (`desk`), is schema 1.
- **desk-notebook refuses a change from an older editor to a page holding what it would drop** (`socket.ts`, before Hocuspocus sees the message; `holdsNewerThan`): for schema 1, any block with a color or any `textColor` run. The whole update is refused, nothing of it applied, and the page is closed for that provider as a refused update always is: it stays attached, what it sends is dropped until it opens the page again, and its empty sync as it opens isn't a change, so it can still read. Every other page, and everyone else, carries on. An older editor on a page with no colors edits as before, which is what lets the desk ship ahead of the app.
- **What the old tab sees.** An app that said a schema gets the close reason `reload`: the page goes read-only with "Notebook was updated. Reload to keep editing." (`web/src/notebook/panel.ts`; the UI/UX Engineer can polish the words). An app from before the guard knows only `page_full` as a refusal, so that's what it gets: its only read-only path, with that path's "This page is full. Start a new page to keep writing." It's the wrong reason in words, and it stops the tab taking text it can't keep; a new page has no colors, so writing there works, and a reload fixes it all. Text typed into the refused change stays on that tab's screen, unsaved, with the browser's prompt on leaving.
- **Raising `NOTEBOOK_SCHEMA`** is how the next format change gets the same protection: teach `holdsNewerThan` what the older schema would drop.

## Alternatives
- **Hex values in the page:** a theme or palette change would rewrite notes, and Dusk and Dark need their own values for the same intent. Rejected.
- **Colors outside the page's XML** (a side map in the Y.Doc): blocks have no stable ids to key it by, and undo and versions wouldn't follow the text. Rejected.
- **A label inside the page's text:** the page list would need every page's text, and a label is how pages are organized, like a tab's color. Rejected.
- **Labels in the Markdown copy as front matter:** every `readable/` file would change shape for something Markdown readers don't use. Rejected; the notebook file carries them.
- **Color only the selection's whole list** (not a list item): an item is what a member points at. The lists take `color` too, for imports.

## Tests
The guard: `services/notebook/tests/colors.test.ts` proves the premise (an editor with the old schema, typing anywhere, drops a block color from its own copy), then that on a guild's shared page such an edit is refused whole, the color stays at the desk and for the other member, the old tab gets `page_full` (or `reload` when it said a schema), more from it is dropped, and the same tab still edits a page without colors; and that today's editor may take a color off. `web/notebook`'s `colors.test.ts` has the token and `holdsNewerThan`, and the Desk app's `deskBackend.test.ts` and `panel.test.ts` the read-only page and its line.
