# Draft: a self-hosted desk is the cloud desk's software on amd64 Debian 13, with a stand-in for the metadata service

Date: 2026-11-06 · Status: Proposed · Subcontractor task 31, updated by task 35 (the bundle refresh) · The integrator numbers it at merge

Guide and details: `selfhost/README.md`. Platform side: `ma-platform` ADR draft `draft-self-hosted-desks.md` and contract `selfhost.md`. Study: `ma-platform` `docs/research/self-hosted-desks.md`.

## Context
The owner wants members to run desks on their own hardware, and to move a cloud desk onto one (tasks 31 and 32). Cloud desks are arm64 AMIs whose deskd reads its identity and credentials from the cloud's metadata service, and most home machines are x86-64. The rules for this weekend keep `image/`, `deskd` releases and `desk-rtc` with their owners, so the self-hosted desk has to run them as they are.

## Decision
1. **The same software, built for amd64, with nothing patched.** The cloud desks' `desk-rtc` (0.3.5, the first with the port setting) and `desk-stream` (0.2.4), and `deskd` `2026.11.06-4919e5d`, from the commits their arm64 releases came from (`selfhost/build-bundle.sh`, on an amd64 Docker host). `desk-stream`'s artifact is byte for byte the published one, and `desk-rtc`'s carries its release's own `run` and `health`. The first bundle (task 31) had to carry `desk-rtc` `0.3.0-sh1`, 0.3.0's binary with `run` and `health` patched to take the port from a file; since task 35 the port is a `desk-rtc` setting (point 6), and the script refuses a `-sh` version.
2. **Debian 13 amd64 in its own VM,** with a second disk for `/data`. Debian, not Ubuntu, because its Chromium is the same package line as the cloud desks', which ADR 0035 needs when a profile moves between them (task 32): Ubuntu's Chromium is a snap.
3. **`selfhost/install.sh` follows `image/recipe/build.sh`** and installs the recipe's own files, with the differences listed in the README: no SSM agent, no `desk-egress` or `desk-preread`, public NTP, systemd-resolved as the resolver, and three firewall changes (the next point, and SSH only on request).
4. **The desk's Browser can't reach the home network** (private, link-local and CGNAT ranges), so a page open on the desk can't probe the member's router or other devices. `--allow-home-network` lifts it. The agent needs no rule of its own: the cloud desk's allowlist already holds it to loopback, DNS at the resolvers (at home, often the router) and HTTPS at the providers' global addresses.
5. **`ma-selfhost` stands in for the metadata service** on `169.254.169.254:80`, on `lo`. It holds the desk's Ed25519 key on `/data/selfhost`, pairs, and serves deskd its tags, its desk ID as the instance ID, the desk's address as `public-ipv4`, and 15-minute credentials from the platform. The existing rule that only root and deskd reach that address covers it. It's Python with Debian's `python3-cryptography`, like the image's other root-side helpers (`desk-units`, `desk-egress`), not a Java service: it's plumbing that stands where the cloud's own service stands, not a desk service.
6. **The desk's one ICE candidate is its home-network address, on port 4443,** by default. A member who forwards that port, or uses a VPN, gives that address instead. `desk-rtc` offers one address, so this is one path at a time. **Not 443:** Chrome (156) drops a remote host candidate with a private address on a port below 1024, so ICE never starts. Measured: the same address on 5000 and a public one on 443 both connected, and switching Local Network Access off or granting it changed nothing (the first guess, now dropped). **The port is `desk-rtc`'s own setting** (task 35): `port=` in `/etc/ma/desk-rtc.conf`, which `run` passes as `--config` and `health` reads back through `desk-rtc --print-port`. A cloud desk has no such file and keeps 443, unchanged. `install.sh --port` and `sudo ma-selfhost port <n>` set it, and the firewall's port, through one helper (`ma-selfhost-port`).
7. **The desk's key signs its DTLS identity.** The platform takes a self-hosted hello only with fingerprints the key signed in a `session` call (`ma-platform` contract `selfhost.md` §3), because fingerprints aren't secret and a copied 15-minute session could otherwise add one. `ma-selfhost` can't read desk-rtc's identity file (its private key is in it), so a root helper, `ma-selfhost-dtls`, copies the certificate's fingerprint for it at each start of either service.

## Consequences
- deskd, `desk-rtc` and `desk-stream` stay exactly as released. A new release for cloud desks becomes a self-hosted bundle by building the same commit for amd64.
- **Done since (task 35):** `desk-rtc` takes its port as a setting, so the bundle needs no patch and runs the cloud desks' streaming releases. Updating a desk is `install.sh` again with the newer bundle: it keeps the desk's settings (recorded in `/etc/ma/selfhost.conf` from task 35 on, read from its files before that), moves an older desk's `/etc/ma/desk-rtc-port` to the config once the new `desk-rtc` is in, and every part goes in through `ma-update`, which puts the old one back if its health check fails.
- **Wanted from their owners (not done here):** `desk-rtc` offering several candidates (home, VPN and forwarded addresses at once, the study's "the browser tries them all"); `desk-rtc` reporting its fingerprints somewhere a non-root reader can see them, so `ma-selfhost-dtls` can go; `build.sh` reading the architecture instead of refusing amd64, so `install.sh` could call it instead of following it; `desk-firstboot` accepting `/dev/vd*` virtio disks.
- Not built: signed self-updates (today: copy the newer installer and bundle, and run `install.sh` again), a relay for use away from home without a VPN or forwarded port, an arm64 self-hosted build (Apple Silicon, Arm boards), and a Docker bundle for NAS boxes.
- Members run it on hardware we can't see, so support is by what they can read: `ma-selfhost status` and the journal.
