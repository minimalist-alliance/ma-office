# Desk app (`web/`)

The Minimalist Alliance Desk: React 19, TypeScript, Vite, Konva. It's the page a member sees at `office.minimalistalliance.com` (renamed from `desk.`, which now redirects there). Design: `docs/desk-design.md` §2.2 (quality bar) and §3 (canvas). Owner: UI/UX Engineer.

## Commands
Node 24 is needed and isn't the system Node. Run this once per shell:

```bash
export PATH=$HOME/.local/node-v24/bin:$PATH
```

### Comparing bundles
This machine is shared, so one perf run against another mostly measures who else was busy: the same bundle has read 0% and 16% dropped frames minutes apart. To compare commits, build each and alternate, from `web/`:

```bash
mkdir -p dist/perf-src/<sha>
git archive <sha> . | tar -x -C dist/perf-src/<sha>
(cd dist/perf-src/<sha> && node ../../../node_modules/vite/bin/vite.js build --mode e2e --base /v/e2e/ --outDir ../../e2e-<sha> --emptyOutDir)
node tests/perf/perf.mjs --fixtures three,perf --trials 3 --only deskDrag --dist dist/e2e-<sha>
```

Under `web/dist/`, the build finds this worktree's `node_modules` by walking up. Don't symlink `node_modules`: Vite then loads two copies of React and the app doesn't start. Stay inside your own worktree, and use your own named folder in a shared scratchpad, because `ln -s` writes through a link someone else left there.

## How it reaches a browser
1. Platform's loader owns the HTML page, including `#ma-root` and a blocking `/_loader/theme.js`. It fetches `GET /v1/client-config?app=desk-web`, then `ma-release.json`, and injects our `entry` and `css`.
2. `src/main.tsx` starts. `theme/boot` is its first import, and it sets `data-theme`.
3. `platform/session.ts` runs: sign-in if needed, then `GET /v1/desks` drives the desk list. **`/account` comes before any of that:** it's a page on the Platform app, which asks for its own sign-in, so this path (with or without a trailing slash) goes to `links.account` with `location.replace`, signed in or not. Only an `https` URL on a sibling host counts (`siblingUrl` in `hosts.ts`), never this app's own hosts, so it can't come back here; a missing or odd link carries on as any other path. The account menu's "Account settings" frames that page in a full-screen modal over the office instead (rule "Account settings" below), because leaving this tab would close the member's windows. **Sign-in is one of two things, by `auth.signInPath` in client-config, and a signed-out member goes straight to it with no calm screen first, either way.** Set: our own pages (`ma-platform` `web/signin/`), same origin, with `?return=<path>`, by `location.replace`, as managed login goes, so Back from them goes where the member came from rather than round again (`sessionEnd.shell.spec.ts`). A sign-in that fails at `/auth/callback` (a bad `state`, a bare `/auth/callback`, a failed code exchange, a cancelled Google) goes back to the form with `?error=google`, since only Google returns there and the pages have the words for it; nothing keeps a `return` through Google, because the Desk app stores none. **A dead session goes there too,** with its path as `return` and `notice=session`, which the pages turn into "Please sign in again." (`sessionOver`). "Dead" means exactly this tab's refresh was answered `invalid_grant`, or `ma_session_ended` (a refresh past the member's "Stay signed in", `ma-platform` contract `auth.md` §3.3), and cleared the token it sent (`sessionWasRefused`, which lasts until a refresh works, because a link may hear first and the list only after). The calm screen and its one button stay for everything else: a deliberate sign-out, which ends at `/signed-out` and never takes this path (`leaving`); no token left, the likely cause being a sign-out in another tab; the API giving a second 401 to a good token, which signing in wouldn't mend. **The loop guard:** `mayLeaveForSignIn` records the redirect's time in `sessionStorage`, and a session that dies again within 30 s gets the card, as it does if the storage can't be used. It's this tab's alone, it works with sign-in on any site, and it stops only automatic rounds: a member who takes longer than 30 s to sign in gets sent back again, and the card's button is never held back. The redirect replaces the history entry, so Back can't land on a page that sends them there again. **A session that ends forgets the member** (`forgetMember`, in `sessionOver` before it leaves and in `goSignedOut`): the desk mirror `ma.desks.v1` and the kept pictures (`clearLastScreens`) go, as at sign-out, so whoever signs in next never paints the last member's desk names. **Whose tokens these are:** `auth.ts` reads `sub` from each access token (`onMemberChange`, `currentMember`). The first one, and any that's someone else's (another tab's sign-in replaced the stored token, say), deletes an unfinished export that isn't theirs (`keepExportFor`), and a change re-reads `me`, dropping an answer for the member before, so the account menu never shows the last member's name over the next one's desks. **Unsent text:** a dead session can arrive while a Browser window holds some. What was typed into a page has already gone to the desk and stays there. Held text, an address draft and a composition in progress live only in this tab, and they go, exactly as they do when the calm screen unmounts the shell; nothing keeps them across a sign-in. The pages leave the refresh token where `tokenStore.ts` reads it (`ma-desk-web-refresh`, in sessionStorage for "Until you close the browser" and localStorage otherwise; rule "Stay signed in" below), so arriving back is a normal load and refresh; keep that key and rule in step with `web/signin/src/handoff.ts`. Google stays a redirect. Already being on `signInPath` means the route isn't there and the SPA fallback answered, so `ownSignInPath` says use managed login, or it would redirect to itself with an ever longer return path. The Desk app writes no `ma-signin-hint`: it has no step-up yet, so there's nothing of that to clear. **Absent, as in prod: Cognito PKCE at managed login, which is also the rollback (`usesManagedLogin`).** A signed-out member and a dead session go straight there through `startSignIn`, under the same guard, with the same exceptions for the card: a deliberate sign-out, no token left, and a second 401 to a good token. That goes for a setting that can't be used, since it reads as no setting, but not for one that's on with its route missing, where the card and its button stay. Three things differ from our own pages. A signed-out member has the guard here too, since managed login can come straight back with no code: to `/auth/callback`, which is a failed callback, or to the app, where the guard says the card. A failed `/auth/callback` stays on the card, in its own words, because there's no form to show an error on, and a reload from there is a signed-out member like any other. And nothing carries a path or a line through Cognito, so a member always comes back to `/`, and a dead session's "Please sign in again." isn't said. Cognito's own form offers Google where it's on for that client; the card's Google button stays for when the card shows. A reload of any card is a signed-out member too, so it goes straight there, unless the guard's 30 s are still running. **Every sign-in address is made by `signInAddress` in `platform/signInAddress.ts`,** from the setting plus `return`, `error` and `notice`. The setting is a path today and may become an absolute `https` URL on a sibling host (the pages moving to `id.`): then `return` is an absolute URL on this site, and this app can never be on the pages, so `onSignInPage` is false whatever the paths say. Anything else reads as no setting. `release.spec.ts` tests both modes, against stand-ins for the pages and for managed login in `harness/serve.mjs` (`authorizeHolds`, `authorizeBounces`), and `HARNESS_SIGN_IN_PATH=/_signin/` runs the `shell` and `release` projects with the setting on; `tests/real-desk/rt-managed.mjs` runs prod's mode against real Cognito on staging, with no account; `web/signin/tests/apps.spec.ts` runs this bundle with the real ones.
4. `desk/liveStore.ts` keeps one link per desk. Each calls `POST /v1/desks/{id}/connect` with `start: false`, then the gateway and WebRTC. A stopped desk answers `200` with `state: stopped`, and its link rests until `GET /v1/desks` says the desk runs (a `304` counts as saying the same again). So does one still being set up, and a desk the list shows as setting up or held never calls `connect` at all ("Desks that can't open" below). A session that closes with `4503`, `4002`, `desk_stopping` or `closed_by_desk` retries with `connect {start: false}`, first at about 2 s, because a `deskd` restart can say any of them. It shows "reconnecting…" and then "can't reach desk", and rests only when `connect` or the gateway says the desk is stopping or stopped. While `connect` says not ready the retry grows from 3 s to 10 s, unless `connect` sets a pace or a wake is under way, and a `phase: ready` push ends any wait. A wake the member asked for in this tab asks `connect` once a second for its first 90 s (`desk/rtc/policy.ts` `wakePollMs`, TD-227 part 3), unless it's queued for capacity or `connect` asks for more than the usual 3 s, within 24 `connect` calls a minute per tab (`CallWindow`; the API allows 30). A wake another tab started stays at 3 s.
5. **Rendering never wakes a desk.** `desk.attention.set` (rule "One live picture") goes only over a session that's already open, so it can't either. `start: true` goes out only when the member focuses that desk or opens one of its apps (`shell/actions.ts`, through `wakeDesk` and `DeskLink.wake()`), and only after `connect` has just said it's stopped: at most once per request, and a failed wake is not retried. The first refit of a page load counts as focus, so one desk, or a reload in desk mode, wakes on arrival. "One desk" is what Platform's list says, counting every desk on it: until the list answers, a refit runs on what this browser remembers, where a new desk may be missing or have no layout, so it only paints and the arrival waits (`refit`). A reload in desk mode doesn't wait, since the member was on that desk. Later refits (a resize, a list change) wake nothing, and `goOverview` never does, so a member with one desk can zoom out and stay out until they focus it or reload. The export page's "Download your data" is a member's request too, and wakes each chosen desk that's asleep (rule "The export page"). **The one exception: a desk whose `GET /v1/desks` row has `startsWithOffice: true`** (the Alliance Member's hosted small desk, `ma-platform` ADR 0097, the owner's decision) is woken as the office opens, once a page load, and only while the page can be seen, so a background tab waits until it's looked at (`wakeWithOffice` in `liveStore.ts`). Platform stops it 20 minutes after the member goes idle. `alliance.shell.spec.ts` counts the wakes against the harness. **A phone (`isPhone()`) with more than one desk arrives in desk mode too,** on the remembered `activeDesk` if still in scope, else the first in reading order (`refit`, `shell/arrival.test.ts`, `phone.landing.shell.spec.ts`); before the list answers it only paints that desk. Larger screens arrive on the overview.

**`/export` (the export page) is the one other page,** and only where client-config says `export.enabled === true`: `App.tsx` waits for client-config on that path (nothing paints for those few ms), then renders the lazily loaded `export/ExportPage.tsx` instead of the shell, after sign-in as ever. Anywhere else, with the flag off or absent, or client-config unreadable, `/export` is the office as before. The session still runs underneath it (the list's poll, `syncLinks`), so the page uses the office's own links. Rule "The export page" below.

**A new version while a tab is open (`platform/newVersion.ts`).** Every 15 minutes (`VERSION_CHECK_MS`), and never while the tab is hidden, the signed-in shell fetches client-config afresh and compares its `version`, the release pointer the loader reads to pick a bundle, with `__MA_VERSION__`, which this bundle was built as and its `ma-release.json` carries. So it asks exactly what a reload would load, cohorts and rollbacks included, with no file or route of its own. The first ask is a turn after load; a tab coming back after a turn or more asks at once; a failure or a missing `version` says nothing and waits a turn; a hung ask gives up at 15 s. A different version shows "A new version is ready, reload when you like" with a Reload button and a Dismiss (×), and asking stops (`chrome/NewVersion.tsx`). **It never reloads by itself:** a reload closes the member's windows and drops what lives only in this tab. Dismiss puts it away for this page. Under 600 px it's "A new version is ready" and the buttons. It's said once, politely, through the shell's live region; the notice itself isn't live, so it isn't said twice. **It's one of the shell's notices, never in the top bar:** see the notices rule below. `npm run dev` asks nothing; `?versionEveryMs=` shortens the turn outside production builds, for `version.shell.spec.ts`, and the harness's `releaseVersion` plays a new release.

All URLs after client-config come from client-config, which follows the calling origin. `platform/hosts.ts` only derives where to fetch client-config.

**Theme flash.** The loader's `theme.js` paints from `localStorage['ma.theme.resolved']`, so `themeStore` always writes that key, and removes the loader's inline `background-color` and `color-scheme` once `themes.css` has applied.

Don't add a per-frame DOM write, a React state update during motion, or a blur that isn't in a cached bitmap. Run `npm run perf` after touching `src/canvas/`. `liveStore.ts` holds every update from a link until the camera settles. `useLive` is what panels render from, so anything that changes often (uptime, RTT) goes in `useAbout` instead.

At rest they're on whole device pixels with smoothing off, so the bevel stays crisp, at most half a device pixel from exact; a landing moves one at most a device pixel, half of that the camera's own.   - **What arrives** moves nothing if it's the same. Reads: at load, every 60 s while the tab shows, on coming back to it (at most once per 5 s), and at once from another tab through `storage`. **Platform has no `304`:** it ignores `If-None-Match` and sends the whole document to every read, so the same `ETag` is a no-op, with no merge, no write, no render and no camera move. The camera re-fits only if a desk's bounds changed, never for a stack or an app.
  - **What holds an arrival:** a drag of a desk, its corner or an app (`Konva.isDragging`, which is all of them), a keyboard edit (`kbEdit`), a camera move, and cleanup's 240 ms (`anyTidying`), which also holds a save. As well as those, an open menu, the hidden list and its ring, which were placed from where things are now: a save needn't wait for those. It's checked again every 400 ms and lands by itself. One waiting from Platform isn't replaced by another tab's copy, since the same `ETag` won't be read twice. A page going away during one sends what it said as well.
  - **Desks never overlap, whoever saved them** (ADR 0064). `arrivingLayout` in `layoutDoc.ts` clears the document first, on its own and in its own `z`, so every browser with nothing to send lands on the same places whatever its own order. Merging can then make an overlap of its own, a desk moved here and another moved there, and that's cleared with this browser's unsaved desks staying put, then what the document says, and only a desk this browser alone has going round them. **It settles:** clearing is quiet, so it marks nothing as changed, and only a member's own change ever causes a save. The browser with something unsaved sends all of it, cleared, and the other takes that. A saved overlap stays on Platform until this member's next real change. The same goes for a keepalive save carrying a document held back.
  - **What goes** waits 2 s after the last change, 10 s at most, and never runs during a drag. Leaving the page sends it with `fetch` `keepalive`, since a beacon can't `PUT`. What Platform hasn't confirmed is listed in `ma.layout.sync.v1`, so a closed tab or a crash retries on the next load. Nothing goes before the desk list has answered, and the list prunes what isn't this member's. **A desk that comes back to what Platform last said isn't a change** (`base`), as after Esc or an undo: it's taken off the list, so it saves nothing and doesn't overrule what arrived while that was in progress.
  - **`ETag` and `If-Match`** are the exact string Platform last sent, quotes included, and never rebuilt from the number while it sends one. The API's CORS exposes `etag` and `retry-after` and allows `if-match` and `if-none-match` (`terraform/api.tf` in `ma-platform`).
  - **`Retry-After`** holds every save, including one that a new change asks for, and a page going away during it leaves the save to the next load. Other failures back off from 2 s to 60 s, and a page going away still tries. API Gateway's own `429` has no `Retry-After`, only `message`, and takes that backoff.
  - **A `412`** takes Platform's copy with this browser's changed desks on top, up to three tries, then backs off. So on one desk the last to save wins. A `428` is taken the same way, though this app always sends `If-Match`.
  - **Stacking is two things.** A desk's `stack`, how its apps are stacked, is part of the desk: raising an app changes the desk, which saves like any other change, arrives like any other, and a different stack is a different desk (`sameDesk`). That's what `CHANGELOG` promises. `z`, the order of the desks, changes on every focus and shows nothing now that desks never overlap, so it never causes a save, rides along with the next one, and each browser keeps its own.
  - **The first save:** an empty document gets what's here, and a browser nobody arranged anything in has nothing to send (`isUntouched`), whatever it pressed, for as long as Platform has nothing usable. A document on Platform beats a local copy with nothing unsaved. **Untouched is narrow:** the apps at their default places in the list's order, one row in the list's order (the list is in order of creation), as a first visit left it in any build that has shipped: 584 x 236 at the top, 584 x 144 at the top (before `eca1294`), or 584 x 144 at `y` 36 (before `b0de92f`). The stack doesn't count, since nothing overlaps there and pressing an app raises it. The one thing it can't tell apart: a new desk shrunk to its smallest from the keyboard, with nothing else touched on any desk, is exactly an old default, and it stays here until the next real change. So a browser's old default can't replace the arranged one, whichever opens first.
  - **Whose it is.** A save goes out only on a token for the member whose document this is: `api`'s `onToken` sees each token as it's about to go, and `checkToken` compares its `sub`. The first read says whose; `ma.layout.sync.v1` records it, and its list of unsaved desks only comes back for the same member. A token that's become someone else's, from a sign-in in another tab, drops everything held here and starts again, and an answer to the last member's call is dropped (`epoch`). A desk the document places that the list hasn't heard of yet goes where the document says when it does (`expectDesks`), since that document won't be read twice.
  - **A dead session** changes nothing here: a layout call follows the rule for any call (`api` refreshes once, and then `SignInRequired`), and only the desk list's poll acts on it. So a `401` on a read or a save signs nobody out, redirects nobody and logs nothing of ours. What's unsaved stays in `ma.layout.sync.v1` through the trip to sign in, and goes when the same member is back. Sign-out sends what's waiting first, for up to 1 s.
  - **A document it can't use:** a newer `schemaVersion` stops saving and keeps what's here. A bad one, or an older `schemaVersion`, is replaced by what's here. A `404` stays local and asks again every 15 min.
  - **Size:** a save is at most 60 KiB (`MAX_SERVER_BYTES`), most recently raised desks first. Any others stay in this browser only. A `413` all the same sends three quarters as much at once, down to 8 KiB (`FLOOR_BYTES`). A `400`, `403`, or a `413` at that floor, isn't asked again until the next change or load, since asking again wouldn't change the answer.
  - **Failing is silent:** no notice and no console line of ours. A browser logs its own line for a failed request, which no app code can stop, so a test that watches the console during a failure filters only that line.
  - **The format** is `SCHEMA_VERSION` in `layoutDoc.ts`, the shape of `ma.layout.v2` without each desk's `id`, with a desk's `stack` if it has one, and a desk that never stacked is byte-identical to what it always was. A save read back and saved again is the same bytes. Fields it doesn't know go back as they came. Changing the format means raising it, and older builds then stop saving.
  - **Theme isn't in the document** (design §3.8 says it is). It's chosen per browser in `ma.prefs.theme`, and the loader reads what it resolved to before the app starts. Sharing it would repaint a page after load, and would set a phone's theme from a laptop's.
- **A desk goes where it's dropped**, with no grid, in hundredths of a unit like everything else in the layout doc.
- **Desks never overlap** (ADR 0064). A moved or grown desk stays under the pointer and pushes its neighbours aside, keeping `DESK_GAP` (24) between them. The rules are pure, in `canvas/deskPush.ts`, with randomised tests: every position is worked out from where everything was when the drag began, on each pointer move, so a retreat brings neighbours back and nothing drifts. A neighbour's direction is the face it was met by, held for the rest of the drag. Its displacement is how far the pusher's edge has come, less how far the pusher has gone off its other axis, which is what stops a neighbour hopping home the moment they stop being level. So no pushed desk moves more in a step than the pointer's |dx| + |dy|, and a desk being moved by two others at once follows at that pace unless it's actually in the way (`keepToPointer`). It lets go only when the neighbour is back at rest and the pusher is behind where they met, has gone wholly past, or is going on along its way rather than back, so a desk can go round. Two desks closer than the gap to begin with keep the gap they had, rather than one jumping. While a desk is in hand, `canvas/deskPushLive.ts` writes neighbours to Konva through `camera.placeDesk`, with no store write and no render, inside the drag's own batched draw, and the drop is one store write. Everything the member does to a desk's bounds goes through `patchDesk` or `placeDesks` in the store, which push and then check, and a document from Platform or another tab comes through `arrivingLayout`, so nothing can write an overlap. A saved doc that overlaps is cleared in `load()` before anything paints (`clearLayoutDoc`, by the smallest moves it can find), and written back only if something moved: a clean doc comes through byte for byte, however close its desks. New desks go 72 along and past anything in the way (`clearSpot`). Hidden desks are pushed too, or clearing the filter would show an overlap. A removed desk leaves its gap. The panels a phone draws aren't the stored sizes, so two small desks can still look overlapped there, as they could before; the push and the check use the stored sizes.
- **A desk's corner never snaps, and never rasters per frame.** The handle stands on the corner, so a drag's position is the corner at any zoom. Dragging it writes to Konva only, and the panel draws in nine stretched pieces of one bitmap (`blitPanelLive`) until the drop, when it gets its exact-size bitmap. A drop doesn't move the camera, so the corner stays under the pointer; Fit and `0` refit on request, and so does a window resize. At the viewport's right or bottom edge the camera pans gently and the desk keeps growing (`edgePan`). Phones (under 600 px) keep the cell grid: four columns, packed from the list order, with no corner to drag.
- **Apps move and resize freely, and anything can go over anything** (ADR 0062, 0064). A dragged app or a dragged corner follows the pointer exactly, stopped only by the work area (8 units from the desk's sides and top, down to the strip) and the 56 x 56 minimum: `clampMove` and `clampResize`, pure, in `canvas/layout.ts`. A drop never moves another app. Everything stored has two decimals. While dragging, `ItemTile` writes to Konva only: the renders are one as a drag starts, to take the hover away, and one at a detail threshold (168 and 352). Hover and the corner go to the topmost app, because that's how Konva's hit graph reads.
- **A desk's `stack` is its stacking order**: item ids, bottom to top, an optional field on the saved desk, read and changed through `stackOrder`, `withStack` and `restacked` in `canvas/layout.ts`. **Its `items` list is only the phone grid's order.** A raise doesn't change the list, and a phone's reorder doesn't change the stack. No `stack` means the list's order, ids it doesn't list go on top in list order, unknown ids and repeats are dropped, and a bad one loads as whatever's left of that. It's left out whenever it says what the list says, so a desk that never stacked reads and writes byte-identical. It needs no new key, because a build that doesn't know it ignores it, and loses it at its next write. Pressing an app raises it, on the press and before any drag (`press` in `ItemTile`, `restack` in `shell/cleanup.ts`), but not a right press, whose menu can send it down. `DeskPanel` works out the draw order once per render, so the stack changes once, and React moves the node to the end of the tiles, which end the desk's group, over the strip's hit boxes: react-konva's `_remove` doesn't stop a drag, and a render can't put it back. A move or a drag sorts nothing. A press on the app already on top stores nothing and renders nothing. **Tiles have no `moveToTop`:** a phone's drag lifts its tile the same way, through React (`lifted`), and it goes back at the drop, so Konva's order never drifts from React's, and a wider window finds every app where the stack says. **There's no marker and no sort on read:** nothing a shipped build saved overlaps, and two apps only come to overlap by one being moved, which raises it, so the order an old desk starts in can never show (a randomised test in `layout.test.ts` proves it).
- **The stacked look** (ADR 0064): a tile that overlaps one below it, or is in hand, draws `elevation.tileStacked`, a stronger shadow and a 1-unit edge just outside the card. `overOthers` in `canvas/layout.ts` is the rule, pure, and goes by `stackOrder`; `DeskPanel` runs it once per change of the layout, so a drop or a raise updates the tiles and a pointer move computes nothing. In hand isn't React state: `ItemTile`'s scene reads the drag's own refs at draw time, so a drag switches its bitmap once with no render, and a corner in hand is always stacked, since what it covers isn't known until the drop. `tileSprite` caches the look as a variant, and a press makes it, so a drag's first frame has no bitmap to make. Phones overlap nothing at rest, and only their tile in hand wears it. The tile's shape keeps what it drew in `attrs.stacked`, for tests.
- **Shadows draw at their token's strength.** `shadowBitmap` fills with the context's opaque default, because a shape's alpha multiplies its shadow's. Filling with the shadow's own color applied the alpha twice.
- **The keyboard goes by place, never by the stack.** `appsInOrder` in `shell/order.ts`: reading order, with ties by id, so two apps at one spot keep their order whichever is on top. `ProxyLayer` renders the buttons in that order, holding them still during a keyboard edit, since moving the focused button in the DOM drops its focus. An app that takes keyboard focus comes to the front (`appFocused`), and a covered one is still reached. Focus that's only coming back, from the menu or a finished edit (`focusBack`), leaves the stack alone. On phones the list is the grid's order: nothing raises, and the keyboard follows the list. **A tile its own open window covers is no Tab stop** (`a11y/covered.ts`, a centre-under-the-window test against the camera; the roving stop moves to the desk's next uncovered place), so a focus ring is never drawn under a window; it returns when the window closes or moves. **The bottom bar and the bandwidth circle rise over the windows while one of their controls has focus** (`:focus-within`, z 21, as the top bar does with its menu). `a11y.office.shell.spec.ts`.
- **No hover during a drag.** Konva sends no pointer events to shapes during a mouse drag, because `Konva.hitOnDragEnabled` is on only after a touch press (`WorldStage`), which a pinch needs. It also spares the hit graph a redraw per frame. `ItemTile` works out hover again at the drop. `shell.spec.ts` counts every React commit during a drag through the devtools hook, and allows none.
- **Cleanup** (ADR 0062, 0064): `tidyDesk` in `canvas/layout.ts` is pure, reads only where apps are and never how they're stacked, so it takes even a pile at one spot apart the same way every time, and running it on its own result changes nothing by construction, with randomised tests. Any overlap counts as something to change; a stack order alone doesn't. It resets the stack to reading order and leaves the list, so a phone's grid doesn't hear of it. `shell/cleanup.ts` holds the one undo, which restores positions, the desk's size and the stack: in memory, and good while the desk is the same object cleanup stored, since any change stores a new one, except that a change of stack alone carries it over (`restack`), or a click on an app would end it. - **The hidden count** (ADR 0064): an app is hidden if what the union of everything above it leaves of it holds no box of 12 x 12 units (`HIDDEN_MIN`), so a sliver doesn't save it and a hidden app still covers what's under it. `hiddenItems` in `canvas/layout.ts` is the rule, pure, with a randomized test against a brute-force grid. It's the row's leftmost, past cleanup's slot while that's held, at rest whenever it's above zero. `etchCountSprite` cuts the icon and number as one bitmap, so it's one blit a frame on a desk that has one and nothing on a desk that doesn't, and a new number is a new bitmap once. The icon is `drawHiddenIcon`, an eye with a slash: a thick outline, a pupil, and a clear gap either side of the slash (a clip, so each pass of the cut draws the same shape), because the cut would eat thin lines. The tooltip is the container's `title`, from the hover, so hovering renders nothing. The shape keeps what it drew in `attrs.drawnCount`, for tests. **The list** is `chrome/HiddenList.tsx`: the menu's style, above the icon, placed from the proxy's box, reading order, six rows of 40 and then it scrolls, with each row's icon on its own small canvas. Choosing raises the app, closes the list and rings the app; from the keyboard, focus goes to it. A raise can hide something else, so the count doesn't always drop. **The ring** is a DOM element on the proxy layer, so its 600 ms animation is opacity and transform on the compositor and draws no canvas frames. `animation: none` under reduced motion is the static ring. A camera move ends it, because that layer follows the camera only at rest. Phones have none of this. `tests/e2e/hidden.shell.spec.ts` covers it.

- **The clipboard, both ways (`browser/clipboard.ts`, deskd API.md section 10).** Text only, the desk's `CLIPBOARD`, and text lives only as long as the call: it's never logged, kept or put in an error, and the bar says one of a few fixed lines. **The member's clipboard is read in one place,** the `paste` event's `clipboardData` on the hidden textarea, which a real Ctrl+V, Cmd+V, Shift+Insert or a menu's Paste fires and which needs no permission. `readText` has one exception, on Security's condition (Nov 11, #12): the phone key row's Paste, `readForPaste` in `browser/touchPaste.ts`, called synchronously in that button's own `onClick`, once per tap, never on mount, focus, visibility, a timer or any other event; its text goes straight into `StreamClipboard.paste()` and is dropped (no state, store, log or telemetry), and a refusal, an unsupported browser or any error says "Your browser didn't allow that paste." and does nothing else, with no retry (an empty clipboard says "There's nothing to paste."). ## Open tiles (`src/opentile/`, ADR 0053, the owner, Nov 11)
The owner: "When I expand the apps enough, they are supposed to actually be viewable and usable right there on my desk like when they are opened into models. [...] All apps should be able to be 'opened' by expansion."
- **The first load holds only the level and the way in** (+0.34 KB): `detailLevel(w, h, app)` gains `open` above `large`, at least 6 x 5 cells (`span(6)` x `span(5)`, 536 x 444 units) or an app's own minimum in `OPEN_MIN` (`canvas/layout.ts`; only the Browser's, 7 x 5). `CELLS.open` is 6 x 5 and `SMALLER.open` is `large`, so the phone grid draws an open tile as `large`. `door.ts` `useOpenNeeded()` (called by `Shell` before the desks render) reads the kill switch, client-config `openTiles: { enabled: false }` (absent is on), into `setOpenLevel`, and says whether a tile is at `open` on the shown desk, not in carousel mode, not on a phone: then `Shell` mounts the layer (`loadOpenTiles`, the one import), after the `ProxyLayer`. `ItemTile` writes "Open in its window" in an open tile's foot while its window is open (`.open-tile-note`). `useKeyboard` leaves every key inside `.open-tile` alone. `.open-tile` is in `pinch.ts`'s `OWN_PINCH`. From the overview, `openItem` on a tile at `open` focuses its desk and launches no window. Everything else is the chunk's.
- **Live** (`model.ts` `liveTiles`, in the chunk): only on the shown desk (`shownDesk`), with the camera at rest, at least 480 x 320 CSS px on screen (`OPEN_LIVE_MIN_W`, `_H`), partly on screen, its app's window not open (closing ones count: the window wins), and nothing above it in the desk's stack over it (the canvas can't draw over the DOM; a press brings it to the front, and it's live). Four at most (`MAX_LIVE`), the most visible area first; one per app (of two tiles of one app, the larger). The rest draw the `large` widget.
- **The layer** (`OpenTileLayer.tsx`, `opentile.css` with it; `cssCodeSplit` is off, so its rules are in the one stylesheet) follows the camera as the carousel's stage does (`canvas/useCameraRest.ts`, shared): laid out in screen pixels for the camera at rest, one transform during a move, laid out again at rest, never remounted for a pan or zoom (one that stops being live at rest unmounts, as a closed window, and mounts once when it's back: a hidden Browser on the looked-at desk would keep streaming). ## Shipping a change
The owner's feedback comes through the coordinator and should be live in minutes. Platform's runbook: `docs/runbooks/desk-rollout.md` in `ma-platform`. UI/UX may promote to prod once staging passes; once the owner's desk exists, "passes" includes a run against the real `DeskKind=test` desk.

1. **Build only from a clean tree at `origin/main` plus the change.** If other work is in progress in this worktree, use a temporary `git worktree add --detach <scratch> origin/main` and remove it afterwards. `build:release` marks a dirty tree `-dirty`; never publish one.
2. Run `typecheck`, `lint`, `test`, then the `shell` and `release` projects, and `rtc` if `src/desk/` changed. **Look at the screenshots** in `test-results/shots/`: passing tests have missed a broken image.
3. **Stop on a failed rebase.** Don't chain `git pull --rebase` to `git push` without checking it finished: `CHANGELOG.md` conflicts at the top often, because several sessions add entries there, and a stopped rebase once pushed part of a series.
4. `scripts/desk-web-release.sh publish web/dist/release`, then `promote staging <version>`, check, then `promote prod <version>`. `rollback <env>` undoes one step. Versions are immutable, so a new change needs a new commit.

**Testing on real staging, by scripted Playwright with secrets never logged:** the scripts are in `tests/real-desk/`, see its README.
- `e2e-signup` has no desk and can't wake anything. `desk-1` has two desks, so its overview wakes nothing. `member-1` has one desk, the Desk Engineer's build box, and signing in as it **starts that EC2**, by design: one desk wakes on arrival.
- A real `connect {start: true}` starts a real instance, so check which desks a test account holds first.
- Check mode-specific images and files in the `release` project, not `shell`: the mock build isn't where the shipping asset paths are proven.
