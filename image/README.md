# Desk VM image

Debian 13 arm64 AMI for one desk (one EC2 per desk). Spec: `docs/interfaces/desk-runtime.md`. Decisions: ADR 0007, 0009, 0032.
Until Platform's Image Builder exists, `bake.sh` builds AMIs from a temporary builder EC2 (ADR 0032's narrow exception).

## Commands (run from this directory, default AWS profile, us-east-1)

Everything is tagged `Project=minimalist-alliance`, `Purpose=desk-image-build`, `ManagedBy=claude-cli`, `CostCenter=platform`.
Builders and test instances are terminated on exit, even on failure, and the temporary key pair and security group (this workstation's IP only) are deleted. That rule is the only place `bake.sh` and `verify.sh` put the address: not in a log line, and not in user data. `count-address.sh` also hands it to its temporary reader, in the script it runs there over SSH, and prints only counts.
`bake.sh` bakes in exactly the releases that `recipe/releases.pin` names, from the release bucket, never a local build, except `desk-agent-filter`, which it builds from the recipe to the pin's hash: see "Baked releases" and "desk-agent-filter". `ALLOW_UNPASSED=1` lets a test bake take a version with no `passed-test.json`.
`verify.sh` writes `evidence/verify-<ami>.txt`.

## Layout

- `recipe/build.sh`: runs as root on a fresh Debian 13 arm64 AMI, idempotent; Platform's Image Builder can call it. The last step removes SSH keys and bake.sh's copy of the recipe, disables sshd, cleans cloud-init and logs, then asserts it. See "What the image keeps from its builder".
- `recipe/files/`: files installed under `/` (units, nftables, Xorg and Chromium config, `ma-update`, `smoke-test`, scripts in `/usr/local/lib/ma/`).
- `recipe/keys/amazon-ssm-agent.asc`: SSM agent signing key (fingerprint pinned in `build.sh`, from the AWS docs).
- `recipe/desk-stream/`: the source of the `desk-stream` release: `desk-stream` (Python, builds the pipeline and takes commands), `run`, `health`, `stream.conf`, `stream-capped.conf`, `stream-deep.conf` (ADR 0036), `ON_DEMAND`; from 0.3.0 also `src/deskcap.c` and its builds, `gst-plugins/aarch64/` and `gst-plugins/x86_64/`, each with a `BUILD` naming the source's hash (ADR 0073). `package-desk-stream.sh` packs it. `build.sh` refuses to bake if it differs from the pinned `desk-stream` release.
- `recipe/releases.pin`: the releases baked in, one line each: component, version, sha256 of the published `.tgz`.
- `recipe/desk-agent-filter/`: the `desk-agent-filter` release (ADR 0070): Go source and tests, `run`, `health`. `bake.sh` builds it from here and checks it against `releases.pin`.
- `recipe/desk-egress/`: the `desk-egress` release (ADR 0036): `desk-egress` (Python, as root), `run`, `health`. `build.sh` bakes it from here, and `ma-update` replaces it. Its budgets are the image's `/etc/ma/egress.conf`, not the release's.
- `lab/throttle/`: ADR 0036's lab, outside any bake: `lab.sh` (two boxes, the branch applied by `build.sh`'s own steps, tests, teardown), `net.py` (the traffic) and `tests/`.
- `recipe/yuvconv/`: the benchmark's GStreamer converter (a copy of `spikes/browser-bench/remote/gstplug/yuvconv.c`), built on the builder and left in `/usr/local/lib/ma/gst-plugins/`, so `stream.conf` can name it. The compiler is removed again.

## What boots

`desk-firstboot` finds the only non-root disk and formats it only if blank (no filesystem, no signature, no partitions), then `data.mount` mounts label `ma-data` on `/data`, `desk-datadirs` creates the layout and owners, then `desk-rtc` and `deskd` start if a release is installed (`ConditionPathExists` on `/opt/ma/<component>/current/run`).
`desk-xorg`, `desk-audio`, `desk-browser` and `desk-stream` are installed but not started at boot.
`desk-kind` reads the `DeskKind` tag before `desk-rtc` and `deskd` start. On a Guild Desk (an exact `DeskKind=guild`) the Browser's units are skipped and `desk-guild-net` and `commons-server` run (see "Guild Desk").
`desk-agent-filter` and then `desk-agent` start the same way once a release is installed, and are skipped until then (see "desk-agent").
`desk-notebook` starts beside `deskd` once a release is installed, and is skipped until then. Neither waits for the other (see "desk-notebook").
`desk-data.socket` listens on `/run/desk/data.sock` from boot, and `systemd-tmpfiles-setup` makes `/data/.ma-export-tmp` on the mounted volume (from 0.2.6, see "desk-data").

## What the image keeps from its builder

None of its logs. The builder's journal holds every login with its source address, so the last step of `build.sh` moves journald to `/run` with a drop-in that lasts until the builder stops, zeroes and removes everything under `/var/log/journal`, and asserts that it's empty. It has to do this before `/etc/machine-id` is emptied, because journald needs that file to restart. `journalctl --vacuum-*` can't do this job, since it only sees the current machine ID's directory.

Builders are never logged in to with a pty, so `bake.sh` doesn't use `ssh -t`. On Debian 13 one such login writes its source address to `/var/log/wtmp`, `/var/log/lastlog` and `/var/log/wtmp.db`, which all users can read. `build.sh` won't finish if `/var/log/wtmp.db` exists.

`verify.sh` checks that a booted image has one directory there, this boot's machine ID, and that the journal works. It can't check for the address itself, because it logs in from the workstation and the test box records that. A count needs a box nobody logged in to, so `count-address.sh` boots the image with no key, no user data, no role and no inbound rule, stops it after first boot, and mounts its root read-only on a temporary reader. It counts by path, across the whole filesystem and across the raw partition, free blocks included, and counts the reader's own journal as a control. Run it on every bake before the AMI goes on a desk.

Counted on 2026-11-06 (`evidence/count-*.txt`). A test bake of this recipe: one machine-ID directory, the journal working, 0 on every path and on the raw partition, and `verify.sh` 22 of 22 (`evidence/verify-<ami>.txt`; the test AMI is deleted). `0.2.2`: 9, all in a second machine-ID directory, the builder's, and 0 everywhere else. `0.2.4`, the first release with this wipe: 0 everywhere, one machine-ID directory, the journal working (`evidence/count-<ami>.txt`). Every image up to `0.2.3` was baked with the old wipe, so it's assumed to carry the same directory, and so is every desk made from one. A new image doesn't clean that up.
## First open (TD-193, from 0.2.4)

A root restored from the AMI's snapshot loads each block from S3 the first time it's read (EBS's "volume initialization"), so a desk's first Browser open on a new root, after a new desk or a root swap, waited on EBS: up to 79 s to Chromium's port and 88 s to the page when the snapshot had never been read. On a fully read root the same first open takes 3 s. The proof and every number are in `spikes/first-open/README.md`. Four changes, measured together on test bakes of this recipe:

- **`desk-preread`** reads, once per root, every image file a real start of the Browser stack opened at bake: `/usr/local/share/ma/preread.list`, made by `recipe/first-open/trace` (about 480 files, 512 MB). 16 readers in parallel, which is what EBS rewards. It starts after `data.mount` and `docker.service`, nothing waits for it, it runs as a dynamic user with `/data` inaccessible and reads only regular files on the root filesystem, never `/data` (ADR 0035). It leaves a stamp at `/var/lib/desk-preread/done` on the root, so it runs once per root: a reboot doesn't start it (`ConditionResult=no`), and a root swap brings a root with no stamp. It gives up after 900 s and tries again on the next boot.
- **A baked GStreamer registry**, `/usr/local/lib/ma/gst-registry.bin`, made with `desk-stream`'s plugin path and `HOME`. `desk-stream.service` copies it to `/run/desk-stream/` on the first start of a boot, so no start scans every plugin (about 100 MB of reads). GStreamer still rescans any plugin whose size or time changed.
- **No GL in Xorg** (`Disable "glx"` in `xorg-dummy.conf`): Chromium runs with `--disable-gpu`, and software GL made every Xorg start read LLVM, z3 and Mesa, 61 of its 68 MB.
- **`desk-xorg-ready`** polls for X every 0.1 s, not every 1 s, since Chromium waits on it.

What it gives, on t4g.medium, from test bakes of this recipe on never-read snapshots. A first open: Chromium's port in 1.5 s and the page's first frame in 2.1 s (p50 of 8), or 5.6 s to the page when the open starts at the same moment as `desk-preread` (3 boxes), against 18.7 s with `desk-preread` off (6 boxes). `desk-preread` took 2.7 to 6.2 s for 512 MB. A warm open (after a reboot): 2.8 s and 3.6 s, the same with or without it, against 0.2.3's 3.3 s and 4.0 s, and `desk-preread` doesn't start. On a first boot, units that start after Docker finished about 3 s later while it read. `verify.sh` passed on the test bake, including its checks that `desk-preread` runs on a fresh root, reads only image files, isn't waited on, skips a root with its stamp and runs again after a root replacement.

Not covered: the boot itself also reads a never-read snapshot, so `Startup finished` takes 22 to 36 s instead of 8, and `deskd`'s baked container (section A of the handoff) will load its image from cold blocks too, while `desk-preread` reads. The read list leaves out `/opt/ma/deskd/` and `/var/lib/docker/`. Measure `deskd`'s first hello on a never-read root with the launch image.

## Outbound throttle (ADR 0036, from 0.2.4)

`desk-egress.service` runs `/opt/ma/desk-egress/current/run` as root, before `desk-rtc` and `deskd` (`Wants`, never `Requires`, so its failure stops neither). It puts HTB on `ens5` with three classes, rate equal to ceiling: 1:10 for `desk-rtc` (uid 1101 from port 443, UDP and TCP) at 60 Mbit with a 1 MB `burst` and `cburst`, 1:15 for root and `deskd` at 2 Mbit, and 1:20, the default, for everything else at 100 Mbit. The leaves are `pfifo` on 1:10 and `fq_codel` on the others. No `tc filter`: the `classify` chain in `nftables.conf` (output hook, priority -150) sets `meta priority`, and HTB reads the class from it. The chain only labels: nothing in it can drop a packet. Every 60 s `desk-egress` reads `tc -j -s class show`, applies the budgets in `/etc/ma/egress.conf` (ADR 0036 section 5: the 30 GB bucket on 1:15 and 1:20 refilled at 1 Mbit, the stream's capped and deep steps, the 1:10 clamp), saves its state in `/data/desk-egress/state.json` (root, 0700) and puts the shaper back if it's gone. It never sees `/data/browser` (`InaccessiblePaths`).

- **A profile change** writes `/run/desk-egress/profile` and `try-restart`s `desk-stream`, whose `run` picks `stream-capped.conf` or `stream-deep.conf`. Anything missing or unknown is `stream.conf`. A softer picture comes at once; a sharper one waits an hour. The viewer sees one pause, 155 to 175 ms on a lab box.
- **If it fails** the classes and their ceilings stay, so `fast` holds and `day` and `month` fall to the guard. No clamp outlives the process (`ExecStopPost=desk-egress --unclamp`) or 10 failed ticks. Its `health` fails when the unit or the shaper is down, so `/opt/ma/smoke-test` does too, and an `ma-update` of any component rolls back until the shaper is fixed.
- **To test the budgets,** lower the thresholds in `/etc/ma/egress.conf` (`tick_seconds` too) and restart the unit. A release never touches that file.
- **No user but root can change any of it.** `desk`, `rtc` (as its unit runs it), `kiosk`, `agent`, `stream`, `kiosk` in a user namespace and `deskd`'s container are each refused `tc`, `nft`, `SO_PRIORITY` above 6, `SO_MARK` and port 443. `gst-ptp-helper` shipped with `cap_net_admin`, so `build.sh` makes it root-only with a `dpkg-statoverride`, which dpkg keeps through upgrades and which also clears the capability.
- **`verify.sh` section 3d** checks the qdiscs load, the classes are as specified with no filter, each uid lands in its class, no user can change it, a clamp lifts on stop, the shaper comes back within a tick, and the capped and deep confs build and send video, with a small window of kiosk's changing colour on `:99` meanwhile, since from `desk-stream` 0.3.0 a still screen sends only about one repeat a second (main's 3d failed on that until 0.3.3's branch). Its first-boot check counts four components in the smoke test.
- **`desk-stream`'s release has to be republished** for the profile confs. The image takes `desk-stream` from `releases.pin`, and `build.sh` refuses to bake when the pinned release differs from `recipe/desk-stream/`. That's `desk-stream` 0.2.2 (sha256 `7fb30cc5…31e8d`), packed from this recipe, passed on the test desk and pinned on 2026-11-06. `desk-egress` isn't pinned: `build.sh` bakes it from `recipe/desk-egress/`.
- **The lab** (`lab/throttle/lab.sh`) made every result in ADR 0036 section 8: two boxes from `ma-desk-0.2.3`, the branch applied by `build.sh`'s own steps, `verify.sh`'s sections 2 to 3d run against them, about 3 instance-hours a pass. Evidence: `evidence/throttle-2026-11-06/`.

The IMDS rules in `nftables.conf` now refuse only a new TCP connection, like port 9222's below, and everything that isn't TCP. When the client closed first, its last ACK carried no uid and was refused, and IMDS resent its FIN about 10 times a minute for each such connection (`evidence/throttle-2026-11-06/lab2-8*`). Root and `deskd` still get 200, and every other user is still refused.

## desk-agent (the bake after the launch image, task 04)

`desk-agent` (`services/desk-agent/`) runs the desk's agents as uid 1103 (`agent`) in Docker, with `deskd` relaying `agent.*` to it over a Unix socket. From 0.2.7 its pinned release is baked in like `deskd`'s ("Baked releases"), so a new desk starts it at boot and a root swap brings it back. On 0.2.5 and 0.2.6, which have only what's below, it arrives through `ma-update`, and until then `desk-agent.service` is skipped by its `ConditionPathExists`, which a rollout's `run` satisfies. What the image gives it, from `services/desk-agent/docs/proposals.md` section 4:

- **`desk-agent.service`**, the shape of `deskd.service`. It requires Docker and `desk-datadirs`, wants and follows `desk-egress` and `desk-agent-filter` (never requires them), and stops the container with 30 s of grace. It doesn't wait for `deskd`: it holds no key until `deskd` hands one over, and answers `health` without one.
- **`/run/desk-agent`**, `agent:desk`, mode 2750 (`tmpfiles.d/ma.conf`). The setgid bit gives `agent.sock` group `desk`, so `deskd` (1100) can connect while `agent` stays out of group `desk`, which would open `rtc.sock` to it. `agent-admin.sock` is 0600, for `health` as root.
- **`/data/agent`**, `agent:agent`, 0700 (`desk-datadirs`): its `agent.db`, usage ledger and audit log. Never keys.
- **Its way out** is `desk-agent-filter` and nothing else ("desk-agent-filter", below). uid 1103 holds the members' provider keys and reads whatever a provider sends back, so it reaches loopback, and its HTTPS and DNS land on the filter whatever address it aims at. Everything else is refused, IMDS and port 9222 first.
- **`verify.sh` section 3e** checks, from 0.2.7, that the pinned release is installed as a rollout lays it out, that the unit is enabled, passes its condition and runs, that `health` answers, and that `agent.sock` is group `desk` and `agent-admin.sock` 0600 (before 0.2.7 it checked that the unit was skipped with no release). Then the two directories, and that a socket uid 1103 makes in `/run/desk-agent` is group `desk`, so `deskd` connects and `kiosk` can't. Section 3d no longer sends as uid 1103, which can't reach the subnet's gateway. Section 3e1 is uid 1103's way out.
- **The first release** is `desk-agent` `2026.11.06-60828be` (2026-11-06, task 37), on the test desk and the owner's desk, both on 0.2.6. Pinned and baked from 0.2.7 (task 42), so a desk born on 0.2.7 or swapped to it has it with no rollout. On 0.2.6 or older a root swap takes it off again, so roll it on after one.
- **An image without this** can't take a `desk-agent` rollout: `ma-update` finds no unit, the smoke test fails on `desk-agent`'s `health`, and it rolls back. A release left installed there would fail every later component's smoke test.

## desk-agent-filter (from 0.2.9, ADR 0070)

`desk-agent` (uid 1103) reaches only the providers' names, not their addresses: OpenAI and xAI share Cloudflare addresses, so an address list let other sites through. `recipe/desk-agent-filter/` is a small Go program with no dependencies, run as its own uid 1106 (`agent-filter`) with no capabilities, by `desk-agent-filter.service`, before `desk-agent`. It never sees inside TLS and holds no keys. Decision, threat and numbers: ADR 0070.

- **The redirect.** `nftables.conf`'s `agent_redirect` chain sends uid 1103's TCP 443 to `127.0.0.1:14443` and its DNS, UDP and TCP, any destination, to `127.0.0.1:14053` (`[::1]` for IPv6). Only uid 1103 reaches those ports, root included, and only uid 1106 can answer from them. uid 1106 reaches TCP 443 on public addresses and DNS at `127.0.0.53`, and nothing else.
- **TLS.** It reads the ClientHello (5 s, 16 KiB, split across records or segments, strict) and refuses no SNI, a name that isn't exactly in the list, and `encrypted_client_hello`. It resolves the name itself through the stub, keeps only global unicast addresses and ignores the address the client aimed at. It then forwards the hello and splices both ways, with half-close, keepalive, no time limit, and at most 64 connections. A refusal is a closed connection with no bytes back.
- **DNS.** A listed name's A is the placeholder `192.0.2.1`, which never reaches the wire because the redirect takes it first, and AAAA is empty. Every other name, type or class is NXDOMAIN, malformed is FORMERR or dropped. It never forwards, so nothing can tunnel through it.
- **It fails closed.** With the filter down, the redirect lands on nothing and uid 1103 gets connection refused. `Restart=always`, 1 s. `desk-agent` only `Want`s it. Its `health` fails while it's down, so `/opt/ma/smoke-test` does, and an `ma-update` of any component rolls back until it's back.
- **To add a provider's name:** put the exact host on its own line in `/etc/ma/agent-egress.conf` (`recipe/files/etc/ma/agent-egress.conf`, no wildcards) and `systemctl restart desk-agent-filter`, which drops any call in flight. The file also has to match the base URLs in `services/desk-agent/docker/desk-agent.env`. A release doesn't touch it, so a name for every desk is a change to the recipe and a bake.
- **Reading why something was refused:** `journalctl -u desk-agent-filter`. It names refused names, 10 lines a minute at most, then a count, and never contents. It stays on the desk.
- **How it's built.** `package-desk-agent-filter.sh <version>` builds from the recipe with the Go it names, after the tests, and the same source and Go give the same bytes. `releases.pin` holds that hash, and `bake.sh` builds it and refuses any other, so a bake publishes nothing. `build.sh` installs it with `ma-update` like the others, and the AMI gets the tag `DeskAgentFilterVersion`. A source change needs a new version and a new hash in the pin. A fix can also reach a running desk without a bake: `desk-service-release.sh publish desk-agent-filter ...` and a rollout, as for any component.
- **Self-hosted.** The same source and rules: `selfhost/build-bundle.sh` builds it for amd64, and `install.sh` installs it. Nothing depends on the shaper.
- **`verify.sh` section 3e1** is `verify-agent-filter.sh`, which also runs alone on a lab box. With 0.2.8's sections, `verify.sh` makes 42 checks with it, and 43 with section 3f ("A stop ends inactive"): 0.2.9 passed 43 of 43. Its checks are named `F-*`. Each was seen to fail with the thing it guards broken: `evidence/agent-filter-2026-11-07/mutations.txt`. It needs `www.cloudflare.com` to answer on the addresses of `api.openai.com` and `api.x.ai`, because without that control its refusal proves nothing, so if a provider leaves Cloudflare the check fails and needs a new site.
- **What it can't stop:** a client that names a listed host and asks that host's server for another site (domain fronting), and data sent to a provider under a different key. On the host, resolved's Varlink socket also gives uid 1103 real DNS, but `desk-agent`'s container doesn't have that socket. ADR 0070 has the measurements.
- **Memory, bounded (0.1.1).** The kernel charges each connection's socket buffers to the unit, and TCP grows them to megabytes when one side sends faster than the other reads: in 0.1.0, 30 fast downloads at once filled `MemoryMax=32M` and the kernel killed the filter. 0.1.1 sets every connection's buffers, from the provider 256 KiB and to it 64 KiB, from `desk-agent` 16 KiB and to it 256 KiB, 16 KiB each way on DNS over TCP, each doubled by the kernel within `net.core.[rw]mem_max` (4 MiB here, from `90-ma.conf`). It holds 64 connections at most, and `MemoryMax=96M` fits all 64 with every buffer full (74 MiB). Idle, it uses about 4 MiB. Section 3e1's `F-BUF` reads the buffers on a live provider connection. Numbers: ADR 0070.
- **The measuring tools** are `lab/agent-filter/` (`lab.sh`, `measure.sh`, `mutate.sh`), outside any bake. Keep a stand-in on a private address: Platform's cost guard stops a box that sends 30 GB in 15 minutes (`lab/agent-filter/README.md`). 0.1.1's test bake on 0.2.8, `ma-desk-test-filter-3`, passed `verify.sh` 42 of 42 and `count-address.sh` 0 (`RELEASES.md`).

## desk-notebook (from 0.2.8, S-13)

`desk-notebook` (`services/notebook/`, the Desk Engineer's) keeps a desk's notes and syncs them: Node 24 and Hocuspocus in Docker, as uid 1105, and the only thing that touches `/data/notebook`. `deskd` stays the only door and relays to it over a Unix socket. What the image gives it, the same way it gives `desk-agent` its place:

- **User `notebook`**, uid and gid 1105, in no other group. In group `desk` it could reach `rtc.sock`.
- **`desk-notebook.service`**, `desk-agent.service`'s shape: it requires Docker and `desk-datadirs`, has `ConditionPathExists=/opt/ma/desk-notebook/current/run`, and stops with `docker stop -t 30` and `TimeoutStopSec=40`, because SIGTERM stores every page and checkpoints the WAL. It's enabled in the image. It has none of `desk-agent`'s lines about the network (`network-online`, `desk-egress`, `desk-agent-filter`), because its container has none. - **The pin is optional, and it's one line.** With no `desk-notebook` line in `recipe/releases.pin`, nothing is installed, the AMI has no `DeskNotebookVersion` tag, and the unit is skipped by its condition. - **A release needs this image first.** An image without the unit can't take a `desk-notebook` rollout: `ma-update` finds no unit, the smoke test fails on its `health`, and it rolls back. So `passed-test.json` can only come from a test desk already on an image with this, and the pin comes in the bake after that one, or in a test bake with `ALLOW_UNPASSED=1`. For the first release, `2026.11.07-0e1fb6c`, the Desk Engineer installed these pieces by hand on the test desk (on 0.2.7) to roll it out there, and 0.2.8 pins and bakes it, so a new desk or a root swap to 0.2.8 runs it from first boot.
- **`verify.sh` section 3n** checks the user, `/data/notebook`'s owner and mode on a volume this image formatted, `/run/desk-notebook`'s owner and mode, the unit enabled with its requirements and its stop grace, and that `deskd` doesn't name it. Then uids 1100, 1102 and 1103 are refused a world-readable file in `/data/notebook` and its listing, while uid 1105 reads that file. A refusal has to be "Permission denied", so a broken test can't pass as one. Group `desk` enters `/run/desk-notebook` and connects to a socket uid 1105 makes there, which is group `desk`, and the others are refused. With no pin: nothing installed, the condition really evaluated at boot (`ConditionResult=no` alone is also what a unit that never tried to start reports, so the timestamp is checked too), inactive, no restarts, both directories empty. With the teen lock's eight ("Teen Browser lock"), `verify.sh` makes 41 from 0.2.8, which carries both, and 42 with `desk-agent-filter`'s section 3e1.**

## Guild Desk (task 48, from the next bake)

A Guild Desk is this same AMI booted with the EC2 tag `DeskKind=guild` and instance metadata tags on, which Platform's provisioner sets at launch. It's the guild's shared server: `deskd`, `desk-rtc` (its guild mode), `desk-notebook`, `desk-agent` with `desk-agent-filter`, `desk-egress` and `commons-server`, and no Browser. The contracts are `~/ma-coord/guild-eng.md` §3.2 and §3.3; the runtime spec is `docs/interfaces/desk-runtime.md` §3.1.

- **The flag.** `desk-kind.service` runs `/usr/local/lib/ma/desk-kind` once a boot, as root with no capabilities and IMDS as its only address, after `network-online.target` and before `desk-rtc`, `deskd`, `desk-preread`, `desk-guild-net` and `commons-server`. It reads `meta-data/tags/instance/DeskKind` over IMDSv2, asking again with backoff for up to 30 s, and writes `/run/ma/desk-kind` (`guild` or `member`), **the desk's one answer, which `deskd` reads instead of IMDS** (runtime spec §3.1, the Security Analyst's `GDS-5`). **Only an exact `guild` also writes `/run/ma/guild`**, the file every condition below tests. No tag, metadata tags off, IMDS silent for 30 s, `Guild`, `guild `, any other value or any error is a member's desk with its Browser, and the journal says why, for example `desk-kind: member (instance metadata tags are off at launch, so no DeskKind can be read) in 9 ms`. The flag is written last and removed first, so whoever sees it can trust it. Nothing `Requires=` the unit, so it can't fail a boot. A tag changed after launch takes effect at the next boot.
- **The Browser's units are skipped there.** `desk-xorg`, `desk-audio`, `desk-browser`, `desk-stream`, `desk-browser-thaw`, `desk-adblock` and `desk-preread` each have a drop-in, `/etc/systemd/system/<unit>.service.d/desk-kind.conf`, with `ConditionPathExists=!/run/ma/guild`, so their unit files stay as their owners wrote them. `desk-units` answers every verb on them with `err unsupported guild desk has no Browser: <verb> <unit>`, so `deskd` gets a clear no instead of a start systemd would skip in silence. - **The Guild Desk's rules.** `desk-guild-net` (root, `CAP_NET_ADMIN` only) puts nine rules in `inet ma` on a Guild Desk: the seven below and two voice labels ("Voice and the guild's budget", below), and nothing on TCP 443 ("TCP 443 per network: taken out before release", below). In input, appended: inbound UDP 8791 up to 8790 + cores, at most 8 (`nproc`, which is what Go's `runtime.NumCPU()` gives `commons-server`), comment `ma-guild-commons-voice`. In output, first: anything to `127.0.0.1:8799` or `[::1]:8799`, UDP or TCP, is refused to every uid but `rtc` (1101), comment `ma-guild-commons-relay`: that's Commons' loopback relay port, where `desk-rtc` forwards Commons' voice ICE from 443 on a Guild Desk (`sub/guild-rtc-443`; Security's `GDS-3`), and no other uid, `agent` above all, may speak to it. Also first: a new TCP connection to `127.0.0.1:8790` or `[::1]:8790` is refused to every uid but root and `commons`, comment `ma-guild-commons-local`, so no member's agent (uid 1103 may reach loopback) or anything else reaches Commons' local HTTP port if a release ever listens there (the Security Analyst's bar for task 48). They go first because the chain accepts uid 1103's loopback traffic further down. `desk-guild-net.service` adds them at boot, and `nftables.service.d/desk-guild-net.conf` again after every start and reload of `nftables.service`, since `nftables.conf` flushes the ruleset. Each run replaces every copy in one transaction. Nothing is opened for TCP: the room link is a Unix socket, and TCP and UDP 443 are already open on every desk for `desk-rtc`. **`nftables.conf` is unchanged, and a member's desk never runs the helper,** so its ruleset is exactly what it was.
- **Voice and the guild's budget (desk-net-031, the bake after 0.3.0).** On a Guild Desk `desk-egress` adds class 1:30 for voice, and the guild's budget replaces the member's stream steps and `desk-rtc` clamp. Sizes are in `/etc/ma/guild.conf` (root, 0644, the image's), read only with `/run/ma/guild`; `desk-egress.service` is ordered after `desk-kind` for it, which delays nothing on a member's desk, since `desk-rtc` and `deskd` already wait for `desk-kind`.
  - **The tier** is the instance type the hypervisor reports, `/sys/devices/virtual/dmi/id/product_name` (no IMDS): `t4g.small` 25 members, `t4g.medium` 50, `c7g.xlarge` 200 (Platform's `guild_desk#current`), anything else 200, since a voice ceiling that's too low cuts every member's voice while a cost line that's too loose still has Platform's stops behind it.
  - **The class:** 0.8 Mbit a member of the tier, rate equal to ceiling (20, 40, 160 Mbit), `burst` and `cburst` 1 MB, prio 0 beside `desk-rtc`'s 1:10, leaf `fq_codel`. A member hears at most 10 voices at 60.8 kb/s on the wire (`apps/commons/README.md`), 0.61 Mbit, so 0.8 leaves 30%. Its own ceiling means `desk-rtc`'s data and voice never share tokens, and prio 0 puts it ahead of 1:20 when the interface itself is busy. `fq_codel` keeps one listener's queue from holding up another's, and a ceiling that's reached drops rather than delays. The 1 MB bucket covers a round of 10 voices to all 200 members at once, about 300 KB a 20 ms.
  - **`desk-rtc`'s class, 1:10, on a Guild Desk (desk-net-031-rtc, for `ma-desk-0.3.1`):** every member's data channels and the voice relayed over ICE-TCP, not one member's video. 0.75 Mbit a member, never under a member's desk's 60 (60, 60, 150 Mbit at 25, 50, 200), with an `fq_codel` leaf in place of the 1,000-packet `pfifo`, so one member's bulk can't stall another's small messages and a full class drops from the bulk. `guildscale`'s burst profile, a tenth of the sessions moving 1 MiB each way every 5 s, is about 0.5 Mbit a member down: on the member's 60 Mbit FIFO it stalled every member's data for seconds, voice or not (`docs/sub-status/desk-net-031.md`). `desk-egress` also checks a Guild Desk's leaf kinds each tick and replaces a `pfifo` an older release left, deleting it first, since `tc` won't change a qdisc's kind under the same handle. Proven on a `c7g.xlarge` with 600 sessions in the burst profile and 200 members' voice: data round trips 0.68 ms at p50, 117 ms at p99 and 746 ms at worst, against 96 ms, 6.7 s and 63 s on a member's 1:10, and voice lost nothing (`evidence/desk-net-031-rtc/`). A member's 1:10, its leaf and its tick are as they were.

Voice relayed over ICE-TCP stays in 1:10 too: a TCP segment's first byte isn't a packet's. Labels only, as the chain is: with no 1:30 (a `desk-egress` from before this) HTB puts them in the default class, as before.
  - **The budget, and why.** On a member's desk the bucket, the stream steps and the clamp hold one member's use to their allowance and the guard's per-desk stops. A Guild Desk carries up to 200 members, and each one's bytes, data and voice, are metered to that member's own allowance (`guild-eng.md` §3.2, the heartbeat's per-session counts), which Platform holds them to. A desk-wide member's allowance there would cut the whole guild's voice for the guild's total: today Commons' voice lands in 1:20 under the 30 GB bucket, and 200 members with 10 talking send 62 GB an hour (ADR 0080), but 1:20's 100 Mbit drops a fifth of it (measured, below), the bucket empties in under an hour of that, and the 135 GB clamp takes `desk-rtc`'s class to 1 Mbit after about three such hours. What the desk still needs is a cost guard for what no member's meter sees: a broken or compromised server. So: the **30 GB bucket stays on 1:15 and 1:20**, which on a Guild Desk carry the desk's own senders (root's updates, `deskd`'s link, the agent filter's provider calls), none metered to a member, and a guild's agents at their default dollar caps send at most a few GB a day *(model)*; the **stream steps and the 1:10 clamp go** (no stream, and 1:10 is members' metered data); and **one day line for the guild** takes their place, over all the desk's outbound in any 24 h: 4 GB a member of the tier (100, 200, 800 GB; **capped at 120 GB for now**, below), 12.8 of ADR 0080's worst hours (312 MB a member: everyone in one room, 10 voices heard, nobody pausing) for every member in a day. Past it voice drops to 0.2 Mbit a member (3 voices heard, so a normal conversation still carries) and 1:10 to 0.1 Mbit a member, until the 24 h total is under 3.5 GB a member. A server sending at its ceiling all day is held to about 530 GB in any 24 h at 200 members (1,030 GB on the members' 800 GB line) and 130 GB at 25; there's no month line, since members' allowances already bound honest use and a month total would only stop the whole guild for their sum.

## TCP 443 per network: the gate is `desk-rtc`'s, not nftables' (desk-net-031-sec, from 0.3.1; the gate's fairness from 0.3.2)

Every desk limits who can hold silent connections on TCP 443 in **`desk-rtc` 0.4.2's ICE-TCP gate** (`desk-rtc/internal/rtcserver/tcpgate.go`; the table, the per-network places, the reserve and the timing are in `desk-rtc/README.md`, "The ICE-TCP gate" and "From 0.4.2"; the record is `docs/sub-status/desk-rtc-gate041.md`). A new connection waits in it until its first RFC 4571 frame is a STUN binding request for a ufrag one of the desk's sessions has, **and that frame's MESSAGE-INTEGRITY verifies with the session's ICE password** (0.4.2). Places are per IPv4 /24 and IPv6 /64 as well as in all (64 in all and 16 for one network on a desk that isn't a Guild Desk, a Guild Desk's sized to its tier), each held 3 s at most (1.5 s with half the places taken). 0.4.2 adds per-address fairness inside a network, reserved places for networks a live session is expected from, and caps past the gate (6 connections per session, 48 per network, a silent handed-over connection closed after the consent timeout). Before 0.4.1 the gate held 64 for 5 s with no per-network share, so silent connections could shut a member's TCP fallback out (found in review, Medium); 0.4.1 answered that, and 0.4.2 Security's `GATE041-1` and `GATE041-2`. A network the desk has never verified is still shut out by 64 networks holding one place each, until Platform's gateway passes the client's address (`desk-rtc-gate041.md`, "For Security").

nftables has no part in it. A first version put per-network limits (16 at once, then 2 a second) ahead of `tcp dport 443 accept` in `nftables.conf`, and **Security's `NET031-3` found they count a bare SYN**: a few forged SYNs a second claiming a member's /24 shut that whole network out of the fallback with no handshake. That was worse than what it fixed, so the rules were taken out before any release. **`nftables.conf` is byte for byte 0.3.0's** (`92e3ef93`, blob `8e821bc9`), `desk-guild-net` adds nothing on TCP 443 and deletes a rule an earlier build of it left, and `verify.sh` 1k4 compares the loaded ruleset with that file. An image that pins `desk-rtc` before 0.4.1 has the 64-for-5-s gate and nothing else, so 0.3.1 pinned 0.4.1 and 0.3.2 pins 0.4.2.

## A stop ends inactive (from 0.2.9)

`deskd.service` and `desk-agent.service` stop their container with `docker stop`, so the JVM gets SIGTERM and exits 143, and the `docker run` client that is the unit's main process exits with it. Up to 0.2.8 systemd counted that as a failure, so each stop ended the unit `failed` (`status=143`), and `desk-browser-close` printed `deskd=failed`. A start or a boot cleared it, so nothing broke, but a failed unit after a clean stop hid a real failure. From 0.2.9 both units have `SuccessExitStatus=143`, and a clean stop ends `inactive` with result `success`. `Restart=always` still restarts either one after any exit it didn't ask for. `desk-notebook.service` needs none: Node stores every page on SIGTERM and exits 0 (a SIGKILL is still 137, a failure). **`verify.sh` section 3f** stops and starts the three, one at a time, and fails if any ends a stop as anything but `inactive` with result `success`, or doesn't come back healthy. It failed on 0.2.8 (`RELEASES.md`, 0.2.9).

## desk-data (from 0.2.6, task 32's export helper)

`desk-data` is the read-only root helper behind `deskd`'s `data.*` methods: a member's "Download your data" and a move to their own computer read their files through it (`tools/desk-data/README.md`, `desk-runtime.md` §8.7). Before 0.2.6 no image carried it, so a desk had it only from `tools/desk-data/install.sh` over SSM, and a root swap took it off again (the test desk lost it on its swap to 0.2.5).

- **Copies, not a second source.** `recipe/files/usr/local/lib/ma/desk-data`, `recipe/files/etc/systemd/system/desk-data.socket` and `desk-data@.service`, and `recipe/files/etc/tmpfiles.d/desk-data.conf` are copies of `tools/desk-data/`'s four files, installed by `build.sh`'s "install files" step like every other desk tool. `bake.sh` copies `tools/desk-data/`'s file over any of them that differs (from 0.3.0; before, it refused and the copy was a manual step each bake), logs each copy, and the bake's Git SHA then reads `+dirty` until the copies are committed. Change the tool there, run `python3 -I -m unittest discover -s tools/desk-data/tests` (no root), and commit the copies. 0.2.8 carries `tools/desk-data` as of `main` `0e1fb6c` (Notebook's `notebook` part, 46 tests). 0.2.9 carries it with `main` `bda80ac`'s review fixes (`docs/sub-status/data-review-fixes.md`, 56 tests), unchanged since.
- **What `build.sh` does.** `chmod 0755` on the helper, `systemctl enable desk-data.socket` beside `desk-units.socket`, and checks both, and that the root has no `/data/.ma-export-tmp`. The tmpfiles line is its own file, so `build.sh`'s `systemd-tmpfiles --create .../ma.conf` leaves it alone and the directory is made on the volume at boot (`data.mount` is `Before=local-fs.target`).
- **What a desk gets.** `/run/desk/data.sock`, `0600 desk`, reachable inside `deskd`'s container through its `/run/desk` mount; one root `desk-data` per connection (`Accept=yes`, at most 24), refusing any uid but 1100, with `CAP_DAC_READ_SEARCH` only, no network, `/data` read-only and `/data/.ma-export-tmp` (`0700 root`) its one writable place. It never runs unless `deskd` asks, so an idle desk costs nothing.
- **`verify.sh` section 3b3** checks it on a booted image, after 3b2 has a running Chromium with history: the socket enabled and listening, the two modes, `kiosk` refused by the socket's mode and root by `SO_PEERCRED`, `parts` for `desk`, and a `read` of the live `History` that arrives whole (size, trailer and SHA-256 agree), passes SQLite's `integrity_check` and has verify's visit in it, with no scratch file left. It also prints `systemd-analyze security`'s score, for the record. So `verify.sh` makes 32 checks from 0.2.6.

## Teen Browser lock (from 0.2.8, task 40)

A desk browses from our cloud, so it gets around a family's router filter, a school's filter and any filtering DNS at home. So a teen's desk Browser runs under extra Chromium policies (`ma-platform` `docs/decisions/0098-age-rules.md`, section 3.2 (the draft was `draft-age-rules.md`)). Teen sign-ups stay off until `desk_image#current` has this.

**Who does what.** `deskd` can't write `/etc`, so it writes only the band: `/data/desk/age-band`, atomically, exactly `teen\n` or `adult\n`, and it doesn't start the Browser until the band is written. The Desk Engineer builds that. The image does the rest: `desk-browser.service` has `ExecStartPre=+/usr/local/lib/ma/desk-browser-policy`, a Python helper that runs as root before every start of Chromium, a crash restart included. Nothing else starts Chromium on a desk.

- **`/etc/ma/chromium-teen.json`**, `root:root 0644`: the policies, from the draft. It shares no key with `ma.json`, because Chromium doesn't define which of two managed files wins. `build.sh` refuses to bake if it does, and so do the unit tests and `verify.sh`.
- **`/etc/chromium/policies/managed/ma-teen.json`**: the lock, a copy of that file (temp file in the same directory, then rename, `root:root 0644`). It lives on the root. The AMI ships without one: the read-list trace at bake locks the builder, having no band, and takes it off again, and `build.sh` asserts it's gone.

**How it reads the band.** uid 1100 can write that directory, so the band is an attacker's input to a root process. The helper opens `/data/desk` with `O_DIRECTORY|O_NOFOLLOW` and the file relative to it with `O_RDONLY|O_NOFOLLOW|O_NONBLOCK`, so a symlink is refused and a FIFO can't hang it. `fstat` must say a regular file of at most 16 bytes. The bytes are compared exactly.

**It fails closed.** Exactly `adult\n` takes the lock away. Everything else puts it in place: `teen\n`, no file, no `/data/desk`, a symlink, a FIFO, a directory, too many bytes, wrong case, no newline. It logs the outcome and why, to the `desk-browser` journal, never what the file holds.

**If the lock can't be put in place,** the helper exits 1 and Chromium doesn't start. Measured on a lab box: `units.sock` answers `err failed start desk-browser: Job for desk-browser.service failed…` at once (not after 34 s), and `Restart=on-failure` runs the helper again every 3 s, so the Browser comes up by itself once the cause is gone. `RestartPreventExitStatus` doesn't apply to `ExecStartPre`, as 0.2.3 found. It also refuses a policy file that isn't `root`'s alone or isn't a JSON object with something in it, which would be no lock at all. A lock that won't come off an adult's desk is exit 0, logged: that desk browses filtered, which is safe, and better than no Browser.

**If `/data` is unavailable,** the unit `Requires=` and follows `desk-datadirs`, which requires and follows `data.mount`. With the volume really detached from a lab box, `start desk-browser` failed on the dependency (`deskd` sees `err timeout` at 34 s, since the device wait is longer), the helper never ran and Chromium never started. With `/data` empty and the helper run by hand, it locks: no band directory.

**Moving between bands.** A band change takes effect at the next start of `desk-browser`. Nothing restarts a running Browser for it here; a crash restart picks it up. `deskd` decides when to restart. A band change, in either direction, is a Chromium restart and nothing more: `verify.sh` carries a persistent and a session cookie through every change.

**An image without this has no lock.** The lock is on the root and the helper is in the image, so a root swap or a rollback to an image without them brings up a teen's Chromium unfiltered, with nothing on the desk to say so. `/data/desk/age-band` is still there, and nothing reads it. From 0.2.8 the AMI carries the tag `DeskTeenLock=1`. **The Platform must never put a teen's desk on an AMI without it**, and `desk_image#current` must have it before teen sign-ups open.

**A `deskd` that doesn't write the band locks every desk.** A missing band is locked, by design, so an image with this helper and a pinned `deskd` without the band filters every adult's Browser at its next start, the owner's too, until a `deskd` that writes it arrives: filtered DNS, SafeSearch, and all extensions disabled. So bake this only with the Desk Engineer's `deskd` pinned, and roll that `deskd` onto a desk before or with this image. The same goes for `selfhost/build-bundle.sh`'s pin.

**What the policy does to a session (ADR 0035).** Nothing in it deletes anything, and `RestoreOnStartup` stays in `ma.json`. Key by key:

## Ad blocking (ADR 0076, from the bake after 0.2.9)

The desk's Chromium blocks ads and trackers, on by default on every desk, adult or teen, with **the image's own blocker**: the block and allow rules of uBlock Origin Lite's default lists at a pinned release, in an extension with two permissions (`declarativeNetRequest`, `storage`), no host permissions and no script but its own worker, force-installed from a file in the image. The simplified view is built from the same tab, so it's blocked there too. A member turns it off for a site from the office; the Platform has a kill switch. Decision, the first build (uBOL from the Web Store) and why it changed (the Security Analyst's `T47S-2`, `T47S-3`), and the numbers: ADR 0076. The interface for `deskd` and the app: `docs/interfaces/desk-runtime.md` §8.9.

- **`recipe/adblock/`**: `blocker.pin` (uBOL's GitHub release for Chromium: version, URL, sha256), `build-blocker.py`, `worker.js`, `managed_storage.json`. `build.sh` runs `build-blocker.py build /usr/share/ma/adblock` on the builder: it fetches the release, refuses it unless the sha256 is the pin's, keeps the default lists' `block` and `allow` rules (dropping 881 `redirect` and 52 `modifyHeaders` rules at `2026.1103.1743`, one of which removes `Set-Cookie`), packs the extension as a CRX3 signed with an RSA key it makes and destroys in that step, and writes `ma-blocker.crx`, `update.xml` (`file://` to the CRX), `blocker-id` and `blocker.json`. Each build has its own id, which `build.sh` writes into the template. **To move the pin:** `build-blocker.py diff old.zip new.zip` lists every rule added and removed; read it, bump the three lines, bake, and run `verify.sh` (its `cookies` part is the check `T47S-2` asks for on every version).
- **`recipe/adblock/site-allow.json`: the blocker's few site exceptions** (task 46, `docs/sub-status/adblock-sites.md`). Some pages test whether an ad library loads and, when it doesn't, start an ad-recovery player from numbered subdomains of a throwaway domain, which costs more than the ads did, or break their own video player. Each entry is `{sites, urlFilter, why}`: the pages of those sites (and no others) may fetch one exact request, `||host/path`, with no wildcard. `build-blocker.py` turns the file into the ruleset `ma-site-allow`, `allow` rules at priority 100000 (above uBOL's own 10, 30 and 40 and below the member's per-site switch), and refuses an entry that is anything else: a bare host, a wildcard, a redirect, no `why`. The ad requests themselves stay blocked by the lists. **To add one:** find the bait with `lab/adblock/bench/ddmin.py <site>` (it allows the blocked hosts a page has, then drops them while the symptom stays gone), narrow it to one URL, prove it with `bench/trace.py` and `bench/vidwide.py`, and write the `why`. A fix that only a `redirect` (a harmless stand-in script) would give isn't added here: the Security Analyst must clear a new rule type first. The kill switch turns this ruleset off with the rest.
- **`/etc/ma/chromium-adblock.json`**, `root:root 0644`: the template. `ExtensionSettings` (the blocker `force_installed` from `file:///usr/share/ma/adblock/update.xml`, `override_update_url`, so it never updates from anywhere else), `DeveloperToolsAvailability: 1`, and the blocker's settings as `3rdparty` policy: `noFiltering: []` and `off: false`. No key in common with `ma.json` or `chromium-teen.json`: `build.sh`, the unit tests and `verify.sh` refuse one.
- **`/etc/chromium/policies/managed/ma-adblock.json`**, `root:kiosk 0640` (`T47S-3`): the template with the member's list as `noFiltering` and the kill switch as `off`, written only by `desk-adblock`. Chromium (kiosk) reads it; uids 1100 and 1103 can't. The AMI has it with no site off, so a desk blocks before anything else runs. It's on the root: a swap brings back the AMI's, and the next start of Chromium renders the list again.
- **`/data/desk/adblock-off`**: `deskd`'s list, one site a line. uid 1100 writes it, so it's an attacker's input to root, read as the teen lock reads the band: `O_NOFOLLOW` on the directory and the file, `O_NONBLOCK`, a regular file of at most 64 KiB, each line a lowercase ASCII hostname with two labels or more, at most 1,000 sites. A bad line is dropped and counted; a file that can't be read counts as empty. Either way blocking stays on. It logs counts, never a site. A clear of history empties it (`deskd`), and the next apply or start of Chromium drops every site from the policy.
- **The kill switch, `/data/.ma-adblock-off`**: a regular file root owns. With it there the blocker turns every list off and stays installed, the member's list kept. The Platform sets it on a desk over SSM with `touch /data/.ma-adblock-off && systemctl start desk-adblock`, and clears it with `rm` and the same `start`. On `/data`, so a root swap keeps it; uid 1100 can't make or remove it. A symlink or a file someone else owns is ignored, and logged. On a desk whose Chromium is frozen (ADR 0045), `systemctl start desk-adblock` can't confirm and fails after 20 s, with the policy written: thaw it first (`deskd`'s `start desk-adblock` on `units.sock` does), or it applies at Chromium's next start at the latest. That Chromium picks it up at a thaw on its own isn't measured.
- **`desk-adblock render`** runs as root before every start of Chromium (`ExecStartPre=-+` in `desk-browser.service`, after the teen lock). The `-` means a template or disk it can't use leaves the policy that's there and never stops the Browser.
- **`desk-adblock apply`** is `desk-adblock.service`, a oneshot `deskd` starts through `units.sock` after it writes the list (and the Platform with the kill switch). As root it renders the policy. Then, as uid 1100, it has Chromium read its policy files at once (`chrome://policy`'s reload, in a hidden page, which is no tab and never reaches history or the session) and reads the blocker's state back from its service worker until Chromium's settings, what the worker says it applied, its `declarativeNetRequest` rules and its lists all match, steady for 1.5 s. It answers `ok` in about 2 s measured, or at once when Chromium isn't running or the blocker isn't installed yet (then it applies at the next start or install). Exit 2, an `err` on the socket, means the blocker didn't show it in 20 s; the policy is written regardless. A CDP call that isn't answered in 4 s costs a new connection, not the apply, and every page it opened is closed, and no other. `ProtectSystem=strict` with only the managed policy directory writable.
- **The blocker applies the policy itself**: at install, at every start of Chromium and whenever Chromium says the managed settings changed (`chrome.storage.onChanged`, `managed`), so a list changed while Chromium was down applies by itself (3 s after the start, measured), and so does the kill switch with no apply at all (Chromium's own watcher, about 9 s). A site off is two `allow` rules at the top priority: every request the site's pages make, and the site's own pages and frames. Not `allowAllRequests`, which Chromium applies only with host permissions, so a frame from elsewhere inside the page still has its own requests filtered.
- **Why `DeveloperToolsAvailability: 1`:** unset, Chromium refuses DevTools on force-installed extensions only, so `desk-adblock` couldn't read the blocker's state and would have to wait and hope. 1 adds the blocker and nothing else, and the blocker is our own code. For the Security Analyst to read.
- **The worker sleeps** when idle. To read its state, wake it with CDP's `ServiceWorker.startWorker` for its scope from any page target, as `desk-adblock` and `verify-adblock.sh` do.
- **`verify.sh` section 3b5** runs `verify-adblock.sh`, which also runs alone on a lab box (`lab/adblock/lab.sh verify <part>`), in eight parts: `install` (the image's blocker at the pinned version from the local manifest, two permissions, no host permissions, content scripts or other scripts, only block and allow rules, every list on, under the teen lock and on band `adult`, Chromium reporting the policy as mandatory); `switch` (through `units.sock`, one site off and another blocked, read back from the blocker and `chrome://policy`, then on again, and no page of the helper's left); `restart`; `stopped` (a list written while Chromium was down applies by itself); `kill`; `cookies` (`T47S-2`: a seeded profile's cookies of every kind and local storage byte-identical after pages with the blocker on, a site off and on again; no script of the blocker in a page); `hostile` (a symlink, a FIFO, a directory, an oversized list and bad lines; the policy `root:kiosk 0640` and unreadable to uids 1100 and 1103); and `keys`. **Section 6c** checks a real root replacement: the list kept on `/data`, rendered before Chromium started, and in effect. Each was broken once and failed: `evidence/adblock-2026-11-07/breaks.txt` for 3b5's eight on a lab box with what ships (13 breaks; the first pass's 4 misses were the checks', fixed and re-run, as the file says), `breaks-swap.txt` for 6c on the first build (the root replaced with 0.2.9's, which has no helper; not re-run on what ships). The first runs of the breaks (`breaks-first-run.txt`) had two that passed broken: a break whose pattern matched nothing, and a restart check the first build's cached list fooled; `breaks.sh` now proves each break took. The test page loads a path from a rule the installed blocker has today, so the check follows the lists as they change.
- **Self-hosted desks** build and install the same blocker, template, helper and unit from `selfhost/install.sh`, which renders the policy. The member has root there.
- **The measuring tools** are `lab/adblock/`, outside any bake: `lab.sh` (the box, and `verify <part>`), `apply.sh` (this recipe's ad blocking onto an older image, the blocker built on the box), `breaks.sh` and `break-swap.sh`, `bench/` (the measurement, the privacy check and their CDP client; config `ma` is the shipped blocker), `explore/` (what was tried first, `evidence/adblock-2026-11-07/exploration.txt`), `tables.py` and `sheet.py`. The measurement itself is ADR 0076's "Measured", with its raw results in `evidence/adblock-2026-11-07/`.

## Chromium tabs (0.2.1)

`desk-browser` runs `/usr/local/lib/ma/desk-browser-start`, which holds the Chromium command line. It passes the home page URL only when the profile has no saved session; otherwise it passes `--restore-last-session` and no URL (a URL on the command line is opened in addition to the restored tabs, which added a tab per restart). Before launching it removes stale `Singleton*` files and marks a crashed last exit as clean, because after `kill -9` Chromium skips `RestoreOnStartup` and, with the crash bubble disabled, came back with one empty tab. `verify.sh` checks first start, restarts, a second tab and `kill -9`. Hidden tabs get no animation frames and 1 timer tick per second; the visible tab keeps 60 fps. That is Chromium's page-visibility behaviour and is left on (switching timer throttling off cost +24 points of one core for one busy hidden tab and gave no frames). `deskd` starts them through `/run/desk/units.sock` (runtime spec section 8.3): `desk-units.socket` runs `/usr/local/lib/ma/desk-units` as root per connection, which allows only uid 1100, only `start`, `stop`, `freeze` and `thaw`, only those four units, and `freeze` and `thaw` only for `desk-browser` (below, "Freezing an unseen desk").

## Chromium downgrade guard and the format record (0.2.3, ADR 0035)

**A Chromium older than the profile can destroy it.** Measured on 156.0.8078.79 with a throwaway profile: a `Cookies` database marked newer is razed, persistent and session cookies alike, and `Web Data` is recreated. `History` and `Login Data` refuse to open and keep their rows. A newer `Last Version` alone does nothing, and Chromium overwrites it on every start, so the check has to come first.

`desk-browser-start` compares `Last Version` with the installed package, using `sort -V`, before it changes anything. If the profile is newer it logs `REFUSING TO START` (priority crit) and exits 78, which `RestartPreventExitStatus` stops from looping. `desk-units` runs the same check through `--check` first, because `desk-browser` is `Type=simple` and `systemctl start` alone reports `ok`. `ExecStartPre` doesn't work here: `RestartPreventExitStatus` ignores it, so it loops.

**To recover:** update Chromium to at least the version named in the journal line, then `systemctl reset-failed desk-browser`. Never remove the profile. Chromium's package isn't held, because members need its security updates.

**A format leaves a record.** `desk-firstboot` writes `/data/.ma-volume` when it formats, with the volume's ID, the time and the image, and logs `FORMATTED` at priority crit. `desk-datadirs` adds a record with `formattedAt: null` to a volume formatted before 0.2.3, and copies it to `/data/desk/volume.json` at every boot, for `deskd`'s heartbeat.

## Freezing an unseen desk (ADR 0045, from the next image)

**What it does.** `deskd` asks `units.sock` for `freeze desk-browser` once nobody has viewed the Browser for 60 s and nothing has worked Chromium for 60 s, and for `thaw desk-browser` before anything reaches Chromium again. `desk-units` writes `1` or `0` into `/sys/fs/cgroup/system.slice/desk-browser.service/cgroup.freeze` and waits, up to 5 s, for `cgroup.events` to say so. Every process of Chromium stops in one step, nothing in Chromium or its pages sees a change of state, it costs no CPU while frozen, and its memory stays. The protocol, the refusals (`busy download`, `busy network`, `busy stopping`, `inactive`) and their order are in `docs/interfaces/desk-runtime.md` §8.3.

**Why not `systemctl freeze`.** That was the plan, and it fails ADR 0035 on systemd 257, measured on a lab box from 0.2.9: a unit systemd froze can't be stopped (`Cannot stop frozen unit`), a start of it says ok and leaves it frozen, and a thaw over D-Bus is refused while the unit has a job pending. So a reboot with Chromium frozen couldn't thaw it: the shutdown's stop failed, Chromium was signalled frozen at the very end and came back `Crashed`. A freeze written in the cgroup leaves systemd's `FreezerState` at `running`, so its jobs run as usual. **Never `systemctl freeze desk-browser`, and read `cgroup.events`, not `FreezerState`, to see whether it's frozen.**

**Every stop thaws first.** A frozen Chromium can't take SIGTERM, and systemd would kill it at `TimeoutStopSec` (measured: 30 s, then SIGKILL, result `timeout`). `desk-browser-thaw.service` is wanted by `desk-browser`, `PartOf=` it and `After=` it, so it's part of every stop or restart of `desk-browser`, a shutdown's included, and stops first; its `ExecStop` writes `0` into `cgroup.freeze` (a file, because a D-Bus thaw is refused by then). Measured with Chromium frozen: `systemctl stop desk-browser` 0.08 s, `restart` 0.15 s, `stop desk-xorg` 0.1 s, all result `success`, and a reboot ended `SessionEnded`. `desk-units` also thaws before a `stop` of `desk-browser`, `desk-xorg` or `desk-audio` and a `start` of `desk-browser`, and `desk-browser-close` thaws before it quits Chromium. `systemctl daemon-reload` leaves a frozen Chromium frozen.

**Every stop quits Chromium over CDP first** (the Security Analyst's IMG-1). `desk-browser-thaw`'s second `ExecStop`, `/usr/local/lib/ma/desk-browser-quit` (root), runs `desk-browser-close --quit` while `desk-browser` has a stop or restart queued: the same `Browser.close` as before a root swap, up to 31 s for Chromium to go (with no answer on CDP, 31 s for its own cookie commit), and `sync -f /data`, with no stop of `deskd` and no `systemctl stop` (the stop is already waiting on it), never failing the stop. So a plain `systemctl stop`, a restart, `deskd`'s holds and policy restarts through `units.sock`, and a shutdown write the cookies Chromium's 30 s timer hasn't committed yet; SIGTERM alone loses them (TD-110). A clean quit this way leaves `exit_type` `Normal`, not `SessionEnded`; both restore the session. A stop of `desk-browser` can now take up to about 85 s when Chromium doesn't answer (55 for `desk-browser-thaw`, then 30 for SIGTERM), so `desk-units` waits 90 s and its unit 100; usually it's under a second. `verify.sh` 3b2a proves a cookie set 5 s before a plain stop, a frozen restart, a frozen stop, a stop through `units.sock` and a guest shutdown comes through.

**No freeze lands in a stop's quit** (the Security Analyst's T46L-1). `desk-browser` reads `active` until its stop's quit is over, so `is-active` alone let a freeze through mid-quit, and Chromium, frozen, was then killed without its session: on a lab box with `main`'s files before this, a freeze asked just before a stop landed in its quit in 4 of 5 stops, and in a restart and in each of 3 stops where 1 was written during the quit; every one ended in SIGKILL at the stop's timeout, most with `exit_type` `Crashed` and a cookie set 8 s before lost. Now:
- `freeze` answers `err busy stopping` while `systemctl list-jobs` shows a stop or restart of `desk-browser` or `desk-browser-thaw`, queued or running, and asks again after its write, undoing the freeze if a stop has come since;
- from that first look to its answer `desk-units` holds an `flock` on `desk-browser`'s cgroup directory, and `desk-browser-thaw`'s first `ExecStop` waits up to 5 s for it before it writes `0`: a freeze under way when the stop is queued has answered, or died and let go, before the thaw and the quit;
- `desk-browser-close`'s wait writes `0` again every second, so anything that gets past both holds Chromium for a second at most;
- `desk-browser-thaw` is `Before=deskd.service`: with both stopping, as at a shutdown, `deskd`, the only thing that asks for a freeze, stops first. While a shutdown runs `units.sock` takes no new requests at all: a new `desk-units` can't start then, and the connection is reset (measured).
**A shutdown reaches Chromium only through its units.** On the system bus Chromium holds a logind shutdown inhibitor ("Saving browser state") and ends its own session the moment logind announces a reboot or power-off (`PrepareForShutdown`), before systemd stops any unit, the way SIGTERM does: measured on the lab box, a plain reboot ended `SessionEnded`, `desk-browser-quit` found nothing left to quit, and a cookie set 8 s before was lost, frozen or not, with or without this fix. Earlier shutdown checks (verify.sh section 6) froze Chromium well before the EC2 stop, which probably let its overdue cookie commit run the moment it was thawed, so they didn't show this. So `desk-browser.service` sets `DBUS_SYSTEM_BUS_ADDRESS=unix:path=/dev/null/no-system-bus`: no inhibitor, no signal, and a reboot then goes `deskd`, `desk-browser-thaw`'s quit over CDP (`Normal`), `desk-browser`, with the 8 s cookie kept. Chromium logs a few `Failed to connect to the bus` lines as it starts, and nothing after. It used the system bus for nothing else here (UPower, which a desk doesn't run).
`verify.sh` 3b2a item 13 checks the order and the lock as installed, that Chromium has no system bus connection or inhibitor, `busy stopping` with a stop held queued, an 8 s cookie through stops and a restart begun inside a freeze's network window, and through a stop with `1` written mid-quit; section 6 checks that at the guest shutdown `deskd` stopped before `desk-browser-thaw` began and Chromium was quit over CDP (`Normal`, `quit=cdp`). Freeze and thaw times are unchanged (`docs/sub-status/freeze-race.md`).

**Never give `desk-browser.service` an `ExecStop`, `ExecStopPost` or `ExecReload`.** systemd 257 starts those inside the unit's cgroup with `vfork` (`CLONE_INTO_CGROUP`); if the cgroup is frozen then, the child is frozen before it runs and PID 1 waits on it in D state (`kernel_clone`) until something thaws the cgroup. Measured: a stop of a frozen `desk-browser` with an `ExecStop` hung PID 1, so logins and a power-off hung too, until a root shell already open wrote `0`. That's why the quit lives in `desk-browser-thaw`, outside the cgroup, and `verify.sh` 3b2a checks the three are empty.

**The network check** reads `/proc/<a Chromium pid>/net/route`, `ipv6_route` and `dev`, so `desk-units` keeps `PrivateNetwork=yes` and `AF_UNIX` only. It counts the desk's whole outside traffic, not Chromium's sockets alone: on a desk nobody looks at no media flows, so that's Chromium's and a little control traffic. With desks sharing one network namespace on a host it would count every desk's, and has to change. QUIC is counted, as it's at the interface.

**No sound check.** It was built and measured, then dropped on the Desk and UI/UX Engineers' word: `deskd` freezes only after no session has had the desk's media for 60 s, so nobody hears a sound then. `desk-units` doesn't run `pactl`.

**Measured** on a `c7g.xlarge` (`docs/sub-status/desk-units-freeze.md`): a freeze through `units.sock` p50 568 ms (the 0.5 s network window), a thaw p50 about 60 ms, a thaw to the first page frame p50 68 to 73 ms and p95 80 to 89 ms (20 each, three runs), about 52 ms of CPU a request, and a frozen Chromium uses no CPU (cnn.com in front: 99% of a core before the freeze, 0 during) and keeps its memory.

## Who can reach Chromium's debugging port (0.2.3)

`nftables.conf` lets only uid 0 and 1100 connect to port 9222, on `127.0.0.1` and `::1`. The rule that refuses everyone else matches a new connection only (SYN without ACK). It used to match every packet, and the kernel's own packets for a closing connection carry no uid, so each CDP request left Chromium's side in `LAST-ACK` for about 100 s, and a new connection from that port hung until it went. `evidence/cdp-last-ack-2026-11-06.txt` has the repro. `verify.sh` checks both addresses by uid and counts those sockets after the keymap check's thousands of requests.

## Keymap and window size (0.2.2)

`desk-xorg` runs `desk-xorg-ready` once X is up. It loads rules `evdev` with symbols `pc+us` with `setxkbmap`, and only then gives `rtc` and `stream` X access, so neither can see the default keymap. Xorg with no input devices starts on rules `base`, which means xfree86 keycodes, while Chromium reads keycodes as evdev.

**Who reaches X (DA-1, from the next bake).** Xorg starts with `-auth /run/desk-xorg/auth`, a cookie `desk-xauth` makes at every start (16 random bytes, `0600 kiosk`, in kiosk's `RuntimeDirectory`), and `-nolisten local`, so there's no abstract socket for a process sharing the network namespace (`deskd` and `desk-agent` run with host networking). Without `-auth`, Xorg treats every local uid as authorised, so `desk-agent` could read and drive the member's Browser. `desk-xorg-ready` is the only client that uses the cookie: it adds `SI:localuser` for `kiosk`, `rtc` and `stream`, which X checks by the socket's peer uid, and nobody else is given it. Every other uid, `deskd` (1100), `desk-agent` (1103), `desk-notebook` (1105) and root included, is refused. Root reaches X for maintenance with `XAUTHORITY=/run/desk-xorg/auth`, or as kiosk (`sudo -u kiosk env DISPLAY=:99 ...`, as `verify.sh` does). `verify.sh` section 3a3 checks it.

**`desk-agent` needs the ruleset (DA-2, from the next bake).** Its only way out is nftables' `agent_redirect` (ADR 0070), so `desk-agent.service` requires and follows `nftables.service`, and its first `ExecStartPre` lists `inet ma agent_redirect`: with the table missing it doesn't start, and `Restart=` brings it back once the ruleset is loaded. `/opt/ma/smoke-test` fails the same way while a `desk-agent` release is installed. Self-hosted desks take the same unit and smoke test from this recipe (`selfhost/install.sh`), with their own `nftables.conf`, which has the chain. `verify.sh` section 3e0 removes the table and loads it again.

`desk-browser-start` resizes the Chromium window to 1920x1080 with `xdotool` once it appears. There's no window manager, so `--kiosk` never makes it fullscreen, and Chromium opens a window that exactly fits a display 1 px smaller each way. The helper exits once the size is right, and runs again on every Chromium start. `verify.sh` checks the keymap, the named keys, ASCII, every spare code in `desk-rtc/internal/xinput/spares.go`, and the viewport.

## Changing encoder settings

Everything the encoder does is in `recipe/desk-stream/stream.conf`. `convert` and `x264` take the same strings as `CONV_*` and `X264_*` in `spikes/browser-bench/followup3/variants.sh`.

1. Edit `stream.conf`.
2. `./package-desk-stream.sh <version>`. The image already has `yuvconv`. Any other plugin the pipeline needs goes in `recipe/desk-stream/gst-plugins/<arch>/` first, as `deskcap` does (below).
3. Roll the artifact out with `ma-update desk-stream <url> <sha256>`, test desk first. No code change and no AMI.

**Quality levels (ADR 0039, `desk-stream` 0.2.4 on).** `stream.conf`'s `[level.low]` to `[level.max]` hold each level's `max-height`, `quantizer`, `bitrate` and `vbv-buf-capacity`, and `desk-rtc` picks one with `level <name>\n` (`docs/interfaces/stream-quality.md` §5). With them the pipeline gains `videoscale ! capsfilter name=size` after `convert`, in passthrough at full size; `stream-capped.conf` and `stream-deep.conf` have none, so they build 0.2.3's pipeline exactly and ignore `level`. x264enc takes a new `quantizer` only in READY, so a level reopens the encoder alone, between two frames: one keyframe, about 30 ms from the command on a lab box (`tests/test_desk_stream_levels.py`).

**Capture only what changes (ADR 0073, `desk-stream` 0.3.0 on).** `stream.conf`'s capture is `deskcap`, not `ximagesrc` and `yuvconv`: XDamage on the root window says what changed, only that is read over MIT-SHM, compared and converted to NV12 (libyuv, as `yuvconv`), and a frame goes out only when the screen changed, a keyframe was asked for (`desk-stream` emits `deskcap`'s `refresh` with every one), or a heartbeat is due on a still screen (at least one a second, so a browser counts no freeze and asks for no keyframe). Motion runs at up to `max-fps`, paced by a token bucket so the first changed frame after a still spell goes out at once. Its two capture buffers are shared with the X server's group only, `0660` (Xorg runs as `kiosk`), where `ximagesrc` made them `0777`. `framemeter`, in the same plugin, counts frames and their latency after the encoder for `[adapt]`, the contention control: when the desk can't hold its frame rate it lowers resolution, then quality, and only then caps at 30 fps (`order = fps` puts 30 fps first). `run` puts `gst-plugins/$(uname -m)` on the plugin path, so one artifact serves cloud desks (`aarch64`) and self-hosted ones (`x86_64`); if `deskcap` won't load, each conf's `fallback-capture` and `fallback-convert` (0.2.4's) run instead. **Building it:** each `BUILD` holds the exact command, run in the folder that holds `deskcap.c`. `x86_64` is the gcc line in a `debian:trixie` container with the packages `tests/test_desk_stream_damage.py` lists. `aarch64` is the same line on a Debian 13 arm64 machine, or the cross line in its `BUILD` in a `debian:trixie` container on x86_64 with `crossbuild-essential-arm64` and those packages for arm64 (`dpkg --add-architecture arm64`); the two give the same bytes (checked 2026-11-10). Write the new hashes into each `BUILD`. `package-desk-stream.sh` refuses a plugin whose `BUILD` names another source, another binary or the wrong architecture. Measured in `spikes/desk-stream-damage/README.md`.

**Video islands (ADR 0075, `desk-stream` 0.3.2 and `desk-rtc` 0.3.6 on).** `videocrop` heads the scale chain, in passthrough with no island. `desk-rtc` sends `crop X Y W H OUTW OUTH` or `crop none` when `deskd` sets an island (`docs/interfaces/desk-runtime.md` §8.8): a new picture size costs one keyframe, a move costs nothing. On by default, with a kill switch only, once the Security Analyst clears T47S-1 (`desk-rtc` 0.3.7) and `deskd`'s part is built.

`ON_DEMAND` in a release makes `ma-update` use `try-restart`, so an update doesn't start a stream nobody asked for. A running `desk-stream` restarts, and a viewer gets a keyframe from the new process.

**Sound is 48 kHz and stays there (`sub/sink-48k`).** `desk-audio.service` loads the null sink with `rate=48000` and `/etc/pulse/daemon.conf.d/ma-48k.conf` sets the server's default and alternate rates to 48000, so a suspend and resume of the sink can't leave it at 44.1 kHz under its 48 kHz monitor (which broke a rollback to `desk-stream` 0.3.1's sound in a bench). `verify.sh` 3a0 reads the sink, its monitor and the server over `pactl`, also after a suspend and resume, and loads a 44100 control sink to show the reader can see a wrong rate. Unpinned (`ma-desk-0.2.9`), sink and monitor were at 44100.

**Sound and picture share one clock (ADR 0037, `desk-stream` 0.2.3 on).** The pipeline's base time is 0 with no start time, so its running time is CLOCK_MONOTONIC, and both payloaders have `timestamp-offset=0`: every RTP timestamp is its capture instant, which `desk-rtc`'s sender reports rely on. A pause no longer freezes running time, so timestamps jump by the pause's length, and the encoder's first audio packet after a resume carries its time from before the pause (`desk-rtc` drops it). Keep any new branch or encoder on this pipeline's clock with `timestamp-offset=0`. The audio buffers are small on purpose, since the sound already reaches a client after the picture: 5 ms Pulse fragments and 10 ms Opus frames, the same in all three `stream*.conf`.

## Desk batches and Debian's updates (S-96, from the image after 0.3.1)

Members' desks take updates rarely and never in the middle of use (`docs/decisions/draft-desk-app-contract.md` section 13): at most one signed **batch** a month of the desk's services, applied all or nothing while the desk is idle. The protocol, the manifest, the state and the idle file `deskd` writes are in `docs/interfaces/desk-runtime.md` §6.1. Test desks and the owner's desk still take single releases through `desk-service-release.sh`.

**What the image has.** `/usr/local/lib/ma/desk-batch` (root, Python, the style of `desk-units`), `desk-batch.socket` on `/run/desk/batch.sock` for `deskd` (offer, status, hold), and `desk-batch.timer`, which ticks 2 minutes after boot and then 5 minutes after each tick. **From 0.3.2** `/opt/ma/etc/batch-keys/` holds exactly one file, Platform's release key (`ma-desk-batch-2026-11.pem`, the public half of KMS `alias/ma-desk-batch`, `ECC_NIST_P256`, sha256 `96287954…3f0a`; `verify.sh` section 7 `install` checks the name, hash and curve), and `/etc/ma/batch-keys.d/` is empty. A batch signed by anything else is refused. (0.3.1 and earlier have no key and no helper; a build with no key refuses every batch, so a new release key means a new `recipe/files/opt/ma/etc/batch-keys/<name>.pem` and a bake.) The first real batches were applied to the test desk on 0.3.2 (`RELEASES.md`, "0.3.2"; `evidence/desk-batch-2026-11-10/`). The repo ignores `*.pem`, with one exception for that directory, and `build.sh` fails if either key directory holds a private key. A lab box or the test desk takes a dev key in the drop-in. `recipe/build.sh`'s block between `# >>> desk-batch` and `# <<< desk-batch` installs all of it, and `lab/desk-batch/apply.sh` runs that same block.

**How a batch goes on.** `deskd` gets it from the platform and offers it on the socket. `desk-batch` checks the ECDSA P-256 signature with `openssl` against the trusted keys and refuses a sequence number at or below any batch it applied or gave up on, then keeps it pending. At the first tick with the desk idle (`deskd`'s `/run/desk/idle.json`, fail closed), it prepares every component that isn't already current (`ma-update --prepare`: download, hash check, unpack and `docker load`, nothing switched; a release already on the desk is prepared from disk by hash), reads idle again, and activates them in the manifest's order (`ma-update --activate`: switch, restart, the 90 s smoke test). A failure before the first switch changes nothing and is tried again an hour later with new URLs, three times at most. A failure after it rolls the switched components back, in reverse, with `ma-update --rollback`, and that batch is never tried again; a rollback batch is a newer sequence number naming older versions. A batch that names an image applies its services and records `root-pending`. `holdUntil` stays 15 minutes ahead while it works, for the platform's idle sweep. A tick cut off mid-batch is finished or put back by the next one.

**Measured on a lab box** (`c7g.large` from 0.3.1, real published releases, 2026-11-09; `docs/sub-status/desk-batch.md`): desk-rtc and deskd back to the launch image's in 12.2 s (prepare 8.0 s with deskd's 127 MB download and load, activate 4.1 s) and forward again in 4.1 s (both previous, nothing downloaded); a cold batch of all five services, four downloaded and three loaded, in 32.6 s (prepare 20.8, activate 11.8); the same through the timer in 32.0 s; a tick killed mid-activate finished by the next one, with no idle. One sample each. A tick with nothing to do costs about 54 ms of CPU every 5 minutes.

**Debian's updates run only while idle.** `apt-daily.timer` and `apt-daily-upgrade.timer` are masked (one first boot lost 31.5 s to them, `evidence/verify-<ami>.txt`). `20auto-upgrades` stays as it was: `unattended-upgrade` run directly doesn't read it, and a self-hosted desk, which `selfhost/install.sh` gives these files without masking anything, keeps Debian's daily timers. A tick runs `apt-get update`, `unattended-upgrade` and `apt-get clean` at `nice 19` in the idle I/O class, once a day at most, while the desk is idle or after 72 hours with no idle. `51ma-unattended` clears Debian's origins and keeps only the security archive, so stable point releases wait for a new image; Chromium's Debian updates come from `trixie-security` (156.0.8078.79-1~deb13u1 is that archive's). On the lab box the first run installed kernel 6.12.116, apt 3.0.4 and vim from it, in 19.9 s. **Until `deskd` writes `idle.json`, apt runs only every 72 hours.** `desk-batch` records `chromium.pending` when a running Chromium's binary has been replaced, and `reboot.pending` for a newer kernel, and does nothing about either: Chromium isn't closed at idle, because a newer Chromium opening a real profile is unproven (every image and `trixie-security` today have 156.0.8078.79, so there was nothing newer to try), and nothing reboots. A new Chromium starts at the Browser's next start: a stop and wake, a reboot or a restart `deskd` makes.

**`apt-listchanges.timer`** still fires once on each new desk, at its first midnight, to build its changelog database (`populate_database`), then disables itself. It's small and it isn't apt's upgrade, so it's left as it was.

## Faster wakes (TD-227, from the bake after 0.3.1)

An Alliance Member's desk is stopped after 20 idle minutes and started as soon as they open their office, so a wake is the first thing they wait for. On the first image (0.3.1) a `t4g.medium` took a median of 27.9 s from the office loading to the first Browser frame, and 31.1 s to Chromium's tabs. With the two changes below: 24.0 s and 24.2 s (5 wakes each, `docs/benchmarks/2026-11-alliance-desk.md`). The wait has four stretches, and these change only one each: A, the office loading to the kernel's first instruction (about 9.8 s, EC2's own power-on); B, the kernel to deskd's hello (11.7 s, 8.8 s after); C, hello to the app's next `connect` poll answering (about 2.3 s, the app's); D, that answer to the first frame (2.7 s), or to Chromium's tabs (5.9 s), 1.9 s and 2.4 s after.

- **cloud-init is off after a desk's first boot.** It configures the network, host name and users on a first boot, and on every later one it only asks IMDS whether anything changed, and it stands in front of the network: `cloud-init-local` is `network-pre.target` and `cloud-init-network` is before `sysinit.target`, so Docker and everything after it waited for it and for DHCP. `/etc/systemd/system/cloud-final.service.d/ma-off-after-first-boot.conf` adds an `ExecStartPost` that writes `/etc/cloud/cloud-init.disabled` once the final stage has succeeded, which cloud-init's generator reads on the next boot and enables none of its units. B drops from 11.7 to 8.3 s, and `systemd-analyze` on one boot of each from 8.0 to 5.9 s. A first boot where cloud-init failed leaves it on. A root replacement brings an image root without the marker, so cloud-init runs once more as on a first boot and writes it again. **The image never has the marker:** `build.sh` removes it before the final assertions and asserts it absent, because a builder that rebooted after the install would have written it and every desk would skip its first boot.
  - **`/etc/systemd/network/20-ma-dhcp.network`** is the fallback for what cloud-init no longer re-renders. netplan's file for a desk (`/run/systemd/network/10-netplan-ens5.network`, from `/etc/netplan/50-cloud-init.yaml`, written once) matches the card's permanent MAC address, so a desk whose card changed (a different instance's volume attached, say) would have no address. This one matches `en*` and `eth*` wired cards by name and does DHCP. It sorts after `10-` and systemd-networkd uses the first file that matches, so on a normal boot it is never the one used; `verify-wake.sh fallback` changes the match, sees the fallback take the card and DHCP answer, and puts the file back.
  - Both files are installed by `build.sh` from `recipe/wake/`, not from `files/`, because `selfhost/install.sh` copies all of `files/` onto a member's own machine, where a drop-in on cloud-final and a DHCP file for every wired card have no business.
  - **To undo it on one desk:** `rm /etc/cloud/cloud-init.disabled` and reboot (cloud-init runs, and writes it again unless the drop-in is removed too).
- **The Browser starts with the machine, once deskd answers.** `desk-browser-prewarm.service` (Type=exec, so it never holds the boot) runs `/usr/local/lib/ma/desk-browser-prewarm`, which polls `/opt/ma/deskd/current/health` for up to 30 s, runs `desk-browser-start --check` as `kiosk` (the refusal for a profile newer than Chromium, ADR 0035, exactly as `desk-units` does it) and then `systemctl start --no-block desk-xorg desk-audio desk-browser`. D' (connect to tabs) drops from 5.9 to 2.4 s, and the first frame is a page, not an empty screen. **What it will not do:**
  - Start with no `/data/desk/age-band`: that is deskd's record of the member's age band, and `desk-browser-policy` locks the Browser for anything but `adult`, so a first boot (no file yet) would start Chromium locked and deskd would have to restart it. A desk's first Browser use is on demand, as before.
  - Run on a Guild Desk (`/run/ma/guild`; the units' own `desk-kind.conf` skip there too) or when `/data/desk/no-prewarm` exists. **That file is the kill switch**: it lives on `/data`, so it survives a root replacement, and it is what `verify.sh` sets for the whole run (the rest of the file assumes the Browser starts on first use), taking it off only for section 8.
  - Start `desk-stream`: deskd stops it at every boot until a viewer wants it (measured, about 0.1 s after a prewarm started it), so there is nothing to keep warm.
  - Start before deskd answers: with Chromium started at multi-user.target instead, deskd's hello came 2.1 s later (median B 10.4 s against 8.8 s, 5 wakes each), because the desk has two vCPUs and the JVM starts in the same seconds.
  - Cost idle CPU the idle stop or the credits would mind: see the benchmark's credits section. deskd freezes an unseen Chromium as before (ADR 0045).
- **Tried and not kept.** Docker without `After=network-online.target` (a drop-in): no gain once cloud-init is off (B 8.2 s against 8.3 s, 5 wakes each), because `containerd` and `docker` then take about 1.8 s after `basic.target`, as long as the network does. Not shipped. **EC2 hibernation** works on this image (Debian 13 arm64, `t4g.medium`, encrypted root; benchmark section 6) and is not faster.
- **`verify.sh` section 8** (`verify-wake.sh`, 6 parts: static, first, later, fallback, boot, gates) is last because it reboots the box three times. Each part was seen to fail with what it guards broken: `evidence/alliance-wake-2026-11-09/mutations.txt`.

## Updating a running desk

`ma-update <component> <url> <sha256>` (root, over SSM): see runtime spec section 6. Exit 0 healthy, 1 rolled back, 2 failed before any change. `ma-update <component> --rollback` swaps `current` and `previous`. Rolling out the release that's already current, from the same artifact, changes nothing and exits 0 if healthy, so a rollout of the baked version is safe. The same version from another artifact is refused.

**Before a root swap, close Chromium** (task 33 item 3; ADR 0035). `CreateReplaceRootVolumeTask` reboots the instance, and AWS says only that it reboots, not that the guest is asked to shut down, so Chromium may not get its SIGTERM. Run `./desk-browser-close.sh <instance-id>` straight before the swap, after `desk-root-preflight.sh`, and swap only on exit 0. It sends this tree's `recipe/files/usr/local/lib/ma/desk-browser-close` over SSM, so it works on every image, and from 0.2.6 the helper is on the desk too. On the desk it stops `deskd` first, the only thing that starts `desk-browser`, and waits for a start `desk-units` is already running. Then it asks Chromium to quit over CDP (`Browser.close`, as root on port 9222): that's Chromium's own Exit, and it writes the cookies it hasn't committed yet. systemd's SIGTERM is Chromium's session-ending path, which writes the session and preferences but leaves cookies to Chromium's commit, about every 30 s, so a cookie set in the last 30 s was lost (`docs/sub-status/td-110.md`; the test desk, 2026-11-07, `evidence/close-cookie-2026-11-07/`). If CDP doesn't answer, or Chromium is still running 31 s after it was asked, the wait has let a commit happen, and systemd's stop follows (`TimeoutStopSec=30` before SIGKILL). Then `sync -f /data`, so nothing Chromium wrote waits in memory for a reboot that may not flush it. It reads `exit_type` from the profile's `Preferences` and nothing else, and never writes there. Its line ends `quit=cdp`, `quit=term` (the stop did it) or `quit=none` (not running), and `sync=ok`. Exit 0 means stopped with a clean exit (`Normal` after `Browser.close`, `SessionEnded` after SIGTERM) or not running, and synced; 1 means still running, killed or not synced, so don't swap yet. `deskd` stays stopped until the reboot: if you don't swap after all, `systemctl start deskd`. A graceful shutdown is covered without it: `desk-browser.service` is ordered `Before=deskd.service`, so on the way down `deskd` stops first and Chromium then gets its 30 s, with the 30 s cookie window above. While Chromium runs its `exit_type` reads `Crashed`, and `desk-browser-start` rewrites a `Crashed` to `Normal` before each start, so read it only before anything starts Chromium again (`e2e/tests/browser-session.spec.ts`, `SESSION_CHECK=root-swap`, does).

**A root swap brings back the baked versions,** which may be older than what the desk ran: `/opt/ma` is on the root, so after `CreateReplaceRootVolumeTask` the desk runs exactly what the new AMI's tags name, with no `previous`. `/data` keeps the DTLS identity and `deskd`'s state. Compare the AMI's `Desk*Version` tags with what the desk ran before the swap, and roll forward whatever is older than the last version that passed.
