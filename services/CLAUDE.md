# Desk services

Java 21 + Spring Boot backend services that run on the desk EC2. Owner: Desk Engineer. Today that is `deskd`, with the walking skeleton's client-to-desk data plane, desk-to-Platform control plane, real token verification, release packaging, and milestone 2's Browser control, and `desk-agent` (task 04): the desk's agents, a module of this build since `sub/deskd-agent-relay`, in no release and on no desk yet. deskd relays the Agent app's `agent.*` methods and topics to it (`agent/`, `API.md` §11), and Notebook's `notebook.*`, `notebook.tree` and `collab` to `desk-notebook`, a Node service in `services/notebook/` that another branch builds (`notebook/`, `API.md` §13). `desk-agent`'s `README.md`, `STATUS.md` and `docs/proposals.md` say what it wants outside its folder, and what's been done of that. `desk-guildhost` becomes another module.

Read first: [ADR 0040](../docs/decisions/0040-desk-services-spring-boot-docker.md) (why Java, footprint and Docker rules), [ADR 0041](../docs/decisions/0041-deskd-drives-cdp-directly.md) (CDP without Playwright) and [`docs/interfaces/desk-runtime.md`](../docs/interfaces/desk-runtime.md) (uids, paths, boot order, `rtc.sock`, container settings, release artifact). `desk-rtc`, `image/` and `web/` belong to other sessions.

**Known gaps**
- **`ACTIVITY` is ignored from a session without input, but `desk-rtc`'s own input count is the better source.** The client-reported `ACTIVITY` stays only for input handled locally, and a token with input can still over-report it.
- **Single-use tokens: settled, keep it.** The System Engineer decided desk tokens stay single-use, and the design says so. Don't relax the `jti` check. Platform changes the wording in `auth.md` §4.1 and `gateway.md` §2.3 once UI/UX confirms the app doesn't reuse a token.
- **A refresh lost in the gateway's 2 h reconnect gap: Platform fixed 
the hub.** `session.refresh` now answers `desk_not_ready` if it can't relay, and UI/UX planned to send AUTH as well. `session.resume` has the same pattern, which Platform will fix after its stop test. Neither is confirmed against a real desk.
- **`media` totals** carry across a restart of `desk-rtc`, but they still lose the bytes since its last `stats`, miss a restart if the new total has already passed the old one, and lose the carry if `deskd` restarts too. They need a file in `/run/desk` to do better. `agent.md` says under-reporting only bills the member more, and Platform doesn't read `media` yet.
- **`final: true` goes out on every SIGTERM,** a plain restart included, because deskd can't tell that from an ACPI stop. `readyToStop: true` goes out only after a heartbeat response has carried `prepare_stop`, because Platform powers the desk off on it. Releases before this one sent it on every SIGTERM.
- **`prepare_stop` is remembered per process.** A deskd restarted after seeing it closes with 4002 on the next SIGTERM. `API.md` §7 tells clients not to rely on 4503 alone.
- **Two opens racing for the last slot** can use up the loser's token. Its retry gets `invalid_token`, and goes through `connect`.
- **Browser, not yet seen on a desk:**
  - `URLBlocklist` really answering `net::ERR_BLOCKED_BY_ADMINISTRATOR` to `Page.navigate`. That needs a managed policy in `/etc`, so only the fake has sent it.
  - In a headed kiosk window with no window manager: `/json/list` moving a tab to the top when it's shown, an isolated world on Debian's build answering, and `Target.createTarget` opening a tab rather than a window. Checked headless only. `document.visibilityState` itself is known good there: pages on `ma-desk-0.2.1` reported `visible` only for the selected tab, and it flipped on activate (the verify record under `image/evidence/`). If those reads failed there, lists would still work, and every call leaving out `tabId` would get `unavailable`.
  - A session-restored background tab that hasn't loaded: if it's silent and above the tab on screen, a call leaving out `tabId` costs up to a second more, and if the tab on screen is silent too it gets `unavailable`.
  - A popup window, which is on screen along with the tab under it. deskd would take the one shown last.
  - Debian's Chromium accepting `Target.setDiscoverTargets`'s `filter`, and the Ctrl+T page's URL, which this assumes is `chrome://newtab/` or `chrome://new-tab-page/`.
  - How long a `start` takes through `desk-units`, which is a Python process per request. Going from `warm` to `live` with both units up doesn't wait for it. A first `live` does.
- **A tab changed on the keyboard, or a title set by itself, takes up to a second** to reach `browser.tabs`, and only while someone is viewing: CDP has no event for either.
- **A live Chromium with an end of input JDK 21 lost is found within about 10 s.** See `CdpClient`: until the probe fails, calls on pages time out, and the topic is quiet. Each read of the tabs now has a reply to lose one behind: a fake cutting the socket a few ms after one lost it in 36 of 40 tries, against none in 60 on the release before, which had no message there. So only a crash in that moment is affected. Reads come once a second while someone is subscribed and viewing, however often a title changes, and one per call. A page that keeps navigating, as `pushState` lets it do on purpose, gets a subscriber's list read up to once per 250 ms, viewing or not, as that's what a navigation asks for.
- **A stop that fails with no session left to retry it stays failed.** `desk-stream` stays up, paused, until a session ends or goes `off`. There's no timer for it.
- **A URL Chromium calls invalid after deskd passed it gets `unavailable`,** as that's not an error `Page.navigate` tells apart from any other. The case that was seen, a host ending in a number, is refused now.
- **Who holds port 9222 is checked by uid, not by program.** deskd won't connect to a listener that could answer 127.0.0.1:9222 (bound to it, to `0.0.0.0`, or to `::` or a mapped form on tcp6) unless its uid in `/proc/net/tcp` is `DESKD_CDP_UID`, nor while another uid holds a connection accepted on that port, and if the table can't be read it connects to nothing (`CdpListener`). What's left:
  - Any other `kiosk` process would pass while Chromium is down, as Xorg and PulseAudio share that uid. One that's been compromised already shares a user with the browser's profile.
  - **The race, which is narrow.** The table is read before each request to the port and again as soon as a WebSocket is open, before anything is sent to it or believed from it. A single request can land on a listener in the moment after a read, and sends nothing: `/json/version` yields only a path that has to match, and `/json/list` only the order of tabs deskd already knows, until the next read. It can't keep what it got: whoever accepted a connection stays in the table under their uid for as long as they hold it, listening or not. That matters because the JDK's client pools connections and a WebSocket's upgrade goes over a pooled one, so a kept connection used to get every later read and the next WebSocket, with all a client typed, while uid 1102 had the port back (`CdpClientTest`). Keeping it now only denies the Browser, as below, until they let go or the client's keep-alive runs out.
  - The kernel's walk of that table isn't atomic, so a listener could be missed. That reads as nobody listening, which connects to nothing, and tries again. A kept connection could be missed too, which lets one more request through to it, and the next read sees it. In 1,653 reads here with other sockets coming and going, no listener was.
  - A process that holds the port still denies the Browser: Chromium can't have it, `/health` says `refused`, and calls get `unavailable`. The next look after it lets go clears that, unless Chromium started meanwhile. Then Chromium is on `::1`, its fallback, and stays there, so `/health` says `displaced` and deskd restarts it (Browser choices below). A socket that's only bound holds 127.0.0.1 too and is in no table, so it can send each restart back to `::1` until it goes. All this was seen with headless Chromium 1248 (`ChromiumIT`), and not with Debian's build, headed, or through the real `desk-units`.
  - **`::1` is firewalled from image 0.2.3.** `image/recipe/files/etc/nftables.conf` lets only uid 0 and the desk's uid (1100) open new connections to port 9222, on `127.0.0.1` and on `[::1]` alike (`docs/interfaces/desk-runtime.md` §1; the rule landed in `aaf45da`). So while Chromium is on `::1`, no other uid, `kiosk` and `agent` included, can reach its debugging port. An image older than 0.2.3 has no `::1` rule. `verify.sh` checks both addresses by uid.
- **A refused Chromium is known only from a start's reply.**
  - The refusal outlives a restart of `deskd`, through an empty `chromium-refused` beside `units.sock` (`/run/desk` on a desk), read once at startup. A reboot clears it, as `/run/desk` is a tmpfs, and that's right, but `deskd` can't read the profile itself, as its container sees only `/data/desk`. So until the first start after a reboot, `/health` and the heartbeat say nothing of it, and Platform clears its flag until the next refusal. `rtc` owns `/run/desk`, so it can add or remove the file, and that's all it gains. A file that can't be written or removed is one log line, and then a restart of `deskd` gets the refusal wrong until the next start. `desk-runtime.md` §2, the System Engineer's, doesn't list the file yet.
  - `desk-units` takes a check that runs over 10 s as no refusal, so `start` says `ok`, `deskd` clears the refusal and its file, and then the wrapper exits 78. The client has `live` with no Chromium. A unit that passes the check and exits 78 anyway looks the same: `systemctl` has said `ok` by then.
  - A session already live when Chromium goes and its restart is refused is never told, as no request of its own failed, and it stays `live`, with the stream up. Its calls get `unavailable` with `reason: chromium`, and only `/health` and the heartbeat say why.
  - A Chromium off its port stays there while a refusal is known, so `/health` says `displaced` and calls get `unavailable` until a start works, and the next look after that restarts it. Restarting it would stop a browser that works, for a start that would very likely be refused. A restart asked for while a start is on its way is dropped if that start is refused. This takes a check that begins to fail while Chromium runs.
  - The wrapper also refuses a `Last Version` that isn't a version, and an installed version it can't read, with the same reason. `agent.md` 0.3.8 describes the check only as a profile newer than the image's Chromium, and the cost guard's `chromium_refused` mail says to move the desk to an image with the same or a newer Chromium. Neither helps those two.
- **The web client retries a refused `live`.** `web/src/browser/streamControl.ts` treats every `unavailable` as worth another try, 0.5 s up to every 30 s, for as long as the window wants `live`. Until the UI/UX Engineer stops on `chromium_older_than_profile`, a refused desk gets a Python process and a `crit` line about every 30 s per open window.
- **Queue limits grow with channels.** `RtcClient.CHANNEL_QUEUE_LIMIT` is per channel, and the sum in `jvm.options` counts `ctl`, `rpc`, `bulk` and `collab`. `bulk` adds only about 0.8 MiB per session, as each `data.read` transfer parks once 64 KiB of it waits (`RtcClient.QUEUE_LIMIT`, per message, and a transfer's frames are one message there). `collab` adds about 0.1 MiB there the same way, as every DATA has one id. Its messages in deskd are the other 14.5 MiB per session of the sum, which `jvm.options` has in full: about 159 MiB, under `-Xmx192m`. A module serving `mdoc` adds up to 3.7 MiB per session unless it does the same, so redo the sum then.
- **The heap sum counts no request in flight but the clipboard's, and no reply waiting to become a RES but one.** `RpcSession` holds a session to 32 calls, not to their bytes, so 32 slow calls of 1 MiB each, with what they parse to, hold about 64 MiB until they end. Only the owner's own client could send that. The clipboard bounds its own (Browser choices), and a budget of bytes per session in `RpcSession` would close the rest. Found while redoing the sum for the clipboard, and not changed with it. `notebook.*` has the same gap on the way back: up to 16 calls per session can each hold a parsed reply of up to 1 MiB, on the same owner's say-so, and the sum counts the one being read. Only `notebook.page.content` and `notebook.version.get` come near that, at 512 KiB of text a part, and a client asks for those one at a time.
- **Task 32's `data/`, seen on a desk only through the export check of 2026-11-06** (image 0.2.6 has `desk-data`; task 37):
  - **`data.browser.cookies` reads Chromium's whole list in one CDP message,** which `CdpClient` drops past 2 Mi chars, about 5,000 cookies. Chromium keeps at most 3,300, at a few hundred bytes each, so only a profile full of long values would reach it, and then the call gets `unavailable` and the connection stays up, as it goes through `CdpClient.ask`. A cookie's strings are cut at 4,096 chars, past what Chromium allows.
  - **`freeBytesSent` is only an `export` session's frames, up to `FreeBudget`'s cap,** 3 times the data volume's size per 30 days from the first free byte, so a client looping `data.read` reaches the meter. `Transfers.countFree` is the only place that adds to it. The price of the owner's rule is what's left: any member can mint an `export` token, so one 32 GB desk can still send about 110 GB off the meter every 30 days (96 GiB of frames and the meter's 7%), roughly $9, whether it's an export or not, and the budget is per desk, not per member. Past that, only the meter and the cost guard stop it.
  - **`/data/desk/free-export.json` is `FreeBudget`'s,** `{startedAt, usedBytes}`, written through `.free-export.json.tmp` with an fsync and a rename, about once a minute while it counts and at shutdown, and read once as `deskd` starts. So a crash forgets up to a minute's count, at most about 260 MB at `bulk`'s top speed. A file that's missing or corrupt starts a new window, as the brief asked, so anything that can delete it can refill the budget. Only uid `desk` can, which is `deskd` itself. It's in the `desk` part, as `desk-data` leaves out only `volume.json` there, so it goes along in an export and a move. That's harmless: it's about 60 bytes of no secret, a rename means a read gets one whole version, and a self-hosted desk isn't metered. Add it to `desk-data`'s `excluded` and `ma-move`'s `swap.go` if it ever matters.
  - **An `export` session's `data.read` is never refused for the bandwidth pause** (Security's `NE-1`, `docs/sub-status/export-move-fixes.md`), past `FreeBudget` included, so a paused member can always export; past the budget its bytes reach the meter as any others do, and the cost guard and the throttle bound them. Before, it was refused past the budget, and `web/src/export/copier.ts`, which retries `unavailable` and then skips the file as "The desk couldn't read it", ended that download "done" with files missing. Only an `owner` session's read is refused now, and the Desk app and `ma-move` read with `export` tokens.
  - **`freeBytesSent` counts a frame once it's queued for desk-rtc,** so a session that ends with frames still queued counts up to about 0.8 MiB that never went. That bills the member less, never more. It's since this process started, like `bytesSent`'s carry, so a restart of deskd starts it from 0, and the meter and `desk-egress` have to take a fall as a restart. The file is the same count with the boot's id, and rtc, which owns `/run/desk`, could change it: deskd never reads it.
  - **12 transfers on the desk, and 8 per session,** each holding a connection to `desk-data` until it ends, as `desk-data.socket` allows 24 (`MaxConnections`), which leaves 12 for calls. A transfer of a session that has ended keeps its place until its thread has closed that connection.
  - **A move keeps the cloud desk's Browser held** (Security's `NE-2`, `API.md` §12, `docs/sub-status/export-move-fixes.md`): `data.browser.keep` turns the calling session's hold into one with no session and no time limit, written to `/data/desk/browser-moved.json` (through `.browser-moved.json.tmp`, synced, renamed, and the directory synced) before it answers, and read once as deskd starts, which holds the Browser again (`BrowserHold.restoreKept`). Only `data.browser.release {kept: true}` from an owner session ends it, removing the file first. A file that's there but unreadable still holds. The file is written and removed under `BrowserHold.keeping`, never under its main lock, so the rtc reader never waits on the disk. While kept, `live` and `warm` get `{reason: "moved", since}` and `/health` says `browser.moved`. `ma-move` never carries the file, and it's in the `desk` part, so an export includes it: about 40 bytes, a date.
  - **Machine parts are refused in deskd too:** `rtc`, `selfhost`, `desk-egress`, `lost+found`, `.ma-export-tmp` and `.ma-move` are dropped from `data.parts.list` and are `not_found` to `data.manifest` and `data.read`, whatever the helper says (`DataMethods.MACHINE_PARTS`). A key must never leave its desk, so that's checked at both ends.
  - **A helper that stalls in the middle of a body holds its transfer** until the reader stops it or its session ends: there's no timer on the body, only on the header (2 min) and on the reader's credit (5 min).
  - **A hold doesn't tell the sessions already `live`** that Chromium has gone, as there's no event for the stream. Their calls get `unavailable` with `reason: chromium` until it ends, and the stream shows the desk without its Browser. The hold is for the last pass of a move, when the owner is at the script.

**To add an RPC method:** call `dispatcher.register` or `registerMutation` in `DataPlaneConfiguration`, and add it to `API.md`'s method table. The gateway URL, its id and the issuer always come from config, which hello's reply carries. deskd sends `GET /v1/agent/config` when hello's reply has none or has no `ageBand`, when `configVersion` changes, and on `notify config`. A read that fails, or leaves the age band unsettled, is tried again with the boot's backoff until one works, which is 1 s up to 30 s, or 60 s after a `403`, `409` or `410`. A config with no `ageBand` never lowers the band or writes its file (`API.md` §10, "How deskd knows the band"). The account's values for spending limits come in it as `agentDefaults` (ADR 0043), so they have no poll of their own, and Platform bumps `configVersion` when they change. When the Platform can't read them, hello leaves the field out and the GET answers `503`; `AccountDefaults` then keeps the last it read, in `/data/desk/account-defaults.json` (temp file, fsync, rename, loaded before `desk-agent` is wired, so it's pushed on connect). A fresh `agentDefaults`, nulls included, replaces it; a corrupt file is ignored with one log line. `desk-agent` audits an `agent.limits.set` with only `timeZone` as `limits.timezone` (`deskd/docs/API.md` §11).

**`rtc.sock` choices the spec leaves open:**
- A peer that overruns its credit loses that session, with reason `credit_violation`. A malformed envelope drops the whole socket.
- deskd grants inbound credit once 64 KiB has drained on a channel (the spec asks for at least 32 KiB). Upload credit stays at 1.5 MiB per session (6 × 256 KiB), inside the spec's 2 MiB cap. Transfer windows must keep it there.
- Close reasons go to `session.close` as they are, and through `SessionObserver` mapped onto the gateway's list.
- `session.state closed` ends nothing: `session.closed` follows it with the reason.
- **A Guild Desk** (task 48, `desk-rtc` from `sub/guild-rtc`): `configure` with `deskKind: "guild"` (from IMDS's `DeskKind`) and `maxSessions` = `maxGuildMembers` × 3; `memberId` (the token's `sub`) on every `session.create`; `member.close {memberId, reason}` on a roster change, answered by each `session.closed` and then `member.closed`; the heartbeat's bytes are per session, from `stats` rows. `desk-rtc` 0.4.0 adds, and `deskd` uses only once `configured` carries `credit` (0.3.x has none): `credit: 65536` in `configure`, held to as each session's send credit; the final counts in `session.closed` and `closed` rows in `stats`, acked with `stats.get {ack}`; and the close reasons `protocol_error` and `over_budget` (gateway hears `closed_by_desk`). `API.md` §15. Contract: `desk-rtc/README.md`, "Guild mode".
- A blocking `RtcClient.send` parks at 64 KiB per message, and at 3 MiB or 4096 messages per channel. The per-channel limit is what stops a client that doesn't read, since it picks the ids: its lane parks, and its credit stops. `offer` has no limit, for callers that bound themselves (events, the last CLOSE).
- A `session.answer` that no session wants leaves no handle behind. One that names another session's handle, or a second handle for a bound session, closes that session.
- More than 4096 control messages waiting means `desk-rtc` has stopped reading, so the socket drops.
- **The clipboard** (`desk-rtc/README.md`, "The clipboard"; `RtcClient` and `RtcClipboard`):
  - **Parts are bytes,** both ways: a set's text goes in parts of 45 KiB as base64, and a get's parts are joined as bytes, up to the `maxBytes` asked for, before anything decodes them. More than that is `too_large`, never a cut piece.
  - **A set's parts go below session data,** as `desk-rtc`'s replies do: after control messages and frames, with one part let through ahead of them for each 256 KiB of frames (`CLIPBOARD_SHARE`), so a paste can't starve. A get and `clipboard.watch` are small, and go as control messages.
  - **One set at a time.** `clipboardSet` refuses a second while one is under way, which is its caller's bug, and an interrupt doesn't cut its wait short: the parts have gone, and the next mustn't go before this one has its answer. So `desk-rtc` never has more than one set of `deskd`'s waiting.
  - **Late replies are dropped:** one for an id nobody waits for any more, a second for the same id, or one with no id `deskd` could have sent (an integer from 0 to 2^53 − 1). None of them touches the link.
  - **deskd's own waits** are 12 s for a set and 25 s for a get (`BrowserClipboard.Timing`), past the 10 s and 20 s `desk-rtc` can take to answer by itself. A wait that runs out with no clipboard message at all heard on that connection since the request went marks the connection silent, as a `desk-rtc` before the clipboard ignores these: from then on calls fail at once with `no_reply`, until any clipboard message comes, or a new connection does.
  - **`clipboard.watch`** goes after `configure` on every connection while it's wanted, since a new one starts with it off, and on any change of what's wanted. It's wanted while any attached session is subscribed to `browser.clipboard`, which `SessionEvents` tells the topic of outside its lock, and the topic settles on a thread of its own.
  - Nothing logs text, a `data` field, a part's number or how many there were, as together they'd give the length.

**Choices the contracts leave open:**
- Heartbeat `seq` is the clock's whole seconds, or the last `seq` + 1 if that's higher. Platform ignores a `seq` it has passed and resets it only on a new `bootId`, so a counter from 1 would have every heartbeat ignored after a restart of deskd.
- `agent.status` comes from deskd's own subscription to desk-agent's `agent.state`: `busy` while an agent is `working`, with `busyUntil` 10 min ahead and `activeTasks` the number working, `error` if one is in error, `online` otherwise, and `offline` while desk-agent can't be reached. `lastActivityAt` is the last `agent.state` with an agent working or the first without, and `lastLlmCallAt` the end of the last run, as a run is one call in Phase 1. A change of status asks for an extra heartbeat. `badges` is still all zero: the Agent app's unseen counts would go there once it has a layout `appId`.
- Extra heartbeats keep 16 s apart, for a margin on Platform's clock, a `notify heartbeat` included. The exception is the first to say `readyToStop` for a stop, which `agent.md` exempts: it goes straight after the reply that first carried `prepare_stop`. If it fails or is refused it goes again at the spacing, or when `Retry-After` allows, as `stopAt` can be only 60 s away.
- The last heartbeat, on SIGTERM, is exempt too after a `prepare_stop`. On a plain restart it can get a 429 if the previous was under 15 s ago. That's accepted, as it's best effort.
- A restart within 15 s of the last process's `final` heartbeat always gets a 429 on its first heartbeat. A refused heartbeat goes again when `Retry-After` allows, not a period later, so that gap is 15 s.
- **A heartbeat that fails any other way** (a 5xx, a timeout, no network, a 429 with no `Retry-After`) goes again at the spacing (16 s), then 32 s, 64 s, held to the period, each plus a random 0 to 25 %, and back to the period after one is accepted (audit D3). A whole period after each blip put two blips near `agent.md`'s 5-minute unhealthy mark.
- **A reply's `nextHeartbeatSeconds` is held to 2 minutes** (`HeartbeatLoop.Timing.MAX_PERIOD`; audit D7), and never under the spacing. The Platform sends 60; 2 minutes keeps a lost heartbeat and its retry inside the 5-minute mark and the reply's revocations, the backstop, within 2 minutes. **Every `Retry-After`** from the Platform or the gateway is held to 5 minutes (`PlatformHttp.MAX_RETRY_AFTER`), so no answer can park boot or the heartbeat for long.
- **`health.checks.dataVolume` is `failing` under 64 MiB usable** (`DataVolume.LOW_SPACE_BYTES`, statvfs's `f_bavail`, one call a heartbeat; audit D5), as well as when the directory can't be written by its mode, which a full disk still passes. Below 64 MiB the desk's own small writes (deskd's state files, desk-notebook's and desk-agent's SQLite journals, Chromium's profile) can fail at any moment. The Files floor (2 GiB) is what an upload may take, not health. `/health`'s own check still writes a file, and still fails only if that fails, so a full disk can't roll a release back.
- **`health.checks.notebook`** is desk-notebook's storage state, from its health frame (main `6216d1e8`): `ok`, `degraded` while its writes fail and edits wait in memory (`health.status` `degraded`), or `failing` once it refuses edits (`refusing`, status `failing`). Absent when desk-notebook isn't there, didn't answer within a second, or doesn't say. `NotebookStorage` reads it on a short connection of its own with no hello, as `docker/health` does, at most every 10 s, and the heartbeat waits a second at most; only the state and counts are kept. `agent.md`'s `health.checks` is an open map, and the Platform reads only `chromium`, so nothing breaks there.
- The log has one line for the first accepted heartbeat, and another only after a failure.
- Hello's reason is `boot` on the first hello of a process, even after a restart within one boot (the contract's `restart`). Platform goes by `bootId`, and telling them apart needs a file. `formattedThisBoot` is false, as firstboot doesn't report it yet.
- `health.checks.chromium` is `older_than_profile` from a refused start of Chromium until a start works, and absent otherwise, with `health.status` `degraded`, which a volume that can't be written still beats. It never says `ok`, though `agent.md`'s example does: Chromium starts on demand, so `deskd` doesn't know that. It waits for the next heartbeat rather than bringing one forward, and outlives a restart of `deskd` (Browser choices). `HeartbeatLoop` gets it as a `BooleanSupplier` from the configuration, so `platform` doesn't depend on `browser`.
- A heartbeat's `dataVolume` also has `volumeId` and `formattedAt` from `volume.json`, and hello's doesn't. No file means neither key, as on images before 0.2.3. `formattedAt` is a JSON null on a volume older than the record. With a record and no usage it's just those two, and with neither it's still null. `image` and `firstSeenAt` stay on the desk. Contract 0.3.8 (`ma-platform` `d1921fb`) lists both in `agent.md`, with `health.checks.chromium`. Platform's handler keeps them with the reading (`dataVolumeReading` in `services/desks/src/agent.ts`), only when the byte counts make sense, so a record sent with no usage isn't kept, and only a `volumeId` of `vol-` and 8 to 17 hex digits or `unknown`, and a `formattedAt` of null or a time of at most 40 chars. The cost guard mails `data_formatted` or `data_volume_changed` when they change, and `chromium_refused` while the check is there (`services/cost-guard/src/run.ts`). The handler drops its refused flag on any heartbeat without the check, which is why the refusal outlives a restart of `deskd`.
- `volume.json` belongs to uid `desk`, so `DataVolume` believes nothing of it. A regular file only, no symlink followed, 4 KiB at most, parsed with `Json`. `volumeId` is `vol-` and 1 to 32 hex digits, or exactly `unknown`, and `formattedAt` is null or an `Instant`, sent as `Instant`'s own text. Anything else is one log line with none of its content, and neither key. It's read on the first heartbeat and kept, as `desk-datadirs` rewrites it only at boot, so it's not on the way to `deskd` starting. The training writes one and fails if its first heartbeat doesn't carry it.
- A hello refused with 403, 409 or 410 from Platform (not API Gateway) retries every 60 s; other failures back off 1 s to 30 s. Every wait of the boot thread (IMDS, hello, the config's retry) is the step or the `Retry-After`, plus a random 0 to 50 %, never sooner (audit D3).
- **desk-rtc gets 30 s to be configured before the first hello** (`BootSequence.Timing.rtcWait`; audit D4). Then hello goes with the identity desk-rtc reported on an earlier boot, kept in `/data/desk/rtc-identity.json` at each `configured` that changes it (desk-rtc keeps its identity in `/data/rtc`, so it's almost always the same), and the gateway link and the heartbeat follow, with `health.checks.rtc: failing`. `RtcClient` keeps reconnecting; sessions get `desk_not_ready` until it's configured; if it then reports another identity, hello goes again with `cert_rotated`. With no kept identity (a desk's first boot, or a junk file) boot waits for desk-rtc as before, since hello needs one or two real fingerprints and there's nothing else honest to send.
- A link told not to reconnect (upgrade 403 or 410, close 4403 or 4409, `connection_replaced`) asks for a hello after 5 min, so it can't stay stuck. Hello is what lifts the block.
- **The gateway link's waits** (audit D1, D2): a link that never came up retries at 1 s doubling to 30 s, each ±20 %. Rate-limited (an upgrade's 429, or close 4429) it waits 30 s or the handshake's `Retry-After` if longer (held to 5 minutes), plus a random 0 to 100 % of that, so limited desks don't all come back at +30 s to be limited again. After a link that was up 30 s past ready drops, the first retry waits a random 0 to 5 s (`Timing.healthyDropSpread`), as a gateway deploy drops every desk in the same second.
- A `ping` or `ready` with no reply in 30 s means the connection is dead. Without this, a black-holed connection would look fine until TCP gave up.
- Messages for the gateway aren't kept across a reconnect. `ready` lists what's live, and the gateway settles the difference.
- A user revocation applies to tokens with `iat` up to the moment it arrived, and for 15 min, so signing in again works.
- SIGTERM closes with 4503 and `desk_stopping` only if a heartbeat response has carried `prepare_stop` since this process started. Otherwise it's CLOSE 4002 `deskd_restarting`, and `closed_by_desk` to the gateway, which doesn't list `deskd_restarting`. This was agreed with the UI/UX Engineer. `internal` moved to 4003 to make room.
- A gateway `session.close` with `client_gone` or `closed_by_client` keeps resume state for 2 min, because the web client ends a session whose ICE restart failed with the second one. CLOSE on `ctl` doesn't keep it.
- The jti is claimed after the slot checks, so a token turned away from a full desk can try again.
- Not built, on purpose: support scope, step-up, resume from hibernation, LLM usage, `badges` pushes, guild peer sessions (the old desk-to-desk model; a guild desk's members are client sessions, `API.md` §15).
- **`export` tokens** (task 32): the same checks as `owner`, `sub` the owner included, and a grant with no video and no input. The scope gate is in `RpcSession`, from what each method registered, so a new method is the owner's alone until it says otherwise, and an `export` session gets `forbidden`, `reason: scope`, for anything else, a method that doesn't exist and every SUB included. It comes before `idem` is looked at, and isn't stored.
- `media.freeBytesSent` is always there when `media` is, and 0 until an `export` session's transfer has sent something free. `media` itself is still null until desk-rtc's first `stats`.

**Agent relay choices** (`agent/`, `API.md` §11, `services/desk-agent/docs/proposals.md` §5 and §8):
- **One desk-agent subscription per topic,** held while any attached session is subscribed (`Topic.subscribersChanged`, settled on a thread of its own) and published to the hub, which numbers events per client. The first client's snapshot is that subscription's own first event. A later client's is a one-off subscription, so a `delta` published while it's taken can repeat text in it until the reply's last `message`.
- **Both topics are coalescible with no `since`:** a desk-agent snapshot is the whole state, a streaming reply's text included.
- **A drop of the link** fails every call in flight with `unavailable` and leaves clients' subscriptions quiet. On reconnect, each topic with a subscriber is subscribed again and its first event published as a `snapshot`. A SUB while it's down gets `NO_SNAPSHOT` until then. Reconnect backs off from 250 ms to 5 s, and logs once while waiting. The backoff starts again only after a connection that lasted 10 s (`Timing.healthyAfter`; audit D7), so a desk-agent that accepts and drops at once is tried with the backoff, not four times a second.
- **`AgentLink` is built as `NotebookLink` is** (Notebook relay choices, below), for the same two defects, which it had (`docs/sub-status/agent-review-fixes.md`). Socket I/O is on the connection's own link thread, writer and watcher, which nothing interrupts, so a client's CANCEL, a deadline or a session's end only ever reaches its own wait, never the one connection every session shares. A call queues and waits for its answer, with no lock held across I/O. A write with no progress for 5 s (`Timing.writeStall`) closes the connection, which fails what's waiting with `unavailable`, and it reconnects. `close()` waits for nothing.
- **16 calls per session wait on desk-agent at once** (`MAX_SESSION_CALLS`), half of `RpcSession`'s 32, and more are refused at once with `unavailable`, so a desk-agent that has stalled never gets the session's Browser calls `rate_limited`. Frames waiting to be written are held to 4 MiB, one frame always fitting an empty queue, with 64 KiB more for cancels and subscriptions. deskd's own pushes count against no session.
- **Events made to fit an EVT** (`EventFit`): a long `delta` is split in order, a snapshot keeps its newest messages, says how many it `omitted` and sets `older: true`, and a long `message` keeps the start of its text with `truncated: true`. desk-agent's snapshot is already `agent.thread.get`'s newest page, at most about 960 KiB of JSON, with its own `older`. An older desk-agent sends `error` with `too_large` for a long thread's snapshot and keeps the subscription, so for a conversation that starts the topic as `{messages: [], older: true}`, not as an agent that doesn't exist.
- **`agent.key.add`:** the secret is checked and taken out of the params before anything goes to desk-agent, sent in a KEY frame with the desk's id, and its bytes zeroed after. It arrived as a JSON `String`, which can't be zeroed (ADR 0040). `IdempotencyStore` keeps results only, so no copy of the request stays.
- **No desk-agent, nothing changed:** a mutation checks the link is connected before it's queued, so with no desk-agent it's `unavailable`, `reason: unavailable`, with no `mayHaveApplied`, and the key stays free (task 33 item 2; it used to say the write may have applied). `beginEffect` runs on the link's writer, right before the request's bytes go (`AgentLink.Gate`), so one that never left the queue has no flag either, and one whose bytes began to go has it unless an answer comes.
- **Waits:** 30 s for `agent.key.add` and `agent.key.models`, which call the provider, and 10 s for the rest. A wait that ends sends desk-agent `cancel`, as does a client's CANCEL or a deadline.
- **Not in the AppCDS training:** the training points `deskd.agent.socket` into its temporary directory, where nothing listens, so the relay's classes load at its first use on a desk. `ModelPrices` starts there and sleeps its jitter, so its fetch's classes load at its first fetch, in the background, which isn't on any member's path.
- **Prices and the account's values** (ADR 0043, `services/desk-agent/docs/proposals.md` §5): `AgentPushes` sends `desk.prices.set` and `desk.account.set` on one virtual thread, on every connection and on a change, the latest only, as a call waits for its answer and the link's listener mustn't block. They're plain `req`s: both sides drop the link on an unknown `t`, and an older desk-agent answers `not_found` to an unknown method, so deskd stops until the next connection. No answer holds it 5 s, unless a new connection comes first. `AgentMethods` is an allow-list, so no client can send them.
- **A removed guild member's purge** (ADR 0080's addendum of 2026-11-10): `AgentPurges` sends `desk.member.purge {memberId}` the same way, with no caller, one at a time, from `GuildPurges`' list on `/data/desk`, on every connection until desk-agent answers; an error waits 5 s, doubling to 5 minutes, and `not_found` (an older desk-agent) waits for the next connection. desk-agent refuses it from any frame with a caller.
- **`ModelPrices`:** its own virtual thread, the file first, then the first fetch up to 2 min later, then about every 6 hours, with `If-None-Match`, backing off from 1 min to 6 hours on a failure, and one log line per run of failures. A 404 is normal and quiet. It keeps a table only if desk-agent could use it (`ModelPrices.valid`): at most 1 MiB, JSON, `version` 1, a non-empty `models` of objects with `input` and `output`, every price a plain decimal string in whole micro-dollars up to desk-agent's $100,000 a million, a long prompt's `above` with its `inputTokens`, and at least one model priced other than 0 in and 0 out. It used to keep tables desk-agent's `Pricing.parse` refused, and stayed on them. An ETag is kept only after a save, so a save that failed is tried again. It logs no body.

**Notebook relay choices** (`notebook/`, `API.md` §13). `AgentLink` has since been rebuilt the same way, for the same two defects:
- **Socket I/O stays on threads no caller can touch.** Each connection has a link thread that connects and reads, a writer on a queue, and a watcher, all virtual, and none is ever interrupted. An interrupt on a thread doing channel I/O closes the channel for everyone on it, so a caller's cancel or deadline only ever reaches its own wait.
- **No caller waits for a write.** A call queues and waits for its answer, in a wait with a timeout from the start, and takes no lock across I/O. A write with no progress for 5 s closes that connection, and only that one, which is what fails what's waiting. `close()` waits for nothing: closing a `SocketChannel` in blocking mode wakes who's parked on it.
- **16 calls per session go to `desk-notebook` at once** (`MAX_CALLS`), half of `RpcSession`'s 32, and the rest are refused at once with `unavailable`, `reason: notebook`. So calls stuck on a service that accepts and doesn't answer can't take every slot and get the Browser's calls `rate_limited`, which they would otherwise: 10 s at more than 3 a second. This also answers mutations with no `mayHaveApplied`.
- **The queue is bounded by what can be in it.** At most 16 calls, each refused past 1 MiB and 64 KiB of JSON waiting; cancels and subscriptions, which may go 64 KiB past that; and one collab message, since `CollabChannel` runs on a serial lane and `collab()` returns once its message is written or dropped. That's also what stops the client's credit when the service is slow.
- **`beginEffect` runs on the writer, right before a call's bytes go,** with `requireOwner`. So a mutation that never left the queue has no flag and its key stays free, whatever it was waiting behind, and one whose bytes have begun to go has it unless an answer comes. It's thread-safe by design, and `RpcContext`'s Javadoc says so.
- **Reads and writes are at most 64 KiB at a time,** whatever the frame's length. The JDK copies a heap buffer to a temporary native one per call, sized to what's left, so a 4 MiB read or write would take 4 MiB of `MaxDirectMemorySize` per carrier thread, and copy it all again on each partial write.
- **A collab message costs one array in each direction.** Toward the service, the frame's header goes first and the lane's own array is the body. Toward the client, `CollabOut` holds it and `Frame.fragments` encodes frames one at a time, which `Session.send` now does for every message, and a message isn't read off the socket until there's room: 4 MiB and 64 KiB may wait, or one whole message of any size up to 4 MiB. Every DATA has `id` 0, one after another whole, so they're one message to `RtcClient`, whose 64 KiB per message parks the sender.
- **What `desk-notebook` may send is limited by what it could become.** A collab message over DATA's 4 MiB, a JSON frame over RES's 1 MiB and 64 KiB, and any frame over the contract's 4 MiB and 64 KiB drop the link with nothing read or allocated, and `reset` follows. The narrower JSON limit is a choice: parsing a frame of 4 MiB could take 4 of bytes, 8 of text and 8 of Jackson's buffers, per session, for a reply that could only be `too_large`. An `err`'s details over 32 KiB become `internal`, so an ERR stays under 64 KiB.
- **A client that leaves `collab` unread stops the link's reader once `CollabOut` is full, and for 30 s at most.** Then the link goes, which frees `desk-notebook`'s buffers for it. Until then, that session's `res` wait too, on the one socket, and nothing else does.
- **`wants` means a subscription, or something queued.** Connected, a link stays up until its session ends, as the contract says. Dropped, it tries again with backoff (250 ms to 5 s) only for a subscribed client, and otherwise at its next use. The backoff starts again only after a connection that lasted 10 s (`Timing.healthyAfter`; audit D7): one that accepted and dropped at once doubles it. Anything queued gets a try within 250 ms, however far the backoff has gone, and fails if that fails: so a call during an outage gets `unavailable` within 250 ms.
- **`reset` goes after whatever was on its way to the client from that connection, and once,** to a session that has sent DATA since the last. DATA that arrives while it's down joins the queue like a call, so it either goes on the next connection or is dropped with a `reset`.
- **The topic is per link and published to all.** Each subscribed session's link holds its own `sub`, as the contract has it, and `{rev}` is the same for the one desk, so what one link hears goes to the hub, and the same thing from another link is dropped. The last one, opaque here, answers a later SUB and a client that fell behind, while a link is live and subscribed to keep it current. `snapshot` has no session to ask for, so this is what makes that work. Which sessions want it comes from `Session.isSubscribed`, read on a thread of its own after `Topic.subscribersChanged`.
- **A mutation that went out isn't sent `cancel`,** as `API.md` §4 says nothing stops it. A read is, and so is a mutation whose 10 s wait ran out.
- **The training drives it,** with a stand-in on a temporary socket (`TrainingNotebook`): a tree, a write, the topic and a collab message, so Notebook's first use loads from the archive. It sets `deskd.notebook.socket`, so `/run/desk-notebook` is never touched.

**Browser choices the contracts leave open** (`desk-runtime.md` section 8, ADR 0041):
- **`warm` to `live` with both units known to be up sends `session.video` first,** and the `start`s follow. Each `start` is a Python process and `systemctl`, and B13 gives that switch 300 ms. 8.4's order holds whenever a unit isn't known to be up. A `start` is still sent, since that's what brings back a unit that stopped by itself.
- **A request waits for steps that began after it came,** so a repeat `live` does run the `start`s again.
- **While `desk-browser` is being started, and for 30 s after, the CDP connector tries every 250 ms** rather than backing off to 5 s. `systemctl` says the unit has started once the process has, and Chromium listens some seconds later. Backing off from what it refused meanwhile made a `browser.tabs` subscriber wait up to 5 s for a browser that was there, which was deskd's own part of a first Browser use. A client's `live` isn't held up by this either way: its reply and `session.video` don't wait for CDP. A start straight after a refusal skips the hurry before it, as it will likely be refused again, and one that works still gets the hurry after it. A desk's first refusal can't be known beforehand, so it does cost those 30 s, about 120 reads of `/proc/net/tcp` if something still wants the connection. Taking that back would need another callback through `BrowserModule`, `BrowserTabs` and `CdpClient`, which isn't worth it.
- **`/run/desk/idle.json` (`idle/IdleFile`, `desk-runtime.md` §6.1)** tells `desk-batch` (root, outside the container) when the desk is idle, so Debian's updates and service batches apply then and not only every 72 hours. Whole file through `.idle.json.tmp` (made new, nothing followed), `0644`, renamed over, at least every 15 s and at each change; one virtual thread waits on a condition for either, so a quiet desk costs a small write every 15 s. Nothing is derived again; each count is read from where `deskd` already has it:
  - `sessions` is `SessionManager.connectedCount` (the heartbeat's `clients.connected`). **A Files transfer always has an open session, so it counts there** and not in `exports`.
  - `agentTasks` is `AgentModule.activeTasks` (the heartbeat's `agent.activeTasks`).
  - `exports` is `DataModule.exportsGoing`: live `data.read` transfers of `export` sessions plus sessions holding the Browser for a copy. A hold a move kept past its session isn't counted, as it lasts until the owner lets go and would stop every update.
  - `downloads` is always 0: only `desk-units` sees a Browser download, at a freeze (ADR 0045), and the contract has downloads hold a Chromium close or a root swap, not a service batch.
  - `idleStopSeconds` is the config's `autoStop.autoStopMinutes` times 60 (`PlatformConfig.autoStopMinutes`), null for never-stop, a self-hosted desk, an unparsable value or before the first config. `lastInputAt` is the heartbeat's `clients.lastInputAt`.
  - `idleSince` is in memory: the first look with `sessions`, `agentTasks` and `exports` all 0, null while any isn't, so a restart of `deskd` starts it fresh. A poke (a session ending or connecting, an Agent status change, an export beginning or ending) later than `idleSince` moves it to that moment, so a session that opens and closes between two looks still restarts the clock. An Agent run count that changes with no change of status (2 runs to 1) isn't a poke; the 15 s write shows it.
  - The file is removed as `deskd` stops. A failed write is one log line, and the old file goes stale, which `desk-batch` reads as not idle. Tested here for the fields, the rename, the mode and the 15 s rewrite; uid 1100 owning it is the container's user, not tested.
- **A refused start of Chromium (ADR 0035) is recognized in one place,** `UnitException.browserRefused`: unit `desk-browser`, code `failed`, text starting `start desk-browser:` and holding `REFUSING TO START`. `BrowserStream` remembers it under its lock from a refused start until a start works. A timeout, a lost socket or any other failure in between leaves it. A stop of `desk-browser` can't set it, and none goes out while it stands. It's also an empty file, `chromium-refused` beside `units.sock`, so it outlives a restart of `deskd` and not a reboot: Platform drops its flag on any heartbeat without the check, so a `deskd` that forgot would read as a fix. The worker writes and removes it after each change, outside the lock, and nothing follows a link at that name (`RefusalMarker`). Only `live` can meet one, as `warm` doesn't start Chromium. Only fixed strings go out: `reason: chromium_older_than_profile` to a client, `older_than_profile` to `/health` and the heartbeat. The text stays in the log. It doesn't fail `/health`, as `ma-update` judges a rollout on that and restarting `deskd` wouldn't help.
- **After a refusal, what `deskd` does by itself is bounded, and a client's request always tries.** Each try is a Python process, `setpriv` and a `crit` line in the journal. The worker can't spin by itself, as each step uses up what asked for it. What could ask again and again is a connection to the port that opens and drops, each bringing a start from `browserLost`, and each start kept the connector at its smallest gap, so about 4 a second, with no end. That takes something answering as uid 1102 while the check refuses, so a hung Chromium or another `kiosk` process. So while refused, a loss asks for a start only if the last start of `desk-browser` was at least `restartEvery` (5 min) ago. Never asking would let a refusal that has since gone, after a fix or from an earlier `deskd`, keep a viewer from the Chromium that's there. A Chromium off its port isn't restarted while refused, as the stop would take away a browser that works, and a restart asked for while a start is on its way is dropped if that start is refused. A client's request goes through each time, as it's how a fix is found.
- **A hold** (`data.browser.hold`, `BrowserStream.hold`) is a stop of `desk-browser` through the worker like any step, so it comes after the step under way, and then no start of `desk-browser` goes out until the release: not one a request asks for, not a lost Chromium's, and not a displaced one's restart. `live` and `warm` are refused with `reason: held` before anything changes, and those still waiting are failed and left `off`, as a failed request is. What sessions had settled on stays wanted, so the release starts `desk-browser` again for whoever wants `live`, and also when Chromium was up as the hold's stop came (started by this deskd and not lost since, or its uid on the port by `CdpListener`, which the worker reads just before the stop), with nobody viewing: a move's last pass mustn't leave the cloud desk's Browser stopped (found by the rehearsal, `tools/desk-move/rehearsal/`). `BrowserHold` in `data/` says who holds it and until when. `/health` adds `browser.held` while it's held.
- **The bandwidth pause** (`ma-platform` ADR 0095, contract `bandwidth.md`; task 33 item 1). `platform/StreamingPause` takes `streaming` from every heartbeat reply and every config, hello's included, so it's known before a session can come: `streamProfile: "paused"` until `resumesAt`, when it ends by itself with no new reply, and anything else, a reply with no `streaming` included, is no pause. While it's on, `BrowserStream` refuses `live` under its lock before anything changes (`unavailable`, `reason: bandwidth_limit`, `resumesAt`), and as it begins, every session wanting `live` has its video cut at once and is left `off`, and a `live` still waiting fails the same way. desk-stream stops once nobody wants `warm`. No stop of `desk-browser` goes out for it, so Chromium and `/data/browser/profile` are left alone (ADR 0035), and `warm`, input, the tabs, the clipboard, Notebook, Chat, Agent and the heartbeat's count go on. A pause with no `resumesAt` lasts until a reply says otherwise. It's in memory only: a restart of `deskd` learns it again from hello's config. `/health` adds `browser.bandwidthPaused`. Clients aren't told when it begins, as there's no event for the stream; the Desk app pauses itself from the meter (ADR 0051). `DataMethods` reads the same pause: a new `data.read` from an `owner` session gets the same refusal, and an `export` session's never does, past `FreeBudget` too (`NE-1`, `API.md` §12).
- **An `off` with nothing to stop asks nothing of `units.sock`.** deskd counts on being the only one starting `desk-stream`.
- **A failed `live` or `warm` leaves its session `off`.** A failed `start` doesn't touch other sessions, which didn't ask for anything just now.
- **The stop after a deskd restart:** if `stream.state` reports a stream before this process has started one and nobody wants it, deskd stops it. A `down` doesn't settle that, as a leftover may still be connecting. That's the only use of `stream.state`. Everything else is informational, as is `stats.stream`.
- **Requests carry an arrival number** (`RpcContext.arrival`), as calls run on their own threads and two can reach a handler out of order.
- **A viewer losing Chromium starts it again,** after a refusal at most once per `restartEvery`. `Restart=on-failure` doesn't cover a clean exit, which is what closing the last tab on the keyboard is. The RPC opens a new tab first for the same reason.
- **Permissions:** `browser.tab.list` and the topic need the token's video, and everything that drives the Browser needs its input, so neither can get around the other. Only `owner` tokens exist today, and they have both. They're read live: a refresh that narrows stops calls short of Chromium, ends `browser.tabs` if video went, and reaches desk-rtc even if `session.create` was out.
- **The active tab is the one on screen,** which `/json/list`'s order alone can't say: a tab opened in the background comes first while hidden. So when that order doesn't settle it, tabs are asked for `document.visibilityState`, in an isolated world a page can't touch, 1 s per tab and 3 s per read. With the last active tab first in the list, nothing is asked. Internal pages are never asked or attached to. A call with no `tabId` fails closed if this can't be told (`BrowserTabs`' Javadoc has the reasoning).
- **Titles and URLs come from `Target.*`, and `/json/list` gives only its order.** Chromium escapes titles for HTML in that list and only there, which `ChromiumIT` pins and `FakeCdp` models. A read asks `Target.getTargets` (`CdpClient.ask`) while the list is being read, so with both stuck it costs what a stuck list always did. The reply is taken on the read path, in the order Chromium sent things, so it can't land on an event that came after it. No reply in time keeps the last titles and leaves the connection alone, unlike any other command for the browser itself: the probe is what says Chromium has gone. A tab comes or goes only by events, never by a read, with two exceptions that are replies. A new connection's first `Target.getTargets` brings the tabs already there, and `Target.createTarget`'s reply brings one just opened. Both are taken on the read path too (`CdpClient.call` with `onReply`), so neither can bring back a tab whose end came right after it. Unlike a list's body, which is cut off at the limit, this reply can't be stopped once it's coming, and everything else on the socket waits behind it: a page with a 2 MB URL, as `ChromiumIT`'s hostile page has, took 135 to 410 ms a read here at load 5 to 8, against the probe's 5 s.
- **`browser.tabs` serves no `since`:** it publishes only while someone is subscribed, so a SUB always gets a snapshot, and that's what wakes it after a resume.
- **The point of no return is just before a command goes to Chromium** (`RpcContext.beginEffect`). Before it, a cancel, a deadline or the session's end stops the call. After it, the call finishes and its result waits for a retry. Only attaching, reading a tab's history and asking whether a tab is on screen go out before it, and none of them changes what the member has.
- **`CdpException.Kind.TIMEOUT` means the command went out and got no reply,** and that's all `browser.tab.navigate` takes for a slow page. No session in time, or too many commands out, is `NOT_SENT`. `Timing.sessionWait` equals `request` in production, and it's separate so a test can make certain which of those two timers ends first.
- **Tab ids are Chromium's target ids.** So they survive a deskd restart, and a client's id is only ever looked up in the model, never passed through.
- **A wrong listener on the debugging port** gets no request at all. One line says so with its uid, once until a trusted listener has been seen. `/health` has `cdp: refused` and `listenerUid`, and calls get `unavailable`, with the same `chromium` reason as Chromium being down: a client can't do anything different about it.
- **Chromium off its port gets restarted.** With only uid 1102 on `::1`, nothing else would move it, since a `start` of a running unit does nothing and no connection was lost. So deskd sends `stop desk-browser` and `start desk-browser`, one after the other through the stream's worker, whoever wants what. Chromium saves its session on the stop, so the tabs come back, reloaded, which is why it's at most once per 5 min (`restartEvery`), never while a start is known to be refused, and why it waits while someone else holds the port, when it would only land on `::1` again. It takes a look at the port to notice, so an idle desk doesn't.
- **The clipboard** (`BrowserClipboard`, `API.md` §10). What the spec leaves open:
  - **Who:** owner tokens only. The method table turns any other scope away first, with `reason: scope`, and the clipboard checks `scope` again behind it. A write needs input, and a read and the topic need video and input. Read live: at the call, again once a write's turn comes, and again before a read's text goes out, so a refresh that narrows stops both. A page can't reach these: there's no way to them but a session's `rpc` channel.
  - **Writes take turns,** in the order they came, desk-wide, on a fair lock, and at most 4 wait or run at once (`MAX_WRITES`). The fifth gets `rate_limited` with `limit: clipboard`. Each holds its request until it's done, which is what that bounds. A write's text becomes bytes only once its turn comes.
  - **Reads share.** One that comes while another is waiting its turn takes that one's answer, read after both came, so there's one get out and one waiting however many sessions ask. A round is cleaned once, and each caller's token decides whether it gets it.
  - **The cap twice on a read:** `maxBytes` is 1,000,000, so more than that on the desk is `too_large`, and the text once cleaned is held to it again, as each bad byte becomes U+FFFD's 3. A reply that wouldn't fit a RES as JSON is refused by counting first (`ClipboardText.replyJsonBytes`, checked against the JSON writer for every character), so the 6 MB a million control characters would take is never built.
  - **Codes:** a set's every failure is `display`, as the paste key mustn't follow. A get's `timeout` and `internal` are `clipboard`, its `too_large` is `too_large`, and the rest `display`.
  - **The topic** has no state: `NO_SNAPSHOT`, so no first event, and a `changed` lost to a client falling behind stays lost, as API.md says. Events are coalesced to one per 250 ms, the first at once and the last always, on top of `desk-rtc`'s own 4 a second.
- **A teen's filtered sites** (`FilteredSites`, `API.md` §10). What the brief left open:
  - **The error code comes from the page,** read in an isolated world from Chromium's `.error-code` element, as no CDP event carries it and `Network.enable` would add an event for every request of every page. Only a code that comes after a name was resolved lets the host go to the resolver, so a page blocked by policy, a bad scheme or the like never sends it.
  - **The write is `document.open/write/close` in that same world,** not `Page.setDocumentContent`. Both work on an error page (checked on Chromium 156), but the method takes a frame, so a page that committed in the meantime would be written over. The world goes with its document, so the write fails instead. deskd also checks that it has heard of no other commit before each step.
  - **Chromium's auto-reload of an error page** (about 1, 6 and 36 s in) fails for a filtered site and commits nothing, so our page stays: watched for 44 s on Chromium 156.
  - **Only the A record is asked, and AAAA only when A has no address,** in one 2 s budget. Every address in the answer has to be unspecified, so one real address means a real site. Cloudflare's extended error (16 Censored, 17 Filtered) isn't read.
  - **No cache.** A reload asks again. At most 4 at once (`MAX_LOOKUPS`), on their own threads, and past that Chromium's page stays.
- **Limits:** 256 page targets, `url` 2048 chars and `title` 256 in the model, any string in a CDP message 4096 before parsing, a CDP message 2 MiB chars, 256 commands out. The list fits one event by cutting further.

## Footprint rules
Memory, CPU and wake time are explicit requirements, measured on c7g.large, where the browser stream already uses 69–76% of the CPU.
- No Netty, Tomcat, JPA, AWS SDK or reflection-heavy libraries. Add a dependency only when the job needs it, and check what it pulls in.
- `@SpringBootConfiguration` plus an explicit `@Import` list and `@Bean` methods: no component scanning, and auto-configuration only where it's really needed. Use `proxyBeanMethods = false`.
- Virtual threads by default, so use `ReentrantLock`, not `synchronized`, around anything that blocks (it pins the carrier in Java 21). SQLite is JNI and also pins, so it gets dedicated platform threads.
- Never publish, or call anything that takes another lock, while holding a lock that code under that other lock also takes. Take what's needed, let go, then publish. `desk-agent`'s `Deltas` did, and a reply froze when the Agent window opened (`docs/sub-status/agent-deadlock-fix.md`).
- An idle session holds no thread. Each channel starts a virtual thread only while it has frames, and each call has its own. Timers are one-shot parked virtual threads.
- The rtc reader must never block, since it serves every session. Listener callbacks only queue work.
- `spring.threads.virtual.enabled` is only read by auto-configuration, and none is imported yet. Explicit executors must use virtual threads themselves.
- One `HttpClient`, built on first use by the boot thread, because building it loads TLS and the CA list. A trimmed JRE needs `java.net.http` and `jdk.crypto.ec`.
- Every HTTP request goes through `PlatformHttp.send`, never `client().send`. On JDK 21 `HttpRequest.timeout` stops at the response headers, so a stalled body would block for ever.
- Nimbus is only for the JWS and the signature. Claims go through `Json`, which rejects repeated keys.
- No periodic timers beyond the ones the contracts require. The idempotency store, rate limits and rings purge as they're used. No lazy init, which would move the cost onto the first user call.
- No dev mode, dev authorizer or TCP listener: other users on the desk could reach a loopback port. There is one auth path. Only endpoints vary by environment, through variables in `deskd.env` (IMDS base URL, API base, JWKS URL).
- Never log tokens, keys, signatures or message payloads.

## Release rules
- The Dockerfile uses no BuildKit-only syntax, since a desk's Docker may have no buildx, and `build-image.sh` builds with `--network host`, since a desk's Docker has no NAT for a bridge.
- The AppCDS training run drops `jvm.options`' `SharedArchiveFile` line, because the JVM refuses `SharedArchiveFile` and `ArchiveClassesAtExit` naming one file. A second run with `-Xshare:on` fails the build if the archive doesn't map. At runtime, `-Xshare:auto` just starts without a missing or stale archive, in silence.
- The training is the real deskd, wired by the real configuration, from boot through a real token, a session, the Browser and the clipboard (`training/CdsTraining`). Its stand-ins are IMDS, API and gateway on loopback, TLS 1.2 and 1.3 with a throwaway CA and a throwaway ES256 key made on the spot, and `desk-rtc`, `desk-units` and Chromium's debugging port on temporary sockets and loopback. It needs no external network, `/data`, `/run/desk` or secrets, and it deletes the one temporary directory it writes. A step that doesn't go as on a desk exits non-zero and fails the build, rather than archiving less in silence. `CdsTrainingIT` runs it from the jar in `verify`, so a change on that path that the stand-ins don't follow fails here, not on the arm64 box. So a new step on the path from boot to first use belongs in `CdsTraining` too.
- **The training can't affect a real run.** It's reached only by the JVM system property `ma.cds.train` on the training's own command line. That's not a setting: `deskd.env` and the Environment have no way to it, and `test-release-scripts.sh` checks that nothing a desk runs names it. Set anyway, it means nothing where `/run/desk` exists. Everything it configures is a system property, which outranks the environment, so nothing around it can point it off loopback. And what's kept is class metadata: a dynamic archive holds no heap, so no value from the run can be in it.
- CDS holds class metadata, not JIT code. The archive removes class loading and verification from the first session, and not warm-up (Measuring).
- deskd reads `deskd.version` from `/app/deskd.properties` through `spring.config.additional-location`, so no Java reads the file by hand.

## AOT rules
- `process-aot` runs in `prepare-package` and writes generated classes into `target/classes`, so the repackaged jar holds them. They are used only with `-Dspring.aot.enabled=true`.
- AOT evaluates conditions at **build** time, which fixes the set of beans. Nothing that varies at runtime may use `@Profile`, `@ConditionalOnProperty` or similar. Read values from the `Environment` when beans are created, and branch in code.
- The jar is repackaged because the Dockerfile unpacks it with `-Djarmode=tools`, which starts faster than a nested jar.

## Measuring
**How much of a session or a first Browser use is deskd's.** Each session leaves one INFO line, after its first RPC's reply or at its end, and each `browser.stream.set` that changes what its session wants leaves another. They carry monotonic times and nothing that says whose session it was. `journalctl -t deskd | grep timing` is the next real run's answer.

```
session timing first=true result=ok openMs=12 offerMs=1 createMs=30 connectMs=812 helloMs=2 firstRpcMs=3
browser.stream.set timing from=off to=live result=ok browserStartMs=812 streamStartMs=140 stopMs=- unitsMs=960 cdpMs=2400 totalMs=2400
```
| Span | From, to | Whose |
|---|---|---|
| `openMs` | `session.open` read off the gateway link, to accept or reject written to it | deskd, with token verification, and a JWKS fetch if one was needed |
| `offerMs` | The offer read off the link, to `session.create` handed to `RtcClient` | deskd |
| `createMs` | `session.create` handed over, to `session.answer` read off `rtc.sock` | Mostly `desk-rtc` |
| `connectMs` | The answer written to the link, to the first HELLO read off `rtc.sock` | Not deskd: the gateway, the client, ICE, DTLS and SCTP |
| `helloMs`, `firstRpcMs` | The message read off `rtc.sock`, to its reply handed to `RtcClient` | deskd |
| `browserStartMs`, `streamStartMs`, `stopMs` | One `units.sock` call for this request | `desk-units`, `systemctl` and the unit. deskd has only the call's own few lines around it |
| `unitsMs` | The request reaching `BrowserStream`, to its answer | The steps above, plus any wait for a step another request began |
| `cdpMs` | The same start, to a connection up with its tabs known | 0 if it was up already. Chromium's own start, then up to 250 ms of deskd's polling, then attach and which-tab-is-on-screen |
| `totalMs` | The later of `unitsMs` and `cdpMs` | |

`first=true` says no earlier session of this process got past `session.open`. `-` means that span didn't finish, or doesn't apply, and `cdpMs` is also `-` if another line was already waiting for Chromium, so that a client flipping states can't make waiting threads. Spans in deskd end when a reply is queued for the `rtc.sock` writer, so that writer's wake-up isn't counted.

`deskd ready in <ms> ms` is the uptime in `/proc/uptime` less the process's start ticks in `/proc/self/stat`, both on the kernel's boot clock. So it's good to about 10 ms and comparable across boots. (`ProcessHandle`'s `startInstant()` isn't: the JDK builds it from the whole-second `btime` in `/proc/stat`, which read about 690 ms high on the build machine.) In the container, the process start comes after docker and runc have done their part, so take a wall clock outside for the whole wake. Numbers from this machine are indicative only; the real ones come from c7g.large.

Last taken 2026-11-05 on this machine, from the unpacked jar with `deskd/docker/jvm.options` and its AppCDS archive, against the real `desk-rtc` and `gateway-shim`, eight runs of each, interleaved, with no TLS on the wire and no container. - **What it gained:** about 13% of the CPU to the gateway link and about 30% of the first session's. `helloMs` went from 1–3 to 0–2 and `firstRpcMs` from 1–7 to 0–2. A later session is 1 or 2 ticks and its `openMs` 3 to 7, so what's left of the first session's 5 or 6 ticks, mostly in `openMs`, is warm-up, which an archive of class metadata doesn't touch.
- **What it didn't gain, in wall time:** first-session setup and `openMs` are better on paper and inside the noise. These are the two runs before this one, at higher load: `openMs` 37–230 (46) against 30–141 (84) at load 3.5 to 5.9, and 52–313 (108) against 34–222 (166) at 7 to 9. So the highs come down and the median doesn't reliably move.

CPU up to context refresh is 371 to 389 ms (median of 5) and 386 to 385 (of 8). Relocating an archive twice the size at each start costs what loading those classes saved by then, and the savings come after. The link isn't reliably earlier either, though the CPU to it is less. Maps the archive where it was dumped, with nothing to patch: RssAnon 42 MiB against 60, RssFile 41 against 24, the same total, and up to 25 ms less CPU to refresh.
